# Saki 产品需求

## 定位

Saki 是建立在 DeepSeek Harness（DSH）之上的个人 Agent 中枢。它把多个开发与运营项目组织成可观察、可让 Agent 直接操作的 Project，先接管一个人的开发和运营，再扩展到业务系统，最终与组织成员共用。

Saki 不复制 IDE、项目管理工具或聊天机器人。它补的是这些工具之间缺失的那一层：项目登记、项目状态、工作到执行的关联，以及证明结果的证据。

## 问题

一个人带着 AI 同时维护多个全栈小项目。每个项目都有自己的仓库、部署、服务器、定时任务、费用和待办，散落在多个编辑器窗口、终端、对话和网页里。项目越多，切换时找回上下文、手工同步状态、确认"现在跑着什么、哪里坏了"的成本越高。

Agent 的工作也是散的：Session 和项目没有稳定关系，Agent 说做完了不等于真的做完，结果也不会自然回到 PR、CI 和部署状态。

## 产品原则

### 工作必须留下证据链

产品意图在文档里，原子工作在 Work Item 里，实施讨论在 PR 里，交付事实在 CI、部署和业务指标里。Saki 连接这些记录，不把聊天记录当作唯一事实来源。判定完成依据 Outcome Evidence，不依据 Agent 自报。

### 权威来源必须明确

Git、GitHub、DSH Session 和业务系统各自拥有自己的数据。Saki 只拥有项目关联、执行关联和必要缓存。展示的每份数据都要能看出来源和确认时间。

### 自动化渐进授权

自动化程度是每个 Project 的显式选择。手动模式由人触发和验收；自动模式只在规则允许的范围内领取、交付和完成工作。失败时停在可解释、可恢复的状态，预算耗尽绝不等于完成。

### Agent 上下文必须声明来源

Agent 的上下文可以来自 `AGENTS.md`、skill、Work Item、项目状态和历史证据，每项都要能追溯来源。外部事件和其他 Agent 的消息不能成为绕过规则的隐藏指令。

### 集成通用能力，拥有产品语义

模型、终端、文件、LSP、浏览器、SSH 和供应商接入由 DSH 或社区提供，Saki 不重复建设。Saki 拥有 Project、Resource Binding、工作到执行的关联、Outcome Evidence 和跨项目视图，这些是它存在的理由。

每次开始一项能力前做一次判断：

| 类别 | 判断标准 | 动作 |
| --- | --- | --- |
| 直接继承 | DSH 已提供稳定能力 | 通过 preset、skill 或插件装配，不复制实现 |
| 薄适配 | 外部能力存在，但接口与 Project 不一致 | 只写适配和必要映射 |
| Saki 拥有 | 承载 Saki 的核心语义 | 在本仓库实现 |
| 暂缓 | 不阻塞当前阶段，且 DSH 或社区很可能提供 | 记下缺口，不提前建设 |

### 自我优化走 PR

Saki 可以改进自己：Agent 修改本仓库的插件、skill、配置和文档，经分支、测试和 PR，由人合并后按锁定版本重新部署。Agent 不热改正在运行的自己，不自行升级 DSH 版本。

## 第一阶段：接管个人开发与运营

运行在一台香港 Linux 服务器上。DSH 从 npm 安装并锁定版本，Web UI 只监听本机，通过 SSH 隧道访问。

| 里程碑 | 交付 |
| --- | --- |
| M0 | DSH 在服务器上常驻，日常开发转移到上面 |
| M1 | Saki 插件：项目登记，以及每个项目的状态总览，Agent 能读写它 |
| M2 | 接入运营项目（如 ai-video-infra）：观察运行状态、费用和定时任务 |
| M3 | 自我优化闭环：Agent 对本仓库提出 PR 并附带证据 |

每个里程碑开始时再决定它的具体范围，不提前展开。

完成标准：我的大部分开发和运营项目在 Saki 中完成日常工作，不再依赖多窗口切换来找上下文。

## 后续阶段

只记方向，不做规划。

- **业务系统**：把运行中的业务系统登记为 Managed System，由承担长期职责的 Agent 值守、运营和恢复。
- **组织工作系统**：组织成员通过各自身份使用共享的 Project 与 Agent 能力，不接触主机凭据。

旧版产品需求和其中为这些阶段设计的机制（身份与授权、持久派发、预算账本、多 Host 等）保存在 `master` 分支的 `docs/saki/product-requirements.zh.md`。

# Saki 0.1.0 frontend contract

English | [中文](0.1.0-frontend-contract.zh.md)

This reference defines the information, state, navigation, and interaction obligations of the version 0.1.0 Web client. It deliberately does not choose layout, color, typography, density, illustration, motion style, visual hierarchy, or a responsive composition. Concept images may explore those choices without becoming implementation authority, and no requirement here implies that every address appears on one page. The [Web UI integration baseline](0.1.0-web-ui-baseline.md) defines which DSH surfaces remain intact and the small shell additions Saki requires.

## Client boundary

`packages/saki/web-ui` is a DSH client plugin with its browser implementation under `src/client/`. It composes through the existing client Cordis tree, services, stores, and typed slots; React remains a projection of immutable client snapshots. The package may use internal feature domains for Project selection, Work, Changes, Sessions, Attention, Model Supply, and Settings, but remains one package until a domain gains an independent Consumer or release lifecycle.

The browser uses `SakiAccess` for Access, bootstrap exchange, and logout, then reads protected Saki Projections and submits Control Intents through `saki-host-api`. Bootstrap and logout are the only product mutations outside Control Intent. The browser does not call GitHub, model providers, credential stores, system Git, or the filesystem directly. It never retains a Host path as an operation handle, constructs Principal, Actor, Browser Session, or Grant facts, or infers success from a notification. Existing DSH conversation, Terminal, settings, attachment, and tool-presentation capabilities are embedded through their services and slots rather than copied into Saki components.

The client cache is disposable. A complete Projection response is the only client baseline; `onChanged` and live Host frames invalidate keys and cause a re-query. Reconnect rebuilds affected snapshots. Client state may retain selection, expansion, drafts, and an optimistic overlay, but none of those values becomes product authority.

## View addresses and context

Each navigable state has a typed `SakiViewAddress` built from stable ids rather than paths or display names. An address identifies a destination or selection state, not necessarily a top-level page. Version 0.1.0 must preserve these addresses through Project switching and browser reload; serialization into public shareable URLs is optional until the Web client has a general routing facility.

| Address | Required context and return target |
| --- | --- |
| Work | Principal-scoped My Work across authorized Projects, with an optional presentation group or item; each item returns to its owning Project and source object |
| Project selector | The Project page without a selected Project; Installation and Host health sufficient to select or register a Development Project |
| Project / Board | Selected Project, Board or Inbox filter, and optional Work Item |
| Project / Milestones | Selected Project, Milestone, and optional Release |
| Project / Changes | Selected Project and Resource Binding revision, with optional file or Diff selection |
| Project / Sessions & Runs | Selected Project, Work Session, DSH Session, and optional Agent Run |
| Project / Trace | Selected Project and optional Work Item, Intent, Execution, Run, or evidence focus |
| Project / Settings | Selected Project, binding, GitHub mapping, default Agent Profile, Automation Policy, budgets, automatic-Done evidence, and synchronization state |
| Conversation (inherited) | DSH Session and optional Saki Project, Work Item, Work Session, or Agent Run return address |
| Settings (inherited) | Installation-level Provider Account Profiles, routes, context policies, and Generation Jobs |

Changing the current Development Project changes every internal Project destination together. Work remains cross-Project, and installation-wide Model Supply remains in inherited Settings, but every mutating affordance names its target Project. A Project switch never discards a draft, optimistic Intent, uncommitted Git state, pending question, or running operation; it either preserves the state under its owning address or asks for a deliberate resolution.

## Product surfaces

Version 0.1.0 adds exactly two top-level Saki pages. Work is the beginner-operable surface: it projects My Work across authorized Projects, uses plain-language groups, shows one next action per item, and hides Git, provider, budget and synchronization details until the user asks for technical details or recovery. It remains a Projection of the same authoritative objects and never weakens Grants or confirmation rules.

Project is the complex surface for one selected Development Project. Its internal destinations are Board, Milestones, Changes, Sessions & Runs, Trace and Project Settings. Only one destination occupies the main content area at a time. Addresses for those destinations resolve inside Project, while contextual Terminal access reuses DSH; selecting a Work Item, Session or Run preserves a return address to the owning section. Principal-scoped Attention resolves to Work, selected-Project automation and Run evidence resolve to Project, and installation-wide Model Supply resolves to Settings.

Session continues to reuse the existing DSH Conversation surface, while Settings remains deployment configuration. They are inherited DSH surfaces rather than additional Saki pages. The existing DSH AppFrame and sidebar also remain the shell. A generic `main.surface` chain slot chooses Work or Project only when its Saki address is active and otherwise renders Conversation. A generic `sidebar.primary.action` list slot places those daily product destinations immediately below New Session and above the Workspace browser. It is distinct from the existing `sidebar.footer.action`, which remains the bottom utility-extension area beside Settings. The Saki plugin uses existing session-header, conversation-view and settings-section slots for smaller additions.

## Access and bootstrap

Before authentication, the browser can read only an Access response with a closed `bootstrap-required`, `session-required`, or `unavailable` state and generic next-step text. It does not reveal the Installation id, whether a particular Principal or Grant exists, Project names, Host capabilities, challenge identifiers, or failure distinctions that would help test a secret. After authentication, the Access Projection may show the Principal's display identity, Browser Session expiry, local-only deployment state, and a request token derived server-side from the presented HttpOnly cookie; no independent verifier secret exists, and action availability remains in server-derived Projections rather than serialized Grant records.

The bootstrap form sends the one-time secret only in the POST body to the exact configured loopback origin. It never puts the secret in a URL, browser storage, analytics, error text, or client logs, and clears the input after the exchange. `exchangeBootstrap` commits challenge consumption and one Browser Session before emitting the HttpOnly, SameSite cookie. A lost response does not permit a retry with the consumed secret and the client does not infer whether cookie delivery occurred; it reloads Access and otherwise follows the generic replacement-challenge guidance. Every later state-changing request carries the authenticated Access Projection's derived session-bound request token in a header. Saki client code cannot read or persist the raw cookie held by the browser's HttpOnly cookie jar, and no durable Saki record persists the raw cookie or request token. The server authenticates the presented cookie by digest and recomputes the token for constant-time comparison after every restart. Expiry, revocation, logout, Principal retirement, or an Installation generation change clears affected caches and returns to the generic access state without exposing the previous Principal's data. A Grant change instead invalidates affected protected caches; the next query keeps the authenticated Principal but rechecks the current Grant and returns only the newly authorized Projection or a generic denied or unavailable result.

## Projection set

The first client consumes a small set of complete read models instead of joining backend records in the browser.

| Projection | Required facts |
| --- | --- |
| Access | Before authentication, only the closed required-action state and safe retry guidance; after authentication, Principal display identity, Browser Session expiry, local deployment state, and a server-derived session-bound request token; no raw cookie or independent verifier secret |
| My Work | Principal-scoped source Project and object, presentation group, Work Item Status, assignment, Run or Intervention summary, one recommended Action Offer, and its reason |
| Project index | Project identity, binding health, attention count, active Runs, GitHub freshness, and automation pause state |
| Development Workspace | Current Project, binding revision and display location, Git summary, primary Work Session, active operations, and blocking recovery |
| Board | Confirmed GitHub Sync Checkpoint, mapped columns and order, Inbox membership, optimistic overlays, filters, and mapping health |
| Work Item detail | Issue facts, acceptance criteria, assignment, Sessions, Agent Runs, Git and PR evidence, CI, interventions, and activity references |
| Milestone and Release | GitHub Milestone scope, title, due date and open or closed state; versioned Saki delivery phase and repair state; exact tag, recursively peeled Release Commit, included official Upstream Baseline, immutable Release Evidence, PR and CI evidence; independent observation time, failure, staleness and invalidation state |
| Changes | HEAD and branch observations, inherited, staged, unstaged and untracked changes, bounded Diff pages, and operation eligibility |
| Session view | Work Session identity, associated DSH Sessions, primary and historical Runs, intervention state, and existing DSH conversation projection |
| Execution Trace | Bounded, ordered references from Actor and Control Intent through Dispatch, Host Operation, Execution, Work Session, Agent Run, Intervention, usage, and Outcome Evidence, including lifecycle state and observation source |
| Project configuration | Configuration revision; read-only Resource Binding and GitHub mapping summaries with return addresses to their owning flows; editable default Agent Profile, Automation Policy actions and trigger mode, typed budgets, automatic-Done evidence rules, and synchronization policy; effective validation and repair state |
| Attention Inbox | Source object, severity, target Principal, target Project, required response, age, and return address |
| Automation | Policy revision, enabled actions, hard limits, reservations, settled usage, unknown observations, and pause reasons |
| Model Supply | Profile health, safe authentication state, model routes, Usage Snapshot age, context policy, and generation queue |

A Projection exposes display-safe locations and external URLs only where the Host has authorized them. Credential values, DPAPI ciphertext, GitHub App private material, local operation handles, mutable entities, and unbounded Diff or log bodies never enter these models.

An Action Offer is a Projection fact, not authority. The control plane derives it from the current Work Item Status, Triage Role or Work Assignment, open Intervention Requests, active Dispatch and Run state, the Principal's Grant, Automation Policy, and current binding, Git, synchronization, credential, and budget observations. The client never derives actions from Work Item Status alone. My Work places an item into ready to start, active, waiting for you, or recently finished as presentation groups and returns at most one recommended card Action Offer; alternative operations remain in the owning detail view. Submit request is a Work page action rather than a card Action Offer. An item awaiting acceptance remains waiting for you, while a Done or Canceled item never offers acceptance.

Submitting an Action Offer sends a typed Intent with the expected Projection revision. The control plane resolves the current Principal and re-evaluates authority and eligibility before accepting it, so a rendered action cannot authorize stale or otherwise disallowed work. When an expected action is unavailable, My Work returns a plain-language reason and offers a repair or inspection operation only when the Principal may perform it.

[K7 Project Settings (#51)](https://github.com/BreakfastDaPaiDang/saki/issues/51) is the sole frontend owner for editable default Agent Profile, Automation Policy, typed budgets, automatic delivery and Done evidence, and synchronization controls. It shows Resource Binding and GitHub mapping as read-only summaries linked to the K1 registration or rebind flow and K3 mapping or repair flow. K7 consumes Project configuration and Automation Projections and submits field-scoped, expected-revision configuration Intents only for its editable fields. The control plane returns effective validation and Action Offers; the client does not infer which policy can run, treat a saved form as activation, or turn an automatic-Done selection into evidence. K6 integration and recovery verification depends on K7 rather than duplicating configuration controls.

## State semantics

Every data-bearing view distinguishes the following conditions without relying on color alone.

| State | Client obligation |
| --- | --- |
| Confirmed | Identify the Projection revision or confirmation time that authorizes the displayed fact |
| Refreshing | Keep the confirmed value readable while indicating that a newer read is pending |
| Optimistic | Identify the pending Intent and preserve the confirmed value needed for rollback or conflict display |
| Stale or offline | Show age and failed source; never describe cached remote data as current |
| Conflict | Show requested and newly confirmed facts and require a new Intent for retry |
| Unavailable | Name the denied capability or dependency and preserve unaffected local functions |
| Repair required | Identify the broken GitHub mapping or Resource Binding and offer only attributed repair operations |
| Reconciliation required | Keep the ambiguous effect visible; do not offer a blind duplicate action |
| Intervention required | Show the durable request, authorized responder, blocking scope, and response status |
| Empty | Explain whether no objects exist, filters removed them, or a source has not completed its first scan |

An accepted Control Intent receives a stable receipt and remains visible until its resulting Projection confirms success, reports failure, conflicts, or requires reconciliation. A transport timeout is not a product failure. The client disables repeated submission while outcome inspection is pending unless the operation explicitly supports another independent Intent.

## Interaction flows

| Flow | Required outcome |
| --- | --- |
| Bootstrap Host Operator | Use `SakiAccess.exchangeBootstrap` without retaining the local secret, accept the opaque Browser Session only after the aggregate commit, reload Access, and reject replay or an unexpected origin without revealing Installation facts |
| Register Project | Select an existing directory, review resolved Git top level and duplicate or dirty-state evidence, confirm bindings, then open the Development Workspace |
| Submit request | Choose an authorized target Project, enter title, intended outcome and acceptance criteria, submit `CreateWorkItem` with Project id, expected Project revision, and expected GitHub mapping revision, and show the confirmed Work Item or a recoverable partial GitHub result |
| Move Work Item | Apply an optimistic overlay, perform expected-fingerprint mutation, confirm GitHub state, or show conflict and restore the confirmed card |
| Give to Agent | Display Profile, Model Route, requested permissions, binding health, inherited changes, and applicable limits before manual submission |
| Automatic claim | Show policy, Actor, reservation, Dispatch, Run, and pause evidence without requiring a click or hiding why work started |
| Review and deliver | Inspect bounded Diffs, select files, stage, commit, push, associate PR and CI, and accept or automatically complete only from Outcome Evidence |
| Inspect delivery and trace | Relate Milestone scope and Release tag to the exact Commit, then follow bounded attributed references without synthesizing a second event history |
| Configure Project | Edit default Profile, policy mode and actions, typed budgets, automatic-Done evidence, and synchronization through expected-revision Intents; show binding and mapping as read-only links to K1 and K3; keep prior confirmed configuration visible on conflict |
| Answer intervention | Open from Attention or the owning object, submit one expected-revision response, and converge on the separately confirmed result |
| Repair binding or mapping | Keep history readable, explain the broken observation, collect explicit replacement selection, and refresh before enabling mutations |
| Use model supply | Authorize a profile, inspect safe health and usage observations, choose a route at a safe boundary, and inspect Generation Jobs and outputs |

Submit request is a production Work page action rather than a prototype-only affordance or card Action Offer. The client preselects a Project only when it displays that choice for confirmation, then submits a `CreateWorkItem` Intent containing title, intended outcome, acceptance criteria, Project id and expected Project revision, and expected GitHub mapping revision. The control plane owns Issue creation, Project membership, Inbox status, idempotency, and recovery. If GitHub creates the Issue but a later step is unconfirmed, Work shows the known Issue and reconciliation or repair action instead of creating a local-only card or blindly resubmitting.

Risky operations require confirmation that names the affected Project and resource. This includes Project retirement, binding replacement without strong continuity evidence, takeover of inherited changes, push, automatic merge, automatic Done, credential removal, and budget exception. Ordinary reversible navigation, refresh, filters, and read-only inspection do not require confirmation.

Board drag has a keyboard-equivalent move operation. Every status, progress, conflict, and attention signal has text semantics and programmatic labels. Focus returns to the initiating object after a dialog or Intervention response. Long-running operations expose cancellation only when the backend operation supports it; closing a panel never implies cancellation.

## Client module responsibilities

The Saki client object layer owns Projection caching, Intent overlays, invalidation, view addresses, and selection. UI components receive data and actions through props and subscribe to immutable snapshots; they do not contain synchronization, retry, permission, or budget decisions. Frame-driven updates use the existing batched notification path, while immediate controlled-input echoes use the existing synchronous gesture path.

Saki registers the Work and Project pages through `main.surface`, their two primary navigation entries through `sidebar.primary.action`, and session or settings additions through existing typed slots. It consumes DSH conversation, Terminal, tool cards, settings, attachments, and file-opening capabilities through their published client services. Cross-domain value imports and a parallel global component registry are prohibited. A backend capability missing from the composed bundle produces an explicit unavailable Projection rather than removing controls through undocumented feature detection.

## Verification and remaining design work

Product-level Playwright flows boot the real Saki bundle, Host transport, control plane, Local Host adapter, temporary Git repositories, and controllable external Providers. They exercise Project registration, a beginner completing the Work cycle without technical controls, Project section switching without losing selection, Board refresh and conflict, manual and automatic launch, page-to-Session return with draft preservation, budget stop, reconnect, binding repair, intervention response, Diff-to-PR delivery, model authorization, and Generation Job output. Component tests cover only pure presentation and local interaction semantics; they do not replace the product flows.

Frontend work may be pre-split into K0 through K7 so ownership and dependencies are visible. K1 through K7 remain non-Ready and cannot begin production implementation until K0's low-fidelity interaction prototypes receive product approval and the backend Projection and Intent fixtures required by that slice are available. K0 proves the flows above on desktop and a constrained viewport without requiring simultaneous panes. Visual direction, density, layout, component styling, and branding remain open decisions; generated concept images are discussion artifacts, not this contract's acceptance criteria.

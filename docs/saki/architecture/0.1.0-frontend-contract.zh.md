# Saki 0.1.0 前端约定

[English](0.1.0-frontend-contract.md) | 中文

本文定义 0.1.0 版本 Web 客户端的信息、状态、导航和交互义务。它有意不选择布局、颜色、字体、密度、插图、动效风格、视觉层级或响应式组合。意向图可以探索这些选择，但不会成为实现权威，本文中的任何要求也不意味着所有 address 必须出现在一个页面。[Web UI 接入基线](0.1.0-web-ui-baseline.zh.md)定义哪些 DSH 页面保持不变，以及 Saki 需要的少量壳层增量。

## 客户端边界

`packages/saki/web-ui` 是 DSH 客户端 plugin，其浏览器实现在 `src/client/` 下。它通过现有客户端 Cordis tree、service、store 和类型化 slot 组合；React 继续作为不可变客户端 snapshot 的投影。该 package 可以为 Project 选择、Work、Changes、Sessions、Attention、Model Supply 和 Settings 使用内部功能 domain，但在某个 domain 获得独立 Consumer 或发布生命周期前保持为一个 package。

浏览器先通过 `SakiAccess` 执行 Access、bootstrap exchange 与 logout，再通过 `saki-host-api` 读取受保护 Saki Projection 并提交 Control Intent。Bootstrap 与 logout 是仅有的两个不经过 Control Intent 的产品 mutation。浏览器不直接调用 GitHub、模型提供方、凭据存储、系统 Git 或 filesystem。它绝不会把 Host 路径保留为 operation handle、构造 Principal、Actor、Browser Session 或 Grant 事实，也不会根据 notification 推断成功。现有 DSH conversation、Terminal、settings、attachment 和 tool-presentation 能力通过其 service 与 slot 嵌入，而不是复制到 Saki component 中。

客户端 cache 可以随时丢弃。完整 Projection response 是唯一客户端 baseline；`onChanged` 与活动 Host frame 使 key 失效并触发重新查询。重连会重建受影响 snapshot。客户端状态可以保留 selection、expansion、draft 和乐观 overlay，但这些值都不会成为产品权威。

## View address 与上下文

每个可导航状态都有一个根据稳定 id 而不是路径或显示名称构造的类型化 `SakiViewAddress`。Address 标识目的地或选择状态，不必对应一个顶层页面。0.1.0 必须在 Project 切换和浏览器 reload 后保留这些 address；在 Web 客户端获得通用 routing facility 前，把它们序列化成可公开分享 URL 是可选项。

| Address | 必需上下文与返回目标 |
| --- | --- |
| 工作 | 当前 Principal 在已授权 Project 中的 My Work，可选展示分组或条目；每项都返回其所属 Project 和来源 object |
| Project selector | 尚未选择 Project 的「项目」页；提供足以选择或登记 Development Project 的 Installation 与 Host 健康状态 |
| 项目 / 看板 | 已选择 Project、Board 或 Inbox filter，以及可选 Work Item |
| 项目 / 里程碑 | 已选择 Project、Milestone 和可选 Release |
| 项目 / 变更 | 已选择 Project 与 Resource Binding revision，以及可选 file 或 Diff selection |
| 项目 / 会话与运行 | 已选择 Project、Work Session、DSH Session 和可选 Agent Run |
| 项目 / 追溯 | 已选择 Project，以及可选 Work Item、Intent、Execution、Run 或 evidence focus |
| 项目 / 设置 | 已选择 Project、binding、GitHub mapping、默认 Agent Profile、Automation Policy、预算、automatic-Done evidence 和同步状态 |
| Conversation（继承） | DSH Session，以及可选 Saki Project、Work Item、Work Session 或 Agent Run return address |
| Settings（继承） | Installation 级 Provider Account Profile、route、context policy 和 Generation Job |

改变当前 Development Project 会一起改变「项目」的所有内部目的地。「工作」保持跨 Project，Installation 级 Model Supply 继续位于继承的 Settings，但每个 mutation affordance 都要标明目标 Project。Project 切换绝不会丢弃 draft、乐观 Intent、未提交 Git state、待回答 question 或运行中的 operation；它要么在所属 address 下保留状态，要么要求明确解决。

## 产品页面

0.1.0 只增加两个 Saki 顶层页面。「工作」是小白可操作的页面：它跨已授权 Project 投影 My Work，使用白话分组，每项只显示一个下一步操作，并在用户请求技术详情或进入恢复操作前隐藏 Git、provider、budget 和同步细节。它仍然投影相同的权威 object，绝不会弱化 Grant 或确认规则。

「项目」是面向一个已选择 Development Project 的复杂页面。它的内部目的地是看板、里程碑、变更、会话与运行、追溯和项目设置；主内容区每次只呈现一个目的地。这些目的地的 address 在「项目」内解析，上下文化 Terminal 入口复用 DSH；选择 Work Item、Session 或 Run 时保留返回所属区段的 address。Principal scope Attention 进入「工作」，所选 Project 的 automation 与 Run evidence 进入「项目」，Installation 级 Model Supply 进入 Settings。

Session 继续复用现有 DSH Conversation 页面，Settings 继续承载部署配置；它们是继承的 DSH 页面，不是新增 Saki 页面。现有 DSH AppFrame 与侧边栏也继续作为壳层。通用 `main.surface` chain slot 只在对应 Saki address 激活时选择「工作」或「项目」，否则渲染 Conversation。通用 `sidebar.primary.action` list slot 把这两个日常产品目的地放在 New Session 下方、Workspace browser 上方。它不同于现有 `sidebar.footer.action`；后者继续作为 Settings 旁边的底部实用扩展区。Saki plugin 使用现有 session header、conversation view 和 settings section slot 完成更小的增量。

## 访问与 bootstrap

认证前，浏览器只能读取 Access response，其中包含封闭的 `bootstrap-required`、`session-required` 或 `unavailable` 状态以及通用下一步说明。它不会暴露 Installation id、特定 Principal 或 Grant 是否存在、Project 名称、Host capability、challenge identifier，也不会提供可用于试探 secret 的失败差异。认证后，Access Projection 可以显示 Principal 的展示身份、Browser Session 过期时间、本地部署状态，以及服务端根据请求呈现的 HttpOnly cookie 派生的 request token；系统不存在独立 verifier secret，操作可用性继续来自服务端派生 Projection，而不是序列化 Grant 记录。

Bootstrap 表单只在 POST body 中把单次 secret 发给准确配置的 loopback origin。它绝不把 secret 放入 URL、浏览器存储、analytics、错误文本或 client log，并在交换后清空输入。`exchangeBootstrap` 在发出 HttpOnly、SameSite cookie 前 commit challenge 消费与一个 Browser Session。响应丢失时，已消费 secret 不允许重试，client 也不会推断 cookie 是否送达；它重新读取 Access，否则遵循通用替代 challenge 指引。此后每个改变状态的请求都在 header 中携带已认证 Access Projection 提供的派生 session-bound request token。Saki client code 无法读取或持久化由浏览器 HttpOnly cookie jar 持有的 raw cookie，且任何 Saki 持久记录都不保存 raw cookie 或 request token。服务端通过 digest 认证请求呈现的 cookie，并且每次重启后仍会重新计算 token 做 constant-time compare。过期、撤销、登出、Principal 退役或 Installation generation 变化会清除受影响 cache，并返回不暴露前一 Principal 数据的通用访问状态。Grant 变化则只使受影响的受保护 cache 失效；下一次 query 保持 Principal 已认证，但会重新检查当前 Grant，并且只返回新授权的 Projection 或通用 denied 或 unavailable result。

## Projection 集合

首个客户端消费一小组完整读模型，而不是在浏览器中 join 后端记录。

| Projection | 必需事实 |
| --- | --- |
| Access | 认证前只有封闭的必需操作状态与安全重试说明；认证后包含 Principal 展示身份、Browser Session 过期时间、本地部署状态和服务端派生的 session-bound request token；不包含 raw cookie，也不存在独立 verifier secret |
| My Work | Principal scope 的来源 Project 与 object、展示分组、Work Item Status、assignment、Run 或 Intervention 摘要、一个推荐 Action Offer 及其原因 |
| Project index | Project identity、binding health、attention count、活动 Run、GitHub freshness 和 automation pause state |
| Development Workspace | 当前 Project、binding revision 与展示位置、Git summary、主要 Work Session、活动 operation 和阻塞恢复项 |
| Board | 已确认 GitHub Sync Checkpoint、已映射 column 与 order、Inbox membership、乐观 overlay、filter 和 mapping health |
| Work Item detail | Issue 事实、验收条件、assignment、Session、Agent Run、Git 与 PR evidence、CI、intervention 和活动 reference |
| Milestone and Release | GitHub Milestone scope、title、due date 与 open 或 closed state；版本化 Saki delivery phase 与 repair state；准确 tag、递归 peel 后 Release Commit、纳入的官方 Upstream Baseline、不可变 Release Evidence、PR 与 CI evidence；独立 observation time、failure、staleness 与 invalidation state |
| Changes | HEAD 与 branch 观察、继承、staged、unstaged 和 untracked change、有界 Diff page 与 operation eligibility |
| Session view | Work Session identity、关联 DSH Session、主要和历史 Run、intervention state 与现有 DSH conversation projection |
| Execution Trace | 从 Actor 和 Control Intent 到 Dispatch、Host Operation、Execution、Work Session、Agent Run、Intervention、usage 与 Outcome Evidence 的有界有序 reference，包括生命周期状态与观察来源 |
| Project configuration | Configuration revision；带有返回 owner flow address 的只读 Resource Binding 与 GitHub mapping 摘要；可编辑的默认 Agent Profile、Automation Policy action 与触发模式、类型化预算、automatic-Done evidence rule 与同步 policy；有效 validation 和 repair state |
| Attention Inbox | Source object、severity、目标 Principal、目标 Project、所需回答、age 与 return address |
| Automation | Policy revision、已启用 action、硬 limit、reservation、已结算 usage、未知 observation 和 pause reason |
| Model Supply | Profile health、安全认证状态、model route、Usage Snapshot age、context policy 和 generation queue |

Projection 只在 Host 已授权时暴露展示安全位置与外部 URL。Credential value、DPAPI ciphertext、GitHub App private material、本地 operation handle、mutable entity，以及无界 Diff 或日志正文绝不会进入这些 model。

Action Offer 是 Projection 事实，不是权限来源。控制面根据当前 Work Item Status、Triage Role 或 Work Assignment、开放 Intervention Request、活动 Dispatch 与 Run 状态、Principal 的 Grant、Automation Policy，以及当前 binding、Git、同步、credential 和预算 observation 推导它；客户端绝不只根据 Work Item Status 推导操作。My Work 使用待开始、进行中、等你处理和最近结束作为展示分组，并且每项最多返回一个推荐 card Action Offer；其他操作留在所属详情中。「提交需求」是「工作」页操作，不是 card Action Offer。等待验收的条目仍属于等你处理，Done 或 Canceled 条目绝不提供验收。

提交 Action Offer 时会携带 expected Projection revision 并发送类型化 Intent。控制面解析当前 Principal，并在接受前重新评估权限与 eligibility，因此已经渲染的操作不能授权陈旧或本来不允许的工作。预期操作不可用时，My Work 返回白话原因，并且只在 Principal 有权执行时提供修复或检查操作。

[K7「项目设置」（#51）](https://github.com/BreakfastDaPaiDang/saki/issues/51)是可编辑默认 Agent Profile、Automation Policy、类型化预算、自动交付与 Done evidence，以及同步 control 在前端的唯一 owner。它把 Resource Binding 与 GitHub mapping 显示为只读摘要，分别链接到 K1 登记或 rebind flow 与 K3 mapping 或 repair flow。K7 消费 Project configuration 与 Automation Projection，并且只为自身可编辑字段提交字段 scope、带 expected revision 的配置 Intent。控制面返回有效 validation 与 Action Offer；客户端不会推断哪项 policy 可以运行、把已保存表单当作已激活配置，或把 automatic-Done 选择当作 evidence。K6 集成与恢复验证依赖 K7，不会复制配置 control。

## 状态语义

每个承载数据的 view 都会区分以下条件，且不只依赖颜色。

| 状态 | 客户端义务 |
| --- | --- |
| Confirmed | 标明授权显示事实的 Projection revision 或确认时间 |
| Refreshing | 在表明较新读取待完成的同时，保持已确认值可读 |
| Optimistic | 标明待定 Intent，并保留 rollback 或 conflict 展示所需的已确认值 |
| Stale or offline | 显示时效与失败来源；绝不把缓存远端数据描述为当前状态 |
| Conflict | 显示请求事实与新确认事实，并要求使用新 Intent 重试 |
| Unavailable | 标明被拒绝的 capability 或 dependency，并保留未受影响本地功能 |
| Repair required | 标明损坏的 GitHub mapping 或 Resource Binding，并且只提供带归因修复 operation |
| Reconciliation required | 保持歧义 effect 可见；不提供盲目重复操作 |
| Intervention required | 显示持久请求、授权 responder、blocking scope 和 response status |
| Empty | 解释是不存在 object、filter 排除了它们，还是 source 尚未完成首次扫描 |

已接受 Control Intent 会获得稳定 receipt，并保持可见，直到产生的 Projection 确认成功、报告失败、发生 conflict 或要求 reconciliation。Transport timeout 不是产品失败。Outcome inspection 待完成时，客户端禁用重复提交，除非 operation 明确支持另一条独立 Intent。

## 交互流程

| 流程 | 必需结果 |
| --- | --- |
| Bootstrap Host Operator | 通过 `SakiAccess.exchangeBootstrap` 使用且不保留本地 secret，只在 aggregate commit 后接受不透明 Browser Session，重新读取 Access，并且在不暴露 Installation 事实的情况下拒绝 replay 或意外 origin |
| Register Project | 选择已有目录，复核已解析 Git top level 以及重复或 dirty-state evidence，确认 binding，然后打开 Development Workspace |
| Submit request | 选择有权访问的目标 Project，填写 title、intended outcome 与 acceptance criteria，携带 Project id、expected Project revision 和 expected GitHub mapping revision 提交 `CreateWorkItem`，并显示已确认 Work Item 或可恢复的 GitHub 局部结果 |
| Move Work Item | 应用乐观 overlay，执行 expected-fingerprint mutation，确认 GitHub 状态，或显示 conflict 并恢复已确认卡片 |
| Give to Agent | 手动提交前显示 Profile、Model Route、所需权限、binding health、继承变更与适用 limit |
| Automatic claim | 无需点击就显示 policy、Actor、reservation、Dispatch、Run 与 pause evidence，且不隐藏工作启动原因 |
| Review and deliver | 检查有界 Diff、选择 file、stage、commit、push、关联 PR 与 CI，并且只根据 Outcome Evidence 验收或自动完成 |
| Inspect delivery and trace | 把 Milestone scope 与 Release tag 关联到准确 Commit，再沿有界且带归因的 reference 追溯，不合成第二套 event history |
| Configure Project | 通过带 expected revision 的 Intent 编辑默认 Profile、policy 模式与 action、类型化预算、automatic-Done evidence 和同步配置；把 binding 与 mapping 显示为链接到 K1 与 K3 的只读信息；发生 conflict 时保持先前已确认配置可见 |
| Answer intervention | 从 Attention 或所属 object 打开，提交一条 expected-revision response，并收敛到单独确认的结果 |
| Repair binding or mapping | 保持历史可读，解释损坏 observation，收集明确替代选择，并在启用 mutation 前刷新 |
| Use model supply | 授权 profile、检查安全 health 与 usage observation、在安全边界选择 route，并检查 Generation Job 与 output |

「提交需求」是生产版「工作」页操作，不是仅存在于 prototype 的 affordance 或 card Action Offer。Client 只会在明确显示并要求确认时预选 Project，然后提交 `CreateWorkItem` Intent，其中包含标题、预期结果、验收条件、Project id 与 expected Project revision，以及 expected GitHub mapping revision。控制面拥有 Issue 创建、Project membership、Inbox status、幂等与恢复。若 GitHub 已创建 Issue、但后续步骤尚未确认，「工作」会显示已知 Issue 以及 reconciliation 或 repair 操作，不会创建仅本地存在的卡片或盲目重新提交。

高风险 operation 需要确认，且确认内容标明受影响 Project 与 resource。其中包括 Project 退役、缺少强连续性证据的 binding replacement、继承变更 takeover、push、automatic merge、automatic Done、凭据移除和预算例外。普通可逆导航、refresh、filter 与只读检查不需要确认。

Board drag 提供键盘等效移动操作。每个 status、progress、conflict 与 attention signal 都有文字语义和程序化 label。Dialog 或 Intervention response 结束后，focus 返回发起 object。长时间 operation 只有在后端 operation 支持时才暴露 cancellation；关闭 panel 绝不意味着取消。

## 客户端 module 职责

Saki 客户端 object layer 拥有 Projection cache、Intent overlay、invalidation、view address 与 selection。UI component 通过 prop 接收 data 与 action，并订阅不可变 snapshot；其中不包含同步、重试、权限或预算决定。Frame-driven update 使用现有批量 notification 路径，而即时 controlled-input echo 使用现有同步 gesture 路径。

Saki 通过 `main.surface` 登记「工作」与「项目」，通过 `sidebar.primary.action` 登记这两个主要导航入口，并通过现有类型化 slot 登记 Session 或 Settings 增量。它通过已发布客户端 service 消费 DSH conversation、Terminal、tool card、settings、attachment 和 file-opening capability。禁止跨 domain value import 与并行全局 component registry。组合 bundle 中缺失的后端 capability 会产生明确 unavailable Projection，而不是通过未记录 feature detection 移除 control。

## 验证与剩余设计工作

产品级 Playwright flow 启动真实 Saki bundle、Host transport、控制面、Local Host adapter、临时 Git repository 与可控制外部 Provider。它们覆盖 Project 登记、小白无需技术 control 完成「工作」闭环、切换「项目」内部区段时不丢失 selection、Board refresh 与 conflict、手动与自动启动、从页面返回 Session 时保留 draft、预算停止、重连、binding repair、intervention response、Diff 到 PR 交付、模型授权和 Generation Job output。Component test 只覆盖纯展示与本地交互语义；它们不能替代产品 flow。

前端工作可以预先拆成 K0 至 K7，以便明确所有权与依赖；K1 至 K7 必须保持非 Ready，并且只有 K0 的低保真交互 prototype 获得产品确认、该切片需要的后端 Projection 与 Intent fixture 可用后，才可以开始生产实现。K0 证明上述流程可以在 desktop 与受限 viewport 上完成，且不需要同时显示多个 pane。视觉方向、密度、布局、component styling 与 branding 继续保持开放；生成的意向图是讨论 artifact，不是本约定的验收条件。

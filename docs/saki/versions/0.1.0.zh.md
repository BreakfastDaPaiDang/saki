# Saki 0.1.0 实现规格

[English](0.1.0.md) | 中文

状态：草稿，供第一阶段首个可用切片评审。本文从 [产品需求](../product-requirements.md)派生，不替代长期产品边界。

## 版本命题

0.1.0 引入第一个产品角色 Host Operator，并让该操作者可以在 Saki Web UI 中完成一个真实 Development Project 从 Work Item 到合并的最小开发闭环。版本不试图完成整个“Agent 原生开发系统”阶段。

## 目标

1. 把本地目录登记为 Development Project，稳定关联 DSH Workspace、Git 工作树和 GitHub Repository。
2. 在一个 Saki 窗口切换多个 Development Project，并理解每个项目的工作、代码和交付状态。
3. 从 Ready Work Item 手动或自动启动 Agent Session，并自动提供正确工作目录和上下文。
4. 查看 Agent 产生的文件变化和 Git Diff，完成文件级暂存、取消暂存、提交和显式推送。
5. 查看并更新 GitHub Issue、Project Status、Milestone、PR 和 Actions 结果。
6. 重启 Saki 后恢复 Project Binding、Work Item、Agent Run 和 Session 关联。
7. 使用 Saki 仓库完成至少一次真实 Issue 到合并流程。

## 非目标

0.1.0 不提供 Monaco 或其他完整手写代码编辑器、VS Code 扩展兼容层、SSH 远程开发、多 Host 执行、持久 Agent Identity、多用户登录、组织权限、共享模型配额、通用定时任务、飞书或 QQ 集成、浏览器控制、电脑控制和完整供应商账号管理。

复杂 Git 历史编辑、逐 hunk 暂存、交互式 rebase、冲突编辑器、stash 管理和完整分支管理不进入发布条件。操作者可以使用 Saki Terminal 或 Agent 处理这些操作。

## 产品角色

Host Operator 拥有本机目录、Git 仓库、GitHub 资源和模型供应能力，并负责 Project 配置与高风险授权。数据模型不得假定系统永远只有一个用户，但 0.1.0 的界面和权限流程不为后续角色增加复杂度。

## 用户故事

1. Host Operator 可以从已有 DSH Workspace 或本地目录登记 Development Project。
2. Saki 自动检测 Git 仓库和 GitHub remote，并让操作者确认关联。
3. Host Operator 可以快速切换 Development Project，并看到需要注意的 Work Item、未提交修改、待审 PR 和失败 CI。
4. Host Operator 可以创建 GitHub Issue，并使其进入所选 GitHub Project 的 Inbox。
5. Host Operator 可以在 Board 上拖动 Work Item，并把状态与排序同步到 GitHub Projects v2。
6. Work Item 详情同时展示验收条件、Blockage、Milestone、Agent Run、PR、CI 和 Outcome Evidence。
7. 手动模式从 Ready 显式点击“交给 Agent”；自动模式按 Automation Policy 无需点击即可领取。
8. 自动模式可以在完成证据满足后提交、交付并自动 Done。
9. Host Operator 可以继续活动 Agent Run 的 Session，并区分等待输入、成功、失败和取消。
10. Host Operator 可以查看 Git 状态和逐文件 Diff，并按文件暂存、取消暂存和提交。
11. Host Operator 可以显式推送分支并创建或关联 PR。
12. Milestone View 可以展示范围、状态分布、Blockage 和 Release 事实。
13. GitHub、目录或 Agent 暂时不可用时，Saki 保留可恢复状态并说明失败位置。

## Development Project 与并发

一个 Development Project 持久关联一个 DSH Workspace、一个 Git 工作树和一个可选 GitHub Repository。一个仓库的多个 worktree 可以登记为多个 Development Project，但同一个工作树同时只能有一个可写 Agent Run。该决定见 [ADR 0003](../../adr/0003-development-project-worktree-ownership.md)。

Project Binding 保存稳定标识符和可重新验证的定位信息，不复制 Git 或 GitHub 拥有的完整权威数据。目录丢失、remote 改变或权限不足时，Project 保留身份并进入需要修复的状态。

## 信息架构

- **Projects**：Development Project 列表和注意事项摘要。
- **Work**：Board、Milestone View 和 Work Item 详情。
- **Changes**：Git 状态、Diff、暂存区、分支和提交入口。
- **Sessions**：当前 Project 的 Agent Session 和 Agent Run 关联。
- **Terminal**：固定到当前 Development Project 的 DSH 终端。
- **Project Settings**：Project Binding、GitHub Project、默认 Agent Profile、Automation Policy 和同步状态。

切换 Development Project 必须同时切换 Work、Changes、Sessions 和 Terminal 的上下文。任何修改代码、GitHub 或 Work Item 的操作都必须显示目标 Project。

## 前端设计缺口

本规格只确定信息与行为，不确定最终布局、视觉层级和响应式形态。拆分前端实现 Issue 前仍需完成 Projects 总览、Board、Work Item 详情、Changes、Session 关联、Automation Policy 和失败恢复的低保真流程，并验证用户能在不打开 VS Code 的情况下完成 dogfood；视觉系统和高保真设计可以后续演进。

## Board

Board 默认只显示当前 Development Project，并筛选所选 GitHub Project 中属于关联 Repository 的 Issue。其他仓库 Issue、PR 和 draft item 不进入 0.1.0 Board。

固定列为 Inbox、Backlog、Ready、In progress、In review 和 Done。Canceled 默认位于归档筛选器；Blockage 是标记和筛选条件，不增加 Blocked 列。

GitHub Projects v2 的 Status 和 item position 是 Work Item Status 与手动排序的远端权威来源，见 [ADR 0001](../../adr/0001-github-projects-v2-work-authority.md)。Saki 把固定状态映射到所选 Project 的 Status 选项，不要求组织统一其他 Project 的命名。

关联 Repository 中尚未加入 Project 的开放 Issue 显示在 Inbox，并带有“未加入 Project”标记。把卡片移出 Inbox 时，Saki 先加入 Project，再写入目标 Status；Saki 新建 Work Item 时同时创建 Issue、加入 Project 并设置 Inbox，部分失败必须展示已完成事实和恢复操作。

每张卡片按信息存在情况显示标题、Issue 编号、Milestone、Blockage、Agent Run、分支或 PR、CI 和更新时间。详情面板显示正文、验收条件、状态、Milestone、Agent Run、Session、Git 变更、PR、CI、Outcome Evidence 和活动记录。

拖动卡片时，Saki 乐观更新本地显示并写入 GitHub；写入失败则恢复到已确认远端状态并显示可重试错误。外部变化通过手动刷新和后台轮询同步，0.1.0 不要求 Webhook，但必须显示最后成功时间和错误。

Inbox 至 In review 对应开放 Issue，Done 和 Canceled 对应关闭 Issue。重新打开 Issue 时恢复最近的非终态；没有记录时进入 Backlog。外部关闭活动 Issue 时，Saki 要求归类为 Done 或 Canceled。

每列使用 GitHub Project item position。若某种 GitHub View 排序无法由 API 表达，Saki 必须说明该 View 只同步状态。

## Agent 与自动化

Ready 表示 Work Item 可以领取。手动模式只有在 Host Operator 点击“交给 Agent”后才创建 Agent Run；自动模式持续领取满足 Automation Policy 的 Ready Work Item。领取成功后，Work Item 才进入 In progress。

手动模式中，Agent 完成一轮执行不会自动 Done。创建或关联 PR 后，Saki 可以进入 In review 并等待操作者验收。自动模式可以分别授权提交、推送、创建 PR、自动合并和 Done，但必须保存触发原因、权限、测试、Commit、PR、CI 或其他 Outcome Evidence，不能只根据 Agent 自报成功。

一个 Work Item 同时只能有一个活动 Agent Run。Agent Run 至少区分 Starting、Running、Waiting for user、Succeeded、Failed 和 Canceled；Agent Run Failed 不自动改变 Work Item Status，而是在卡片上增加需要处理的执行结果。

Agent 输入必须包含 Work Item 标识、标题、正文、验收条件、Blockage、Development Project 标识、Agent Profile 标识和工作目录。任何进入模型请求的附加上下文都必须标明来源，并能够从 Session 记录重建。

0.1.0 至少提供一条可实际使用的 Codex Agent 路径，并复用 DSH 的模型、per-session Agent Preset 和 Provider 扩展。每个 Development Project 在界面上只需选择一个默认 Development Agent Profile，但持久化关系使用稳定 Profile 标识，Agent Run 记录实际 Profile，使后续版本能够在同一 Project 中增加多个 Profile；Work Item 不直接绑定模型供应商。

Agent Profile 只定义这类开发工作如何执行，不是持久 Agent 主体。0.1.0 的一次性 Development Agent Run 可以不绑定 Agent Identity，但必须记录触发者、实际 Profile 版本和本次运行事实；该决定见 [Agent Operations ADR 0001](../../adr/agent-operations/0001-agent-identity-profile-run.md)。

## 核心流程

### 登记 Development Project

1. Host Operator 选择本地目录或 DSH Workspace。
2. Saki 检测 Git 工作树、分支、remote 和候选 GitHub Repository。
3. Host Operator 确认 Project Binding、GitHub Project 和默认 Development Agent Profile。
4. Saki 验证路径、Git 和 GitHub 权限并创建 Project。
5. Projects 显示该项目的工作、代码和交付摘要。

### 从 Work Item 启动 Agent

1. Work Item 位于 Ready，具有验收条件且没有 Blockage。
2. 手动模式由 Host Operator 点击领取；自动模式由 Automation Policy 领取。
3. Saki 检查活动可写 Run、未归属修改、受保护分支、凭据、预算和并发。
4. Saki 创建 Agent Run 和 Session，并写入 Work Item 上下文。
5. Work Item 进入 In progress，卡片显示启动来源、Run 状态和 Session 入口。

### 审阅与交付

1. Changes 显示工作树、暂存区、逐文件 Diff 和来源 Agent Run。
2. 手动模式允许按文件暂存、取消暂存、运行命令、要求修正和提交已确认修改。
3. 推送后创建或关联 PR，Board 展示 PR 与 Actions，Work Item 进入 In review。
4. 手动模式由 Host Operator 验收；自动模式按 Automation Policy 检查 Outcome Evidence。
5. Done 关闭 Issue，并更新 Milestone 进度。

### 恢复中断工作

1. Saki 重启后重新验证 Project Binding。
2. Projects 突出显示活动 Agent Run、未提交修改和待审 PR。
3. Host Operator 可以继续持久化 Session；已终止终端明确显示不可恢复。

## Milestone View

GitHub Milestone 是交付范围，Milestone View 展示目标日期、Work Item 总数、各状态数量、Blockage 和关联 Release。Milestone Phase 为 Planned、In Progress、Ready to Release、Released 或 Canceled，不与 Work Item Status 共用列。

Release 使用 `saki-v*` tag 绑定确切 Release Commit，并记录纳入的 Upstream Baseline。0.1.0 不实现甘特图、复杂路线图或跨仓库发布列车。

## Git 能力

Changes 提供工作树状态、逐文件 Diff、暂存区 Diff、文件级暂存与取消暂存、提交信息、提交、当前分支和 remote。已提交分支由 Host Operator 显式推送；PR 标题和正文由 Work Item 预填并可编辑。

Web UI 不解析 Git 命令输出或持有文件系统权限。Git 操作位于 Host 侧 Provider，第一版调用系统 Git 并返回结构化结果，以便未来替换实现。

## 控制面与执行面

0.1.0 在同一进程与仓库内逻辑分离两个面。控制面拥有 Project、Work Item 投影、Agent Profile、Automation Policy、Agent Run 请求与历史投影；执行面通过 Host Provider 和 DSH 运行时解析 Workspace、操作 Git、创建 Session、运行工具与模型，并回报状态事件和 Outcome Evidence。

Web View 只向控制面提交用户意图，不直接访问文件系统、Git 进程、DSH Session 或凭据。控制面通过结构化 Execution 接口发送带稳定标识、Project、工作目录引用、Profile 版本、触发来源和限制的请求；执行面返回结构化事件与结果，不直接改写 Board 或其他控制面状态。

该分离不要求 0.1.0 实现 RPC、独立队列或微服务。接口不传递活进程句柄、凭据内容或仅本机可理解的隐式状态，以使后续远程 Host 能在不重写产品编排的情况下增加网络适配器。该决定见 [ADR 0004](../../adr/0004-control-and-execution-planes.md)。

## 数据所有权

| 数据 | 权威来源 | Saki 的责任 |
| --- | --- | --- |
| Workspace 身份和目录 | DSH Workspace | 关联、验证和恢复 |
| 工作树、分支、暂存区和 Commit | 本地 Git | 读取并执行明确操作 |
| Repository、Issue、PR 和 Actions | GitHub | 展示并提交授权修改 |
| Work Item Status 和手动顺序 | GitHub Project | 映射固定状态并双向同步 |
| Milestone 范围 | GitHub Milestone | 展示范围与进度 |
| Agent Session | DSH Session | 按 Development Project 恢复 |
| Agent Preset 组成 | DSH Agent Preset | 为每个 Session 装配工具与 prompt |
| Agent Profile、Agent Run、Automation Policy 和 Resource Binding 元数据 | Saki 控制面 | 持久化 Project 关联、配置版本、执行关系和策略 |
| Release Tag 与 Commit | Git 和 GitHub Release | 展示交付事实 |

缓存必须包含来源和最后同步时间，不成为第二权威来源。Work Item 上下文进入模型前必须写入可恢复的 Session 事件。

## GitHub 身份与凭据

GitHub 集成涉及四种独立身份：登录 Saki 的人、调用 GitHub API 的 Actor、执行 `git push` 的凭据和 Commit author。0.1.0 不能因为当前四者恰好属于 Host Operator 就把它们持久化成同一个概念。

| 方式 | 能力与优点 | 代价与限制 | 适用位置 |
| --- | --- | --- | --- |
| 系统 Git Credential Manager 或现有 `gh` 登录 | 直接继承 Host Operator 已有访问，开发成本最低 | 属于个人且权限可能较宽，难以用于无人值守与多用户审计 | 0.1.0 的 `git push` 与开发期 bootstrap |
| GitHub App installation token | 代表 App，在指定账号和 Repository 范围内按最小权限运行；适合无人值守自动化，短期令牌可以自动轮换 | 操作归因于 App，不代表某个用户；需要保存 App 私钥和 installation ID | Board 同步、Issue、PR、CI 查询和后续自动化 |
| GitHub App user access token | 代表具体用户，权限是“用户权限与 App 权限”的交集，可使用 Web 或 Device Flow | 需要登录、刷新、撤销和每用户授权状态；App 还必须安装在目标组织 | 第三阶段用户登录、个人项目和以用户身份操作 |
| 用户令牌与 installation token 组合 | 人工操作归因于用户，后台自动化归因于 App，权限和审计最清楚 | 实现和测试复杂度最高 | 第三阶段目标架构 |

阶段性建议是：0.1.0 不实现 Saki 多用户登录，`git push` 继续使用系统 Git 凭据；新建独立的 Saki Product GitHub App，以 installation token 执行 GitHub Project、Issue、PR 和 Actions API。第三阶段再增加 GitHub App user authorization，并支持 Device Flow，使个人操作使用用户令牌、无人值守工作继续使用 installation token。现有 upstream automation App 保持独立，不扩大为产品身份。

如果接受该方案，0.1.0 的 Saki Product App 只申请组织 Projects 读写、Repository Issues 和 Pull requests 读写，以及 Actions、Checks 和 Commit statuses 读取；Metadata 保留必需的只读权限。`git push` 使用系统 Git 凭据期间不申请 Contents 写权限，也不申请 Workflows 写权限。只有产品明确改为使用 App 创建 Commit、推送分支或编辑 workflow 文件时才增加对应权限。

GitHub 官方将 installation token 定位为无人输入的自动化身份，将 user access token 定位为代表具体用户的身份；installation token 一小时过期，GitHub App 的 user access token 默认八小时过期并可用 refresh token 更新。Device Flow 适用于无浏览器、CLI 和桌面应用。参考 [GitHub App 身份类型](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/about-authentication-with-a-github-app)、[installation token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)和 [user access token 与 Device Flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)。

该建议仍待确认。确认前不扩大现有 App 权限，也不把 GitHub 用户授权写进 0.1.0 发布条件。

## 能力来源判断

| 能力 | 0.1.0 策略 | 长期判断 |
| --- | --- | --- |
| Workspace、Session、Terminal、文件工具、模型 Provider、插件运行时 | 直接继承 DSH | DSH 拥有 |
| 每个 Session 的工具、prompt、persona 和 context 组成 | 把 Agent Profile 映射到 DSH Agent Preset | DSH 拥有运行时组成，Saki 拥有 Project Profile 关系 |
| 多模型供应商、插件市场、浏览器、电脑控制、LSP、SSH、完整编辑器 | 不进入 0.1.0，持续观察并优先集成 | DSH 或社区更可能提供通用实现 |
| Git 状态、Diff、暂存和提交 | 实现最薄 Host Provider | 通用能力成熟后可替换或向上游贡献 |
| GitHub API | 实现独立、可替换 Provider | 平台 Adapter，不承载 Board 产品语义 |
| Development Project、Resource Binding、Board 映射、Agent Run 关联、Automation Policy、Outcome Evidence | 在 Saki 插件中实现 | Saki 必须拥有 |
| 前端代码编辑器 | 暂缓，Terminal、Agent 修改和 Diff 审阅兜底 | 不与成熟社区编辑器实现竞争 |

## 失败与恢复

- GitHub 不可达时，本地 Git、Session 和 Terminal 仍可使用；Board 显示缓存与离线状态，不伪造远端写入成功。
- 本地目录不存在时，Project 保留并提示重新定位或移除 Resource Binding。
- 切换 Project 不得丢弃或隐藏未提交修改。
- GitHub Project 字段缺失或映射无效时，Board 进入只读修复模式并指出缺失字段。
- Agent 启动失败时，Work Item 不得留在虚假的 In progress。
- 自动模式缺少预算、并发、凭据、工作树安全条件或完成证据时停止并等待人工处理，不放宽策略继续执行。
- Session 可恢复但终端进程不可恢复时，界面分别展示两个事实。

## 验证策略

主要自动化验收使用产品级 Web 流程：Playwright 驱动真实 Saki Web UI 和临时 Git 仓库，通过可控 GitHub Provider 与 Agent Provider 覆盖项目登记、Board 同步、手动和自动启动、代码变化、提交、In review 与基于证据的自动 Done。

GitHub API 与 Agent Provider 保留少量接口测试，但不以大量组件 Mock 测试替代产品流程。外部网络、真实组织权限和付费模型不进入必需 CI。

发布前在真实 `BreakfastDaPaiDang/saki` Project 执行 dogfood：手动模式完整完成一次 Ready 到 Done；自动模式至少自动领取一个受控 Work Item，并在配置的 Outcome Evidence 满足后自动 Done；重启后 Project 和 Session 状态仍可恢复。

## 发布条件

1. Saki 自身已登记为 Development Project，并通过日常启动入口稳定运行。
2. 核心用户流程的产品级自动化验收通过。
3. 真实 dogfood 至少成功一次。
4. Host Operator 可以在不打开 VS Code 的情况下完成 dogfood；允许使用 Saki Terminal 和外部浏览器完成登录。
5. GitHub 或 Agent 暂时不可用时，Saki 说明失败并保留可恢复状态。
6. 上游 DSH 同步不会覆盖 Saki 的 Project Binding、Board 或 Agent Run 数据。
7. 自动模式能够无人点击地领取和交付，并在预算、并发、权限或验证失败时安全停止。
8. 关键前端流程已经过低保真验证；高保真视觉不阻塞发布。

# Saki 0.1.0 实现规格

[English](0.1.0.md) | 中文

状态：草稿，供第一阶段首个可用切片评审。本文从 [产品需求](../product-requirements.zh.md)派生，不替代长期产品边界。

## 版本命题

0.1.0 引入第一个产品角色 Host Operator，并让该操作者可以在 Saki Web UI 中完成一个真实 Development Project 从 Work Item 到合并的最小开发闭环。版本不试图完成整个“Agent 原生开发系统”阶段。详细实现分为[后端架构](../architecture/0.1.0-backend.zh.md)与[前端约定](../architecture/0.1.0-frontend-contract.zh.md)。

## 目标

1. 把本地目录登记为 Development Project，稳定关联 DSH Workspace、Git 工作树和 GitHub Repository。
2. 在一个 Saki 窗口切换多个 Development Project，并理解每个项目的工作、代码和交付状态。
3. 从 Ready Work Item 手动或自动启动或继续 Work Session，并自动提供正确工作目录和上下文。
4. 查看 Agent 产生的文件变化和 Git Diff，完成文件级暂存、取消暂存、提交和显式推送。
5. 查看并更新 GitHub Issue、Project Status、Milestone、PR 和 Actions 结果。
6. 重启 Saki 后恢复 Project Binding、Work Item、Execution Dispatch、Intervention Request、Agent Run 和 Session 关联。
7. 使用 Saki 仓库完成至少一次真实 Issue 到合并流程。
8. 通过具名 Provider Account Profile 使用真实 Codex 与 Kimi 订阅 Route，并查看认证与用量状态。
9. 通过由证据选择而非硬编码模型窗口的可观测、可恢复上下文管理继续长时间 Work Session。
10. 加载支持仓库规划、实现、审阅和 handoff 工作流的可版本化 Saki Development Skill Pack。
11. 通过一条经过验证的提供方路径生成和编辑 Project 图片产物，并支持有上限的并发 Job。
12. 在不重置 Project 的情况下升级持久化 Saki 状态，并完成一次加密 Installation Export 与替换 Host restore 演练。

## 非目标

0.1.0 不提供 Monaco 或其他完整手写代码编辑器、VS Code 扩展兼容层、SSH 远程开发、多 Host 执行、持久 Agent Identity、Agent 专属 Attention Inbox、Project Coordinator、会话间自主协调、多用户登录、组织权限、共享模型配额、以绕过提供方限制为目的的自动轮换、通用提供方市场、通用定时任务、飞书或 QQ 集成、浏览器控制、电脑控制和完整供应商账号管理。

复杂 Git 历史编辑、逐 hunk 暂存、交互式 rebase、冲突编辑器、stash 管理、完整分支管理和完整 backup 管理 Web UI 不进入发布条件。操作者可以使用 Saki Terminal、PowerShell 7 或 Agent 处理这些操作。

## 产品角色

Host Operator 引导一个 Saki Installation 及其已登记 Local Host，拥有本机目录、Git 仓库、GitHub 资源和模型供应能力，并负责 Project 配置与高风险授权。首次启动通过短期、单次的本地 bootstrap flow 创建一个本地 human Principal，并为其配置 Host Operator Grant。数据模型不得假定系统永远只有一个用户，但 0.1.0 的界面和权限流程不为后续角色增加复杂度。

## 用户故事

1. Host Operator 可以从已有 DSH Workspace 或本地目录登记 Development Project。
2. Saki 自动检测 Git 仓库和 GitHub remote，并让操作者确认关联。
3. Host Operator 可以快速切换 Development Project，并看到需要注意的 Work Item、未提交修改、待审 PR 和失败 CI。
4. Host Operator 可以创建 GitHub Issue，并使其进入所选 GitHub Project 的 Inbox。
5. Host Operator 可以在 Board 上拖动 Work Item，并把状态与排序同步到 GitHub Projects v2。
6. Work Item 详情同时展示验收条件、Blockage、Milestone、Agent Run、PR、CI 和 Outcome Evidence。
7. 手动模式从 Ready 显式点击“交给 Agent”；自动模式按 Automation Policy 无需点击即可领取。
8. 自动模式可以在完成证据满足后提交、交付并自动 Done。
9. Host Operator 可以打开并继续 Work Item 的主要 Work Session，并区分其当前或最近 Agent Run 的等待输入、成功、失败和取消状态。
10. Host Operator 可以查看 Git 状态和逐文件 Diff，并按文件暂存、取消暂存和提交。
11. Host Operator 可以显式推送分支并创建或关联 PR。
12. Milestone View 可以展示范围、状态分布、Blockage 和 Release 事实。
13. GitHub、目录或 Agent 暂时不可用时，Saki 保留可恢复状态并说明失败位置。
14. Host Operator 可以登记多个 Provider Account Profile，查看其认证和 Usage Snapshot，并在不向 Project 数据暴露原始凭据的情况下选择默认账号。
15. Host Operator 可以使用 Codex 或 Kimi 启动 Work Session，Saki 在多次 Agent Run 中保持其已解析 Model Route 稳定且来源可追踪。
16. Host Operator 可以观察上下文用量与压缩事件，并在多次压缩后继续 Work Session，而不丢失已记录的 Project 决定。
17. Development Agent 可以从仓库发现并使用可版本化的 Saki Development Skill Pack。
18. Development Agent 可以生成或编辑图片，把结果持久化到 Project，并公开其 Generation Job 和来源。
19. Host Operator 可以打开统一 Attention Inbox，在重连或重启后回答 Intervention Request，并返回拥有该请求的 Work Item 或 Agent Run。

## Development Project 与并发

一个 Development Project 持久关联一个 DSH Workspace、一个指向已有 Git worktree 的稳定 Resource Binding 和一个可选 GitHub Repository。一个 Repository 的多个 worktree 可以登记为多个 Development Project，但同一个 worktree 同时只能有一个可写 Agent Run。已接受的普通同 Host 路径拼写会在重复检测前规范化；直接 symlink 或 junction locator 会被拒绝，而不会被视为别名；绑定位置可以在不改变其身份的情况下明确 rebind。参见 [ADR 0003](../../adr/0003-development-project-worktree-ownership.zh.md) 与 [ADR 0014](../../adr/0014-stable-resource-bindings-over-canonical-worktrees.zh.md)。

Resource Binding 保存稳定 id 以及带 revision、可重新验证的位置与 Git 观察，不复制 Git 或 GitHub 拥有的完整权威数据。0.1.0 登记已有目录，在执行完全停稳后 rebind，并在不删除文件或 Git 资源的情况下退役 Project；物理 worktree 创建、移动、repair 与移除使用 Git、Terminal、PowerShell 7 或 Agent。目录缺失或不匹配时保留 Project 身份并阻止可写执行。历史 Session 保留旧 cwd，并在 rebind 后通过后继 Session 继续。自动模式要求 clean tree；手动接管已有变更会把它们记录为继承 evidence。

## 信息架构

- **工作**：当前 Principal 的跨 Project My Work Projection，包括需求、推荐下一步操作、待回答事项、验收和最近结束的工作。
- **项目**：一个已选择 Development Project，内部包含看板、里程碑、变更、会话与运行、追溯和项目设置。

它们是唯一新增的 Saki 顶层页面。Conversation、New Session、Settings 和上下文化 Terminal 入口继续使用继承的 DSH 页面。切换 Development Project 会一起改变「项目」的所有内部目的地，但不会收窄「工作」的跨 Project scope；每个工作条目以及任何修改代码、GitHub 或 Work Item 的操作都要标明目标 Project。

## 前端设计边界

[前端约定](../architecture/0.1.0-frontend-contract.zh.md)确定客户端边界、address、Projection、状态语义、交互与验证，但不选择布局、视觉层级、响应式组合或 styling。前端工作可以预先拆成 K0 至 K7，以便明确所有权与依赖；K1 至 K7 必须保持非 Ready，并且只有 K0 的低保真 prototype 获得产品确认、该切片需要的后端 Projection 与 Intent fixture 可用后，才可以开始生产实现。K0 证明「工作」与「项目」流程可以在 desktop 和受限 viewport 上完成，且不需要打开 VS Code，也不假设多个 pane 始终同时可见；视觉方向与高保真设计继续作为独立决定。

## Board

Board 默认只显示当前 Development Project，并筛选所选 GitHub Project 中属于关联 Repository 的 Issue。其他仓库 Issue、PR 和 draft item 不进入 0.1.0 Board。

固定列为 Inbox、Backlog、Ready、In progress、In review 和 Done。Canceled 默认位于归档筛选器；Blockage 是标记和筛选条件，不增加 Blocked 列。

GitHub Projects v2 的 Status 和 item position 是 Work Item Status 与手动排序的远端权威来源，见 [ADR 0001](../../adr/0001-github-projects-v2-work-authority.zh.md)。Saki 把固定状态映射到所选 Project 的 Status 选项，不要求组织统一其他 Project 的命名。

关联 Repository 中尚未加入 Project 的开放 Issue 显示在 Inbox，并带有“未加入 Project”标记。把卡片移出 Inbox 时，Saki 先加入 Project，再写入目标 Status。「提交需求」发送 `CreateWorkItem`，其中包含 title、intended outcome、acceptance criteria、Project id 与 expected Project revision，以及 expected GitHub mapping revision；Saki 随后创建 Issue、把它加入 Project 并设置 Inbox，任何部分失败都会展示已完成事实和恢复操作。

每张卡片按信息存在情况显示标题、Issue 编号、Milestone、Blockage、Agent Run、分支或 PR、CI 和更新时间。详情面板显示正文、验收条件、状态、Milestone、Agent Run、Session、Git 变更、PR、CI、Outcome Evidence 和活动记录。

拖动卡片时，Saki 乐观更新本地显示，并且只有定向读取仍匹配卡片已确认远端指纹时才写入 GitHub。不匹配会恢复最新 GitHub 状态并显示可见 conflict；mutation 回复丢失时先检查再重试。完整分阶段扫描会原子发布，部分失败时保持旧的已确认 Board 不变。0.1.0 的单个 Board 最多交付 10,000 个 Work Item；更大的完整候选结果会报告容量失败并保留此前已确认 Board，而不会截断。活动 Board 默认每 30 秒轮询，后台 Project 默认每五分钟轮询；手动刷新或本地 mutation 会请求立即扫描。0.1.0 不要求 Webhook；界面显示已确认扫描时间、乐观状态、时效、mapping health、conflict 和当前失败。参见 [ADR 0013](../../adr/0013-polling-first-staged-github-synchronization.zh.md)。

Inbox 至 In review 对应开放 Issue，Done 和 Canceled 对应关闭 Issue。重新打开 Issue 时恢复最近的非终态；没有记录时进入 Backlog。外部关闭活动 Issue 时，Saki 要求归类为 Done 或 Canceled。

每列使用 GitHub Project item position。若某种 GitHub View 排序无法由 API 表达，Saki 必须说明该 View 只同步状态。

## Agent 与自动化

Ready 表示 Work Item 可以领取。手动模式只有在 Host Operator 点击“交给 Agent”后才创建 Work Assignment 与 Control Intent；自动模式无需点击，为 Project Automation Principal 领取符合条件的 Ready Work Item。已接受 Intent 会在唤醒 Host 前持久化 Execution Dispatch；只有 Host Operation success 持久确认目标 Agent Run、精确物理 DSH Session 与精确原始输入后，Work Item 才进入 In progress。

手动 dispatch 切片会在持久接受前要求当前 LLM adapter 解析 Agent Profile 的精确 provider/model route。解析失败会返回 `model-route-unavailable`，不会保留 Agent operation 记录或启动生成。已经解析 adapter 与精确 model metadata 并不建立生产 provider authorization、credential availability、quota 或 account health；下文发布要求仍然约束一条可用 route。

手动操作使用 Host Operator 的 Grant。启用自动模式的 Project 拥有独立 Project Automation Principal，并为其显式配置 Grant；Automation Policy 可以收窄何时使用这些 Grant，但不能扩大权限。每个已接受 Control Intent 都保存控制面根据已认证 Principal、委派链和 Grant revision 派生的 Actor。

每个自动 effect 前，Saki 都会持久预留所有适用有限本地预算，之后结算带归因用量。必需维度覆盖并发 Run、Run wall time、模型请求与 token、Generation Job 与 attempt、GitHub mutation、push 和由 Saki 引发的 CI trigger。提供方全局 quota、成本与观察到的 Actions 时长保持为独立类型化观察；当必需观察未知时，policy 要么暂停，要么明确允许在更严格的 local-only limit 下运行。耗尽会创建 Intervention Request，且绝不意味着 Done。参见 [ADR 0015](../../adr/0015-reserved-automation-budgets-and-usage-ledger.zh.md)。

手动模式中，Agent 完成一轮执行不会自动 Done。创建或关联 PR 后，Saki 可以进入 In review 并等待操作者验收。自动模式可以分别授权提交、推送、创建 PR、自动合并和 Done，但必须保存触发原因、权限、测试、Commit、PR、CI 或其他 Outcome Evidence，不能只根据 Agent 自报成功。

一个 Work Item 同时只能有一个活动 Agent Run。Agent Run 至少区分 Starting、Running、Waiting for user、Succeeded、Failed 和 Canceled；Agent Run Failed 不自动改变 Work Item Status，而是在卡片上增加需要处理的执行结果。

Waiting for user 关联开放 Intervention Request，其中标明所需输入或决定、具备权限的目标、阻塞范围，以及拥有它的 Work Session 或恢复 operation。该请求在 Web 重连或进程重启后仍可回答。针对 expected revision 的第一个有效回答是一条单独归因的 Control Intent；通知送达、关闭通知和超时都不会解决或批准请求。Attention Inbox 投影开放请求及其他失败或结果不明工作，不拥有另一套队列。

一个 Work Item 可以保留多个 Work Session，但最多把其中一个指定为主要会话。0.1.0 只需公开主要 Work Session，并且已经把每个 Work Item 限制为一个活动 Agent Run，但持久化不得强制 Work Item 与 DSH Session 在整个生命周期内一一对应。启动工作时创建或继续主要 Work Session，并把 Agent Run 与其关联；替换该 Session 时保留原有关联和 transcript。

0.1.0 没有持久 Project Coordinator，因此可以用顶层 DSH Session 承载 Work Session。后续协调可以改用 DSH 可继续 subagent，而不改变 Work Session 的身份或归属；DSH 父子谱系仍只记录执行来源。参见 [Agent Operations ADR 0002](../../adr/agent-operations/0002-work-sessions-and-subagent-lineage.zh.md)。

Agent 输入必须包含 Work Item 标识、标题、正文、验收条件、Blockage、Development Project 标识、Agent Profile 标识和工作目录。任何进入模型请求的附加上下文都必须标明来源，并能够从 Session 记录重建。

0.1.0 至少提供一条可实际使用的 Codex Agent 路径，并复用 DSH 的模型、per-session Agent Preset 和 Provider 扩展。每个 Development Project 在界面上只需选择一个默认 Development Agent Profile，但持久化关系使用稳定 Profile 标识，Agent Run 记录实际 Profile，使后续版本能够在同一 Project 中增加多个 Profile；Work Item 不直接绑定模型供应商。

Agent Profile 只定义这类开发工作如何执行，不是持久 Agent 主体。0.1.0 的一次性 Development Agent Run 可以不绑定 Agent Identity 或 Principal identity；它只获得发起 Principal 的 Grant 委派子集，并必须记录触发者、Actor 链、实际 Profile 版本和本次运行事实。相关决定见 [Agent Operations ADR 0001](../../adr/agent-operations/0001-agent-identity-profile-run.zh.md)、[ADR 0008](../../adr/0008-principals-grants-and-actor-attribution.zh.md)和 [ADR 0009](../../adr/0009-durable-dispatch-intervention-and-attention-projections.zh.md)。

## 模型供应、skill 与上下文

### 提供方账号与模型路由

0.1.0 支持由真实订阅提供的 Codex 和 Kimi Route。每次登录创建一个 Provider Account Profile，它引用 DSH 凭据服务保存的凭据，并公开认证、能力、健康和带提供方来源的 Usage Snapshot。操作者可以为同一提供方登记多个 Profile，并选择 Project 默认账号或在启动 Work Session 时选择账号。

Work Session 保持一条已解析 Model Route，除非操作者在安全的请求边界显式修改。Saki 不在活动请求期间换账号，也不静默改写既有来源；每个 Agent Run 都记录实际使用的提供方、模型、推理配置和账号 Profile。账号不可用或额度耗尽时阻止新工作并显示替代选择。0.1.0 不合并订阅额度，也不为绕过提供方限制而自动轮换账号。

Codex 和 Kimi 在提供方支持时必须支持设备码登录。提供方适配器保持为插件并共用 Provider Account Profile 模型；Work Item 和 Agent Profile 都不保存提供方 token。

受管理 refresh token 与 Saki Product GitHub App private key 使用通用 Windows DPAPI 凭据 Provider，并要求 Credential Protection Level 为 `local-user-trust`。有效值缺失、来自 ambient 或明文来源，或者缺少所需保护元数据时，授权与 dispatch 都会快速失败。账号界面显示保护等级，并说明它无法隔离有意以 Host Windows 用户身份运行的进程。

### 上下文生命周期

Saki 分别记录 Context Capacity、Runtime Context Limit 和 Context Policy。Context Capacity 来自模型元数据，Runtime Context Limit 反映账号与产品界面实际开放的上限，Context Policy 拥有压缩触发点和策略。因此，具备一百万 token 容量的模型可以在较低订阅或产品上限下运行，同时不误报其中任何一个事实。

实现前先对 DSH 基础压缩、包含可用远端压缩的 Codex-compatible 策略，以及模型主动上下文裁剪进行可复现比较。比较项包括指令与决定保留、工具调用配对、多次压缩漂移、恢复、延迟、token 余量和成本。0.1.0 根据结果选择默认策略，并可把其他策略作为实验性 Policy；它不把经过检索的逻辑历史宣称为物理模型窗口。

压缩和恢复属于模型可见行为，因此必须发出可重建的 Session 事件。仅追加 Session 记录保留原始输入或其持久引用，界面展示已解析上限、当前估算、Policy 版本、压缩事件和失败。

### Saki Development Skill Pack

仓库在 DSH 可发现的 Project skill 根目录中携带经过版本固定与兼容性审计的 Matt 工程 skills 子集。初始集合覆盖路由、需求与决定、领域建模、Issue 准备、实现、测试驱动开发、审阅和 handoff。它不挂载 Host 的整个 Codex skill 目录，也不依赖 Windows 符号链接。

发布验证通过 skill 发现运行一条 Project 工作流，并至少完成一次从规划到实现的 handoff。依赖不可用 Codex 专属工具的 skill 必须被适配、排除，或给出明确的兼容性说明后失败。

### 生成式媒体

生图使用提供方无关的 Generation Job，不假定复制 Codex 生图 skill 就能提供后端。Job 记录其 Work Session、已解析 Model Route、提示词、输入产物、生命周期、输出产物和来源。0.1.0 通过至少一个真实提供方验证生成和参考图编辑，并把选定输出持久化到 Project 内。

Generation Job 使用每账号可配置的并发上限。提供方允许时，独立 Job 可以并发；超出上限的工作进入队列，同时保留来源、取消和重试状态。主观图片质量不作为发布条件，产物有效性、持久化、来源、编辑行为和队列正确性必须通过验证。

## 核心流程

### 登记 Development Project

1. Host Operator 选择本地目录或 DSH Workspace。
2. Saki 检测 Git 工作树、分支、remote 和候选 GitHub Repository。
3. Host Operator 确认 Project Binding、GitHub Project 和默认 Development Agent Profile。
4. Saki 验证路径、Git 和 GitHub 权限并创建 Project。
5. Projects 显示该项目的工作、代码和交付摘要。

### 从 Work Item 启动 Agent

1. Work Item 位于 Ready，具有验收条件且没有 Blockage。
2. 手动模式由 Host Operator 建立 Work Assignment；自动模式由 Automation Policy 把责任分配给 Project Automation Principal。
3. Saki 检查活动可写 Run、未归属修改、受保护分支、凭据、预算和并发。
4. Saki 接受 Control Intent、创建或继续主要 Work Session、分配目标 Agent Run，并在唤醒 Host 前持久化 Execution Dispatch。
5. Host 领取 Dispatch，并在不启动 operation 的情况下准备一条持久 Host Operation；控制面使用当前 fencing token 接受该映射，然后 Host 以幂等方式创建或恢复同一个 DSH Session 与 Agent Run。获取 live Agent 后，Host 会在交付精确原始输入前立即重新验证新鲜的可写 Git world。
6. 只有 Host 持久确认目标 Agent Run、精确物理 Session 与精确原始输入后，Work Item 才进入 In progress；卡片显示启动来源、Dispatch 与 Run 状态以及 Work Session 入口。

### 审阅与交付

1. Changes 显示工作树、暂存区、逐文件 Diff 和来源 Agent Run。
2. 手动模式允许按文件暂存、取消暂存、运行命令、要求修正和提交已确认修改。
3. 推送后创建或关联 PR，Board 展示 PR 与 Actions，Work Item 进入 In review。
4. 手动模式由 Host Operator 验收；自动模式按 Automation Policy 检查 Outcome Evidence。
5. Done 关闭 Issue，并更新 Milestone 进度。

### 恢复中断工作

1. Saki 重启后重新验证 Project Binding。
2. 发布 readiness 前，控制面会把每个 running Agent Run 与其精确 succeeded `StartAgentRun` Host Operation 和 request 交叉校验，Host 则只根据匹配的物理 Session header 与原始输入恢复 live Agent handle。恢复会复用同一 Session id，不增加输入或 wake，也不发起模型请求。
3. Saki 在接收自动工作前对账非终态 Control Intent、Execution Dispatch、Host Operation 和 Execution Lease。
4. Attention Inbox 突出显示开放 Intervention Request、结果不明的 Dispatch、活动 Agent Run、未提交修改和待审 PR。
5. Host Operator 可以回答 Intervention Request 或继续持久化 Session；已终止终端明确显示不可恢复。

## Milestone View

GitHub Milestone 拥有交付 scope、title、due date 与 open 或 closed state；单一版本化 Saki Milestone Delivery record 则拥有 Planned、In Progress、Ready to Release 或 Canceled phase metadata。Phase 变更携带 expected metadata revision。Milestone View 展示 GitHub 事实、各状态 Work Item 数量、Blockage、Saki phase、repair state 与关联 Release。Released 从该 record 内嵌的不可变 evidence 派生，而不作为 phase metadata 写入，也不与 Work Item Status 共用列。

Release 使用 `refs/tags/saki-v*` reference，递归 peel annotated tag 得到准确 Release Commit，绝不使用 GitHub Release `target_commitish` 作为 identity。Release Intent 把准确官方 upstream Commit 记录为 Upstream Baseline。带 expected revision 的 finalization 会验证该 baseline 存在于配置的 upstream repository，且是 peeled Release Commit 的祖先，然后在 Milestone Delivery 中原子嵌入不可变 Release Evidence，其中包含 tag、GitHub Release、Commit、baseline、此前 metadata revision、PR、CI、Actor 与 Intent mapping。外部关闭的 Milestone 若既没有 Canceled metadata，也没有匹配 Release Evidence，就进入 repair 或 reconciliation。0.1.0 不实现甘特图、复杂路线图或跨仓库发布列车。

## Git 能力

Changes 提供一份完整且展示安全的 status observation，其中包含当前 branch、upstream、精确 HEAD 与 index evidence、worktree fingerprint、有界的 repository 相对 change path、opaque change id，以及 operation eligibility。逐文件 staged 与 unstaged Diff 都有界，并通过这些 id、patch fingerprint 与 cursor 绑定到精确 observation。Mutation Intent 不含路径，规范 Host 路径保持私有。已提交分支由 Host Operator 显式推送；push 不属于结构化 Git operation set，后续 PR 标题与正文由 Work Item 预填并可编辑。

Web UI 不解析 Git 命令输出、不提交规范路径，也不持有文件系统权限。`StageFiles`、`UnstageFiles` 与 `CreateCommit` 通过持久直接 Control Intent 进入系统。每项请求会固定精确 Project、Binding、status、HEAD、index、worktree 与 inherited-change evidence；已选 row 只携带 observation-scoped id 与 fingerprint。每个 Resource Binding 的一条 Binding Write Admission 只允许一项直接 Host operation 或一个可写 Agent Run。直接 Git 使用幂等 `{ kind: 'control-intent' }` Host Operation；手动 Agent 启动会竞争同一 row，并在确认后保留其 `agent-run` ownership。

Stage 与 unstage 会构建并验证 alternate index；Commit 从已观察 index tree 创建一条确定性、无 hook 且无签名的 object。每项 operation 都会在获取真实 `index.lock` 前持久记录一个随机同目录 pin：stage 与 unstage 固定 target index，Commit 固定其精确 lock marker。每份 plan 都会固定 index read limit，Commit plan 还会固定 reflog read limit；configuration change 后的 resume、inspection、cancellation、blocking-lock removal 与 cleanup 继续使用这些值。

在 POSIX 上，index pin 会保留现有 index 的 permission bit，或者记录缺失 index 的实际 Git 风格 mode。在 Windows 上，发布现有 index 会先把 index DACL 应用到仍为空的 pin，再写入 target 字节，并使用 `ReplaceFileW`。Scratch 创建会在 plan 持久化前，于 POSIX 上同步 `objects/info`、每个已有内容的 loose-object fanout 与自底向上的父目录链。Stage 会同步其已选 hash 返回的精确且当前为 loose 的 source object。Commit 会另行保留其精确 candidate commit 与 root tree、用一份有界 manifest 记录本次新生成的私有 object，并在它们当前为 source loose object 时同步其并集；packed object 不需要逐 object Git probe。取得自有 lock 后，Host 会重新检查完整 expected-index evidence，再通过同目录 POSIX rename、Windows `ReplaceFileW`，或用于缺失 index 的 create-only hard link 进行发布，并在记录成功前完成 index 目录 barrier。

Commit 会从禁用 include 的 worktree-local 或 repository-local configuration 获得 Git-canonical identity，并为结构化 mutation plumbing 固定 `core.fsyncMethod=fsync` 与 `core.fsync=loose-object,index,reference`。Attached-HEAD planning 会固定精确目标 branch、在副作用前立即重新验证 HEAD，并只对该 target 执行 compare-and-set；之后的并发 checkout 无法重定向 publication。`update-ref` 后，Host 会同步稳定的 target reflog 文件以及 target ref 与 reflog 的父目录链，recovery 会重复该 barrier。当前 target 无需解析超限 reflog 即可证明 success；发生后续外部 ref 推进时，精确 transition 只有在固定 `reflogReadLimit` 内才会证明 success，而该 limit 只限制解析、不限制文件同步。Detached HEAD 仍可检查，并支持 Diff、stage 与 unstage；但 CreateCommit 不可用，因为 Git 2.45 无法在 compare-and-set object id 的同时原子证明 `HEAD` 始终是 direct ref。Git 2.45 仍是最低版本。已经规划的 operation 会在持久化终态或 reconciliation result 前清除其 operation-owned blocking lock，终态 replay 会重试精确的非阻塞产物清理，而含糊的 attempted publication 会停止在 reconciliation required，不会重复 mutation。POSIX 会传播 scratch、source-object、index、ref 与 reflog 目录同步失败；Windows 会同步文件并使用原子发布，但不能声称目录项在崩溃后仍然持久。[结构化 Git 决策](../../../.agents/notes/implemented/architecture/2026-08-28-saki-recoverable-structured-git-operations.zh.md)拥有完整 failure ordering 与平台后果。

## 控制面与执行面

0.1.0 创建一个稳定 Saki Installation，其中只有一个活动控制面写入者和一个已登记 Local Host。即使两个面运行在同一进程与仓库，Installation 与 Host 仍具有独立稳定身份。控制面拥有 Principal、Grant、Actor 归因、Project、Work Item 投影、Work Assignment、Agent Profile、Automation Policy、Execution Dispatch、Intervention Request，以及历史与 Attention Inbox 投影；执行面通过 Host Provider 和 DSH 运行时解析 Workspace、操作 Git、创建 Session、运行工具与模型，并回报状态事件和 Outcome Evidence。

Web View 只向控制面提交请求操作，不直接访问文件系统、Git 进程、DSH Session 或凭据。已认证 Web session 解析为 Principal；client 不能提供可信 Actor 或 Grant 字段。直接 Git 与手动 Give-to-Agent 会寻址精确 Installation、Host、Project 与 Resource Binding，再使用同一 Host Execution 接口，而且不直接改写 Board 或其他控制面状态。Agent 工作通过一条 Execution Dispatch 与一个 `execution-dispatch` Host Operation source 交付。

除 bootstrap exchange 与 logout 外，每个已实现产品 mutation 都先进入持久、幂等的 Control Intent，随后 Saki 才调用外部能力。两个 access 例外只通过 `SakiAccess` 修改单一 Installation Access aggregate；每次受保护 query 与 submit 都重新验证 active session 与 generation、Principal lifecycle，以及当前 Grant revision 与 scope。Intent 保存不可变 Actor 和准入时使用的 Grant revision。直接 Git Intent 会预留 Binding Write Admission、在副作用前把不可变 source 绑定到一条持久 Host Operation、接受该精确 preparation，并通过 inspection 恢复。撤销 Grant 会阻止新 Intent 与尚未启动的副作用，但保留已有 operation 所需的 inspection、cancellation 与 reconciliation。其他记录通过 Intent 恢复逐步收敛，不声称具有跨记录原子性；产品 View 读取 Projection，post-commit notification 只使这些 Projection 失效。

手动 Give-to-Agent 会在唤醒 Host 前持久化独立 Execution Dispatch、使用带单调 fencing token 的 expected-revision Dispatch Claim，并在当前 claim 下接受一条已准备的 `StartAgentRun` Host Operation。现有 Binding Write Admission 中生命周期更长的 `agent-run` variant 拥有“一个工作树最多存在一个活动可写 Agent Run”这条规则；它命名来源 Intent 与 Agent Run，而非生命周期较短的 Dispatch。Intervention Request、Attention Inbox 与自动领取仍属于更广泛的 execution 闭环。精确输入交付与恢复语义由[手动 dispatch 决策](../../../.agents/notes/implemented/feature/2026-08-18-saki-manual-give-to-agent-dispatch.zh.md)说明。

该分离不要求 0.1.0 实现 RPC、独立队列或数据库服务、微服务、完整事件溯源、密码系统或通用组织 IAM。接口不传递活进程句柄、凭据内容或仅本机可理解的隐式状态，以使后续远程 Host 能在不重写产品编排的情况下增加网络适配器。Web surface 默认绑定到 loopback；已安装 Host plugin 是有特权的可信代码，而模型动态生成的 plugin 在操作者审查前保持一次性。相关决定见 [ADR 0004](../../adr/0004-control-and-execution-planes.zh.md)、[ADR 0005](../../adr/0005-recoverable-control-intents.zh.md)、[ADR 0007](../../adr/0007-single-control-plane-and-enrolled-hosts.zh.md)、[ADR 0008](../../adr/0008-principals-grants-and-actor-attribution.zh.md)、[ADR 0009](../../adr/0009-durable-dispatch-intervention-and-attention-projections.zh.md)、[ADR 0010](../../adr/0010-fenced-idempotent-dispatch-admission.zh.md)、[ADR 0011](../../adr/0011-dpapi-local-user-trust-credentials.zh.md)和 [ADR 0012](../../adr/0012-forward-migrations-and-installation-maintenance.zh.md)。

## 数据演进与 Host 可迁移性

Saki 把权威控制面记录保存在通过 DSH `storageDomain` 路由的专用 SQLite 数据库中。状态格式 capability 而非 build identity 决定兼容性；generation 与 Recovery Backup 元数据中的 build id 只记录来源。保留的 v2 是精确 B03 `saki_control_plane@2`，不含 storage-generation seal；保留的 v3 与 v4 分别把各自控制面版本和 `saki_storage_generation@1` 与 `@2` 配对；保留的 v5 与 v6 把 `saki_host_execution@1` 和各自控制面版本及 `saki_storage_generation@3` 或 `@4` 配对；当前 v7 要求 `saki_control_plane@7`、`saki_host_execution@2` 与 `saki_storage_generation@5`。没有显式相邻 `N -> N+1` chain 的 domain 保留 DSH 版本不匹配拒绝行为；Saki 拒绝向下迁移与不受支持的较新状态版本。

B03 Host 早于 Installation lease，因此过渡时必须由操作者手工停止并保持离线。从 B18 开始，Host 与每条维护命令共用一把不等待 Installation lease。`installation.json` 发布后是唯一权威；没有该文件时，状态源选择只识别准确配置的 B03 数据库或全新状态。在产物副作用前，升级 journal 会固定源状态版本、storage-generation identity 与 build 来源，并固定 backup 和 candidate identity。升级会验证该精确 Recovery Backup、迁移独立 v7 candidate、校验全部当前 domain 与产品关系、证明源字节未改变，最后才原子发布 `ready` manifest。发布前崩溃时，选中的 v2 至 v6 保持权威；发布后崩溃时 v7 保持权威。Journal 校验并清理具名恢复产物，但绝不选择状态。

维护包通过 PowerShell 7 与 CLI 提供 `backup`、显式 `verify` 和精确 v2 至 v6 到 v7 的 `upgrade` operation。Recovery Backup 是精确本地回滚 evidence，验证 build 必须能读取其状态版本；记录的源 build 仍只表示来源，而且该包不暴露 restore 命令。

加密 Installation Export、替换 Host restore 与 retention 属于后续 0.1.0 工作，不在首个维护增量内。Installation Export 包含声明的 Saki 记录与关联 DSH Session export，但排除凭据与 DPAPI 密文、cache、活动 process、worktree 内容，以及作为可复用权限的绝对路径。替换 restore 保留 Installation id、分配新 Host id、把 Resource Binding 标为 `needs-rebind`、在重新授权前禁用 Host 绑定 Provider Account Profile、对账未解决 Dispatch 与 Host Operation，并在恢复完成前保持自动化禁用。旧 Host 必须保持退役或离线，因为 0.1.0 不在历史副本之间提供分布式 fencing。

## GitHub 身份与凭据

GitHub 集成涉及四种独立身份：选择操作的 Saki Actor、执行 API mutation 的 GitHub App 或用户凭据、执行 `git push` 的凭据和 Commit author。0.1.0 不能因为当前四者都与 Host Operator 相关就把它们持久化成同一个概念。

| 方式 | 能力与优点 | 代价与限制 | 适用位置 |
| --- | --- | --- | --- |
| 系统 Git Credential Manager 或现有 `gh` 登录 | 直接继承 Host Operator 已有访问，开发成本最低 | 属于个人且权限可能较宽，难以用于无人值守与多用户审计 | 0.1.0 的 `git push` 与开发期 bootstrap |
| GitHub App installation token | 代表 App，在指定账号和 Repository 范围内按最小权限运行；适合无人值守自动化，短期令牌可以自动轮换 | 操作归因于 App，不代表某个用户；需要保存 App 私钥和 installation ID | Board 同步、Issue、PR、CI 查询和后续自动化 |
| GitHub App user access token | 代表具体用户，权限是“用户权限与 App 权限”的交集，可使用 Web 或 Device Flow | 需要登录、刷新、撤销和每用户授权状态；App 还必须安装在目标组织 | 第三阶段用户登录、个人项目和以用户身份操作 |
| 用户令牌与 installation token 组合 | 人工操作归因于用户，后台自动化归因于 App，权限和审计最清楚 | 实现和测试复杂度最高 | 第三阶段目标架构 |

阶段性建议是：0.1.0 不实现 Saki 多用户登录，`git push` 继续使用系统 Git 凭据；新建独立的 Saki Product GitHub App，以 installation token 执行 GitHub Project、Issue、PR 和 Actions API。第三阶段再增加 GitHub App user authorization，并支持 Device Flow，使个人操作使用用户令牌、无人值守工作继续使用 installation token。现有 upstream automation App 保持独立，不扩大为产品身份。

0.1.0 的 Saki Product App 只申请组织 Projects 读写、Repository Issues 和 Pull requests 读写、用于 tag reference、peeled Commit、upstream baseline 存在性与祖先关系的 Repository Contents read，以及 Actions、Checks 和 Commit statuses 读取；Metadata 保留必需的只读权限。`git push` 使用系统 Git 凭据期间既不申请 Contents write，也不申请 Workflows write。只有产品明确改为使用 App 创建 Commit、推送分支或编辑 workflow 文件时才增加对应写权限。

GitHub 官方将 installation token 定位为无人输入的自动化身份，将 user access token 定位为代表具体用户的身份；installation token 一小时过期，GitHub App 的 user access token 默认八小时过期并可用 refresh token 更新。Device Flow 适用于无浏览器、CLI 和桌面应用。参考 [GitHub App 身份类型](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/about-authentication-with-a-github-app)、[installation token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)和 [user access token 与 Device Flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)。

Saki Product App 与 upstream automation App 保持分离，GitHub 用户授权不进入 0.1.0 发布条件。后续 GitHub 登录把外部 identity 关联到 human Principal；组织成员身份可以为 Grant 管理提供依据，但本身不授予 Host、Project、模型账号或文件系统权限。

| Git 状态、Diff、暂存和提交 | 实现最薄 Host Provider | 通用能力成熟后可替换或向上游贡献 |
| GitHub API | 实现独立、可替换 Provider | 平台 Adapter，不承载 Board 产品语义 |
| Development Project、Resource Binding、Board 映射、Work Assignment、Work Session 与 Agent Run 关联、Execution Dispatch、Intervention Request、Attention Inbox、Automation Policy、Outcome Evidence | 在 Saki 插件中实现 | Saki 必须拥有 |
| 前端代码编辑器 | 暂缓，Terminal、Agent 修改和 Diff 审阅兜底 | 不与成熟社区编辑器实现竞争 |

## 失败与恢复

- GitHub 不可达时，本地 Git、Session 和 Terminal 仍可使用；Board 显示缓存与离线状态，不伪造远端写入成功。
- 本地目录不存在或不再匹配 worktree 观察时，Project 保持只读并提示 operator rebind 或退役；Saki 不会根据路径、branch、remote 或 Commit 相似性猜测替代项。
- 切换 Project 不得丢弃或隐藏未提交修改。
- GitHub Project 字段缺失或映射无效时，Board 进入只读修复模式并指出缺失字段。
- 手动 dispatch 在 Host 确认精确 Agent Run、物理 Session 与原始输入前绝不会把 Work Item 移到 In progress。不可用的 preparation 保持可恢复；结果不明或冲突的 admission 或 Session evidence 保持可见并标记为需要对账。
- 重启恢复会按稳定 identity 对账非终态直接 Git 与手动 Agent Control Intent、Execution Dispatch、Host Operation、Agent Run 与共享 Binding Write Admission。running Run 只有在精确 succeeded operation 与匹配的物理 Session header 和输入均存在时才恢复 live Agent，并会复用同一 Session id，不增加输入或 wake，也不发起模型请求。恢复绝不会把无回复、claimed inbox entry 或 attempted effect 后的 expected value 当作副作用未发生的证明。自动工作还要求恢复未结算 Automation Budget Reservation 与 Intervention Request。
- Acceptance 前取消会记录 canceled Dispatch；acceptance 后取消会保留 accepted receipt 与终态 Host snapshot。Saki 会在持久化 child 与 Intent cancellation 和释放 write admission 前停止并排空 live Agent。Dispose 失败会使 operation 保持可重试并继续跟踪 handle；每个有效终态多记录前缀保持单调，启动时会幂等完成。
- 自动模式因预算、并发、凭据、工作树安全条件或完成证据需要人工处理时创建 Intervention Request 并停止，不放宽策略继续执行。
- 开放 Intervention Request 在 Web 重连或进程重启后仍可回答；通知送达、关闭通知或超时都不会批准请求。
- Session 可恢复但终端进程不可恢复时，界面分别展示两个事实。
- 登录、额度读取或提供方请求失败时保留所选 Provider Account Profile，并区分凭据不可用、用量数据不可用和执行被拒绝。
- Profile 恢复到另一台 Host 后，在重新授权或仅 Host 可用的私钥材料导入完成前保持不可用；Saki 绝不把复制的 DPAPI 密文当作可移植凭据。
- 升级中断后只会重新打开 manifest 选中的 Installation State Generation；无效 candidate 保持非活动，选中 generation 损坏时进入维护恢复，而不会猜测另一个数据库。
- 替换 Host restore 会保持自动化禁用，直到 Resource Binding、Host 绑定 Profile、未解决 operation 和 GitHub 观测完成重新绑定或对账，并警告源 Host 必须保持离线或退役。
- 上下文压缩失败时保留仅追加 Session 记录，并报告下一次模型请求能否安全继续。
- Generation Job 失败或取消时保留其输入和生命周期记录，不把不完整文件展示成已完成产物。

## 验证策略

主要自动化验收使用产品级 Web 流程：Playwright 驱动真实 Saki Web UI 和临时 Git 仓库，通过可控 GitHub、Agent、模型账号、上下文、skill 与生图 Provider 覆盖项目登记、Board 同步、手动和自动启动、账号路由、多次压缩、skill 发现、Generation Job、代码变化、提交、In review 与基于证据的自动 Done。

GitHub API 与外部 Provider 保留少量接口测试，但不以大量组件 Mock 测试替代产品流程。外部网络、真实组织权限和付费模型不进入必需 CI。操作者完成登录后，脚本化本地冒烟测试运行真实 Codex、Kimi 和生图 Route，并保存机器可读证据。

Windows 凭据 integration test 证明静态数据采用当前用户 DPAPI 密文、受管理 reference 会拒绝机器范围与明文回退、保护元数据明确，而且 Projection、event、log、diagnostic、Agent tool、crash artifact 和可移植 export 都不含原始值与密文。

Migration 与当前维护测试覆盖精确 B03 源 schema、保留 v3 至 v6 状态、通往当前 v7 的每项相邻步骤、Host v1 到 v2 保留、无效历史关系、缺失或无效步骤、不受支持的磁盘状态版本、candidate 校验、源不变、Recovery Backup 完整性、lease 排他、CLI 行为与 operation 恢复。v4 至 v6 source reader 被隔离在封闭且冻结的历史 leaf pack 后，drift test 会替换可变的当前 leaf，以证明保留 input 仍然可读。在每个 manifest 发布阶段前后执行 crash injection，证明恰好一个 generation 可以 reopen。后续 export 与替换 Host restore 工作还必须覆盖认证加密、排除数据、新 Host 对账和非空目标拒绝。

已实现的结构化 Git 验收覆盖从 Changes 到 Commit 的完整流程，包括有界且展示安全的 status 与 Diff、显式选择的 Stage 与 Unstage mutation、确定性的 attached 与 unborn Commit creation、重启恢复，以及对含糊 effect 的可见 reconciliation；[结构化 Git 决策](../../../.agents/notes/implemented/architecture/2026-08-28-saki-recoverable-structured-git-operations.zh.md)负责详细边界与 failure-injection evidence。

无密钥组合式手动 dispatch 测试会启动已交付的 Saki bundle、真实 Agent、物理 Session persistence、系统拥有的 `development` preset、checkpoint-policy stack 与可控制 fake LLM。测试会证明已配置 provider 与 model、persona、repository instructions，以及 `read`、`write`、`edit` 和 Windows `pwsh` 工具组成。

物理与重启 assertion 会固定精确原始输入与插入次数、replay 前的 live-Agent registry membership、恢复后的相同 Session id、恢复时不增加输入或 wake 且不发起模型请求，以及在原始输入插入或 pending-input wake 前立即执行的新鲜 writable-Git-world 重新验证。

手动 dispatch 协议与 crash test 会在每个持久边界后停止，并覆盖陈旧 claim、在等待 Host 工作期间过期且无法通过最终 acceptance compare-and-set 的 claim、改变 replay input、acceptance 前 start、acknowledgement 丢失后的 inspection、已取消或替换的输入、冲突 Session evidence，以及每个 Resource Binding 只有一个 writer。测试会证明 acceptance 前取消会阻止 start 并记录 canceled Dispatch、acceptance 后取消会保留 accepted receipt 与终态 Host snapshot、live-Agent dispose 会在持久化 child 与 Intent cancellation 和释放 admission 前完成、dispose 失败会保留 handle 跟踪并保持可重试，而且重启会幂等完成每个终态多记录写入前缀，不会产生另一份输入或 Agent Run。Intervention Request 交互测试仍属于更广泛的 execution 闭环。

发布前在真实 `BreakfastDaPaiDang/saki` Project 执行 dogfood：手动模式完整完成一次 Ready 到 Done；自动模式至少自动领取一个受控 Work Item，并在配置的 Outcome Evidence 满足后自动 Done；重启后 Project 和 Session 状态仍可恢复。一个 Host Operator 可以独立完成 dogfood；0.1.0 不要求第二名审阅者或独立人工 QA 角色，所有可重复检查由自动化证据承担。

## 发布条件

1. Saki 自身已登记为 Development Project，并通过日常启动入口稳定运行。
2. 核心用户流程的产品级自动化验收通过。
3. 真实 dogfood 至少成功一次。
4. Host Operator 可以在不打开 VS Code 的情况下完成 dogfood；允许使用 Saki Terminal 和外部浏览器完成登录。
5. GitHub、Host 或 Agent 暂时不可用时，Saki 说明失败、保留可恢复 Dispatch 与 Intervention 状态，并通过 Attention Inbox 展示所需操作。
6. 上游 DSH 同步不会覆盖 Saki 的 Project Binding、Board 或 Agent Run 数据。
7. 自动模式能够无人点击地完成 assignment 与 dispatch，并在预算、并发、权限或验证需要人工处理时创建可见 Intervention Request。
8. 关键前端流程已经过低保真验证；高保真视觉不阻塞发布。
9. 真实 Codex 与 Kimi 订阅冒烟测试通过设备码登录、可追踪账号选择，以及提供方支持时的可见用量状态。
10. 选定 Context Policy 通过多次压缩连续性测试，并保留可恢复 Session 记录。
11. Saki Development Skill Pack 可被 DSH 发现，并完成脚本化的规划到实现 handoff。
12. 一个真实提供方通过生成、参考图编辑、产物持久化和有界并发冒烟测试。
13. 受管理模型与 GitHub App 凭据通过 `local-user-trust` 安全测试；加密 Installation Export 替换 Host 恢复演练会保留 Installation identity，同时要求重新绑定、重新授权与未解决 operation 对账。
14. 至少一个真实 schema 升级与注入中断在不重置 Project 状态的情况下完成；Recovery Backup 可以由声明状态 capability 能读取其记录版本的 build 验证。

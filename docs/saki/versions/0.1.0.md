# Saki 0.1.0 Implementation Specification

English | [中文](0.1.0.zh.md)

Status: Draft for review of the first usable Stage 1 slice. This document derives from the [product requirements](../product-requirements.md) and does not replace the long-term product boundary.

## Version proposition

Version 0.1.0 introduces the first product role, Host Operator, and lets that operator complete the minimum development loop for a real Development Project from Work Item to merge in the Saki Web UI. The version does not attempt to complete the entire Agent-native development system stage. The detailed realization is divided between the [backend architecture](../architecture/0.1.0-backend.md) and [frontend contract](../architecture/0.1.0-frontend-contract.md).

## Goals

1. Register a local directory as a Development Project with stable associations to a DSH Workspace, Git worktree, and GitHub Repository.
2. Switch among multiple Development Projects in one Saki window and understand the work, code, and delivery state of each project.
3. Start or continue a Work Session manually or automatically from a Ready Work Item with the correct working directory and context supplied automatically.
4. Review file changes and Git Diffs produced by an Agent, stage and unstage by file, commit, and push explicitly.
5. View and update GitHub Issues, Project Status, Milestones, PRs, and Actions results.
6. Restore Project Binding, Work Item, Execution Dispatch, Intervention Request, Agent Run, and Session associations after restarting Saki.
7. Complete at least one real Issue-to-merge flow using the Saki repository.
8. Use real Codex and Kimi subscription routes through named Provider Account Profiles with visible authentication and usage state.
9. Continue long-running Work Sessions through observable, recoverable context management selected by evidence rather than a hard-coded model window.
10. Load a versioned Saki Development Skill Pack that supports the repository's planning, implementation, review, and handoff workflow.
11. Generate and edit project image artifacts through one verified provider path, with bounded concurrent jobs.
12. Upgrade persisted Saki state without resetting Projects and complete an encrypted Installation Export and replacement-Host restore drill.

## Non-goals

Version 0.1.0 does not provide Monaco or another complete manual code editor, a VS Code extension compatibility layer, SSH remote development, multi-Host execution, persistent Agent Identities, Agent-specific Attention Inboxes, a Project Coordinator, autonomous inter-session coordination, multi-user login, organization permissions, shared model quotas, automatic rotation intended to bypass provider limits, a general provider marketplace, general scheduled tasks, Feishu or QQ integration, browser control, computer control, or complete provider-account administration.

Complex Git history editing, hunk-level staging, interactive rebase, a conflict editor, stash management, complete branch management, and a complete backup-management Web UI are not release requirements. The operator may use the Saki Terminal, PowerShell 7, or an Agent for those operations.

## Product role

The Host Operator bootstraps one Saki Installation and its enrolled Local Host, owns local directories, Git repositories, GitHub resources, and model supply, and is responsible for Project configuration and high-risk authorization. First launch creates one local human Principal and provisions its Host Operator Grants through a short-lived, single-use local bootstrap flow. The data model must not assume that the system will always have one user, but the 0.1.0 interface and permission flow do not add complexity for later roles.

## User stories

1. The Host Operator can register a Development Project from an existing DSH Workspace or local directory.
2. Saki detects the Git repository and GitHub remote and asks the operator to confirm the association.
3. The Host Operator can switch Development Projects quickly and see Work Items requiring attention, uncommitted changes, PRs awaiting review, and failed CI.
4. The Host Operator can create a GitHub Issue and place it in the selected GitHub Project Inbox.
5. The Host Operator can drag a Work Item on the Board and synchronize its status and ordering to GitHub Projects v2.
6. Work Item details show acceptance criteria, Blockage, Milestone, Agent Run, PR, CI, and Outcome Evidence together.
7. Manual mode requires explicitly clicking "Give to Agent" on a Ready item; automatic mode claims it under Automation Policy without a click.
8. Automatic mode can commit, deliver, and mark Done automatically after completion evidence is satisfied.
9. The Host Operator can open and continue a Work Item's primary Work Session and distinguish waiting for input, success, failure, and cancellation for its current or most recent Agent Run.
10. The Host Operator can inspect Git status and per-file Diffs and stage, unstage, and commit by file.
11. The Host Operator can push a branch explicitly and create or associate a PR.
12. Milestone View can display scope, status distribution, Blockage, and Release facts.
13. When GitHub, a directory, or an Agent is temporarily unavailable, Saki preserves recoverable state and explains the failure location.
14. The Host Operator can register multiple Provider Account Profiles, inspect their authentication and Usage Snapshots, and select a default account without exposing raw credentials to Project data.
15. The Host Operator can start a Work Session with Codex or Kimi, and Saki keeps its resolved Model Route stable and attributable across Agent Runs.
16. The Host Operator can observe context use and compaction events and continue a Work Session after repeated compaction without losing recorded Project decisions.
17. A Development Agent can discover and use the versioned Saki Development Skill Pack from the repository.
18. A Development Agent can generate or edit an image, persist it in the Project, and expose its Generation Job and provenance.
19. The Host Operator can open one Attention Inbox, answer an Intervention Request after reconnect or restart, and return to the owning Work Item or Agent Run.

## Development Project and concurrency

A Development Project durably associates one DSH Workspace, one stable Resource Binding to an existing Git worktree, and an optional GitHub Repository. Multiple worktrees from one repository may be registered as separate Development Projects, but a worktree may have only one writable Agent Run at a time. Accepted ordinary Same-Host path spellings are canonicalized before duplicate detection, while direct symlink or junction locators are rejected rather than treated as aliases; a binding's location may be explicitly rebound without changing its identity. See [ADR 0003](../../adr/0003-development-project-worktree-ownership.md) and [ADR 0014](../../adr/0014-stable-resource-bindings-over-canonical-worktrees.md).

Resource Binding stores a stable id plus revisioned, revalidatable location and Git observations without copying the complete authoritative data owned by Git or GitHub. Version 0.1.0 registers existing directories, rebinds them after execution quiescence, and retires Projects without deleting files or Git resources; physical worktree creation, move, repair, and removal use Git, Terminal, PowerShell 7, or an Agent. A missing or mismatched directory retains the Project identity and blocks writable execution. Historical Sessions retain their old cwd and continue through a successor Session after rebind. Automatic mode requires a clean tree; manual takeover of existing changes records them as inherited evidence.

## Information architecture

- **Work**: The cross-Project My Work Projection for the current Principal, including requests, recommended next actions, required responses, reviews, and recently finished work.
- **Project**: One selected Development Project with internal Board, Milestones, Changes, Sessions & Runs, Trace, and Project Settings destinations.

These are the only added top-level Saki pages. Conversation, New Session, Settings, and contextual Terminal access remain inherited DSH surfaces. Switching Development Project changes every Project destination together but does not narrow Work's cross-Project scope; every Work item and every operation that changes code, GitHub, or a Work Item names its target Project.

## Frontend design boundary

The [frontend contract](../architecture/0.1.0-frontend-contract.md) fixes client boundaries, addresses, Projections, state semantics, interactions, and verification without selecting layout, visual hierarchy, responsive composition, or styling. Frontend work may be pre-split into K0 through K7 so ownership and dependencies are visible. K1 through K7 remain non-Ready and cannot begin production implementation until K0's low-fidelity prototypes receive product approval and the backend Projection and Intent fixtures required by that slice are available. K0 proves the Work and Project flows on desktop and a constrained viewport without VS Code or an assumption that several panes remain visible at once; visual direction and high-fidelity design remain separate decisions.

## Board

By default, the Board shows only the current Development Project and filters the selected GitHub Project to Issues from the associated Repository. Issues from other repositories, PRs, and draft items do not enter the 0.1.0 Board.

The fixed columns are Inbox, Backlog, Ready, In progress, In review, and Done. Canceled is in the archive filter by default; Blockage is a marker and filter condition and does not add a Blocked column.

GitHub Projects v2 Status and item position are the remote authorities for Work Item Status and manual ordering; see [ADR 0001](../../adr/0001-github-projects-v2-work-authority.md). Saki maps its fixed statuses to Status options in the selected Project and does not require an organization to standardize naming in other Projects.

Open Issues in the associated Repository that are not yet in the Project appear in Inbox with a "not in Project" marker. When a card moves out of Inbox, Saki first adds it to the Project and then writes the target Status. Submit request sends `CreateWorkItem` with title, intended outcome, acceptance criteria, Project id and expected Project revision, and expected GitHub mapping revision; Saki creates the Issue, adds it to the Project, and sets Inbox, while any partial failure shows completed facts and a recovery action.

When information exists, each card shows its title, Issue number, Milestone, Blockage, Agent Run, branch or PR, CI, and update time. The details panel shows the body, acceptance criteria, status, Milestone, Agent Run, Session, Git changes, PR, CI, Outcome Evidence, and activity record.

When a card moves, Saki updates the local display optimistically and writes to GitHub only after a targeted read still matches the card's confirmed remote fingerprint. A mismatch restores the latest GitHub state as a visible conflict; a missing mutation reply is inspected before retry. Complete staged scans publish atomically and leave the prior confirmed Board unchanged on partial failure. Version 0.1.0 delivers at most 10,000 Work Items in one Board; a larger complete candidate reports a capacity failure and retains the prior confirmed Board instead of truncating it. The active Board defaults to 30-second polling, background Projects to five minutes, and manual refresh or local mutation requests an immediate scan. Version 0.1.0 does not require Webhooks; the interface shows confirmed scan time, optimistic state, age, mapping health, conflict, and current failure. See [ADR 0013](../../adr/0013-polling-first-staged-github-synchronization.md).

Inbox through In review correspond to open Issues, while Done and Canceled correspond to closed Issues. Reopening an Issue restores its most recent nonterminal status, or Backlog when none was recorded. When an external action closes an active Issue, Saki requires classification as Done or Canceled.

Each column uses GitHub Project item position. If a GitHub View ordering cannot be expressed through the API, Saki must explain that only status is synchronized for that View.

## Agent and automation

Ready means a Work Item can be claimed. Manual mode creates the Work Assignment and Control Intent only after the Host Operator clicks "Give to Agent"; automatic mode claims eligible Ready Work Items for the Project Automation Principal without a click. The accepted Intent persists an Execution Dispatch before Host wake-up, and the Work Item enters In progress only after Host Operation success durably confirms the intended Agent Run, exact physical DSH Session, and exact original input.

Before durable acceptance, the manual dispatch slice requires the current LLM adapter to resolve the Agent Profile's exact provider/model route. Resolution failure returns `model-route-unavailable` without retaining Agent operation records or starting generation. A resolved adapter and exact model metadata do not establish production provider authorization, credential availability, quota, or account health; the release requirements below still govern a usable route.

Manual actions use the Host Operator's Grants. A Project using automatic mode has a separate Project Automation Principal with explicitly provisioned Grants; Automation Policy may narrow when those Grants are used but cannot expand them. Each accepted Control Intent stores an Actor derived by the control plane from the authenticated Principal, delegation chain, and Grant revisions.

Before each automatic effect, Saki durably reserves every applicable finite local budget and later settles attributed usage. Required dimensions cover concurrent Runs, Run wall time, model requests and tokens, Generation Jobs and attempts, GitHub mutations, pushes, and Saki-caused CI triggers. Provider-wide quota, cost, and observed Actions duration remain separately typed observations; policy either pauses when required observations are unknown or explicitly permits operation under stricter local-only limits. Exhaustion creates an Intervention Request and never implies Done. See [ADR 0015](../../adr/0015-reserved-automation-budgets-and-usage-ledger.md).

In manual mode, an Agent completing one execution does not automatically mark Done. After a PR is created or associated, Saki may enter In review and wait for operator acceptance. Automatic mode can authorize commit, push, PR creation, automatic merge, and Done separately, but must preserve the trigger reason, permissions, tests, Commit, PR, CI, or other Outcome Evidence and cannot rely only on an Agent's self-reported success.

A Work Item may have only one active Agent Run at a time. Agent Run distinguishes at least Starting, Running, Waiting for user, Succeeded, Failed, and Canceled; Agent Run Failed does not change Work Item Status automatically and instead adds an execution result requiring attention to the card.

Waiting for user links an open Intervention Request that identifies the required input or decision, authorized target, blocking scope, and owning Work Session or recovery operation. The request remains answerable after Web reconnect or process restart. Its first valid expected-revision response is a separately attributed Control Intent; notification delivery, dismissal, and timeout do not resolve or approve it. Attention Inbox projects the open request and other failed or ambiguous work without owning another queue.

A Work Item may retain multiple Work Sessions but designates at most one as primary. Version 0.1.0 needs to expose only the primary Work Session and already limits each Work Item to one active Agent Run, but persistence must not enforce a lifetime one-to-one relationship between a Work Item and a DSH Session. Starting work creates or continues the primary Work Session and associates the Agent Run with it; replacing that Session preserves the previous association and transcript.

Version 0.1.0 may back a Work Session with a top-level DSH Session because it has no persistent Project Coordinator. Later coordination may use a DSH continuable subagent without changing Work Session identity or ownership; DSH parent-child lineage remains execution provenance. See [Agent Operations ADR 0002](../../adr/agent-operations/0002-work-sessions-and-subagent-lineage.md).

Agent input must include the Work Item identifier, title, body, acceptance criteria, Blockage, Development Project identifier, Agent Profile identifier, and working directory. Any additional context entering a model request must identify its source and be reconstructable from the Session record.

Version 0.1.0 provides at least one usable Codex Agent path and reuses DSH models, per-session Agent Presets, and Provider extensions. The interface only needs to select one default Development Agent Profile for each Development Project, but persistence uses a stable Profile identifier and Agent Run records the actual Profile so later versions can add multiple Profiles to one Project; a Work Item does not bind directly to a model provider.

Agent Profile defines only how this class of development work executes and is not a persistent Agent actor. A one-off Development Agent Run in 0.1.0 may omit Agent Identity and Principal identity; it receives only a delegated subset of the initiating Principal's Grants and must record its initiator, Actor chain, actual Profile version, and run facts. See [Agent Operations ADR 0001](../../adr/agent-operations/0001-agent-identity-profile-run.md), [ADR 0008](../../adr/0008-principals-grants-and-actor-attribution.md), and [ADR 0009](../../adr/0009-durable-dispatch-intervention-and-attention-projections.md).

## Model supply, skills, and context

### Provider accounts and model routing

Version 0.1.0 supports real subscription-backed Codex and Kimi routes. Each login creates a Provider Account Profile that refers to credentials held by the DSH credential service and exposes authentication, capability, health, and provider-attributed Usage Snapshots. The operator may register multiple profiles for one provider and choose a Project default or select one when starting a Work Session.

A Work Session keeps one resolved Model Route unless the operator explicitly changes it at a safe request boundary. Saki never switches accounts during an active request or silently rewrites prior attribution; every Agent Run records the provider, model, reasoning configuration, and account profile actually used. An unavailable or exhausted account blocks new work and displays alternatives. Version 0.1.0 does not combine subscription allowances or automatically rotate accounts to bypass provider limits.

Codex and Kimi authentication must support device-code login where the provider offers it. Provider adapters remain plugins and share the Provider Account Profile model; neither Work Items nor Agent Profiles store provider tokens.

Managed refresh tokens and the Saki Product GitHub App private key use the generic Windows DPAPI credential Provider and require Credential Protection Level `local-user-trust`. Authorization and dispatch fail closed when the effective value is missing, comes from an ambient or plaintext source, or lacks the required protection metadata. The account interface shows the protection level and states that it does not isolate a deliberate process running as the Host Windows user.

### Context lifecycle

Saki records Context Capacity, Runtime Context Limit, and Context Policy separately. Context Capacity comes from model metadata, Runtime Context Limit reflects the account and product surface actually available, and Context Policy owns the compaction trigger and strategy. This allows a one-million-token-capable model to run under a lower subscription or product limit without misreporting either fact.

Implementation begins with a reproducible comparison of DSH basic compaction, a Codex-compatible strategy including remote compaction where available, and model-directed active context pruning. The comparison measures instruction and decision retention, tool-call pairing, repeated-compaction drift, restoration, latency, token headroom, and cost. Version 0.1.0 selects a default from those results and may expose other strategies as experimental policies; it does not claim that retrieved logical history is a physical model window.

Compaction and restoration are model-visible behavior and therefore emit reconstructable Session events. The append-only Session record preserves original inputs or durable references to them, while the UI exposes the resolved limits, current estimate, policy version, compaction events, and failures.

### Saki Development Skill Pack

The repository carries a pinned, compatibility-audited subset of the Matt engineering skills under a DSH-discoverable project skill root. The initial pack covers routing, requirements and decision work, domain modeling, issue preparation, implementation, test-driven development, review, and handoff. It does not mount the host's entire Codex skill directory or rely on Windows symbolic links.

Release verification runs a Project workflow through skill discovery and at least one planning-to-implementation handoff. A skill that depends on unavailable Codex-only tools must be adapted, excluded, or fail with an explicit compatibility explanation.

### Generated media

Image generation uses a provider-neutral Generation Job instead of assuming that copying the Codex image-generation skill supplies a backend. A job records its Work Session, resolved Model Route, prompt, input artifacts, lifecycle, output artifacts, and provenance. Version 0.1.0 verifies generation and reference-image editing through at least one real provider and persists selected outputs inside the Project.

Generation jobs use a configurable per-account concurrency limit. Independent jobs may run concurrently when the provider allows it; excess work queues without losing attribution, cancellation, or retry state. Subjective image quality is not a release condition, but artifact validity, persistence, provenance, editing behavior, and queue correctness are.

## Core flows

### Register a Development Project

1. The Host Operator selects a local directory or DSH Workspace.
2. Saki detects the Git worktree, branch, remote, and candidate GitHub Repository.
3. The Host Operator confirms Project Binding, GitHub Project, and the default Development Agent Profile.
4. Saki validates path, Git, and GitHub permissions and creates the Project.
5. Projects displays the work, code, and delivery summary for the project.

### Start an Agent from a Work Item

1. The Work Item is Ready, has acceptance criteria, and has no Blockage.
2. The Host Operator establishes its Work Assignment in manual mode; Automation Policy assigns it to the Project Automation Principal in automatic mode.
3. Saki checks active writable Runs, unattributed modifications, protected branches, credentials, budget, and concurrency.
4. Saki accepts a Control Intent, creates or continues the primary Work Session, allocates the intended Agent Run, and persists an Execution Dispatch before waking the Host.
5. The Host claims the Dispatch and prepares one durable Host Operation without starting it; the control plane accepts that mapping under the current fencing token, then the Host idempotently creates or resumes the same DSH Session and Agent Run. After acquiring the live Agent, the Host freshly revalidates the writable Git world immediately before delivering the exact original input.
6. Only durable Host confirmation of the intended Agent Run, exact physical Session, and exact original input moves the Work Item to In progress; its card displays the launch source, Dispatch and Run status, and Work Session entry point.

### Review and deliver

1. Changes displays the worktree, staging area, per-file Diffs, and source Agent Run.
2. Manual mode permits staging and unstaging by file, running commands, requesting corrections, and committing confirmed changes.
3. After push, Saki creates or associates a PR, the Board displays the PR and Actions, and the Work Item enters In review.
4. The Host Operator accepts in manual mode; automatic mode checks Outcome Evidence under Automation Policy.
5. Done closes the Issue and updates Milestone progress.

### Resume interrupted work

1. Saki revalidates Project Binding after restart.
2. Before publishing readiness, the control plane cross-validates each running Agent Run against its exact succeeded `StartAgentRun` Host Operation and request, and the Host restores the live Agent handle only from the matching physical Session header and original input. Recovery uses the same Session id and adds no input or wake and issues no model request.
3. Saki reconciles non-terminal Control Intents, Execution Dispatches, Host Operations, and Execution Leases before admitting automatic work.
4. Attention Inbox highlights open Intervention Requests, ambiguous Dispatches, active Agent Runs, uncommitted changes, and PRs awaiting review.
5. The Host Operator can answer an Intervention Request or continue a persistent Session; a terminated terminal process is explicitly shown as unrecoverable.

## Milestone View

A GitHub Milestone owns delivery scope, title, due date, and open or closed state, while one versioned Saki Milestone Delivery record owns Planned, In Progress, Ready to Release, or Canceled phase metadata. Phase changes carry the expected metadata revision. Milestone View displays the GitHub facts, Work Item counts by status, Blockage, Saki phase, repair state, and associated Release. Released is derived from immutable evidence embedded in that record rather than written as phase metadata and does not share columns with Work Item Status.

A Release uses the `refs/tags/saki-v*` reference, recursively peels annotated tags to an exact Release Commit, and never uses GitHub Release `target_commitish` as identity. A Release Intent records the exact official upstream Commit as Upstream Baseline. Expected-revision finalization verifies that baseline exists in the configured upstream repository and is an ancestor of the peeled Release Commit, then atomically embeds immutable Release Evidence with the tag, GitHub Release, Commit, baseline, prior metadata revision, PR, CI, Actor, and Intent mapping in Milestone Delivery. An externally closed Milestone without Canceled metadata or matching Release Evidence enters repair or reconciliation. Version 0.1.0 does not implement Gantt charts, complex roadmaps, or cross-repository release trains.

## Git capability

Changes provides a complete display-safe status observation with current branch, upstream, exact HEAD and index evidence, worktree fingerprint, bounded repository-relative change paths, opaque change ids, and operation eligibility. Per-file staged and unstaged Diffs are bounded and tied to the exact observation through those ids, patch fingerprints, and cursors. Mutation Intents contain no paths, and canonical Host paths remain private. The Host Operator explicitly pushes a committed branch; push is not part of the structured Git operation set, and the Work Item later pre-fills an editable PR title and body.

The Web UI does not parse Git command output, submit canonical paths, or hold filesystem permissions. `StageFiles`, `UnstageFiles`, and `CreateCommit` enter through durable direct Control Intents. Each request freezes exact Project, Binding, status, HEAD, index, worktree, and inherited-change evidence; selected rows carry only observation-scoped ids and fingerprints. One Binding Write Admission per Resource Binding permits either one direct Host operation or one writable Agent Run. Direct Git uses an idempotent `{ kind: 'control-intent' }` Host Operation; manual Agent start contends on the same row and retains its `agent-run` ownership after confirmation.

Stage and unstage build and verify an alternate index; Commit creates one deterministic hook-free unsigned object from the observed index tree. Before any operation acquires a real `index.lock`, it durably records a random same-directory pin: stage and unstage pin the target index, while Commit pins its exact lock marker. Every plan freezes the index read limit, and a Commit plan also freezes the reflog read limit; resume, inspection, cancellation, blocking-lock removal, and cleanup continue to use those values after configuration changes.

On POSIX, an index pin preserves the existing index permission bits or records the actual Git-style mode for a missing index. On Windows, existing-index publication applies the index DACL to the still-empty pin before target bytes and uses `ReplaceFileW`. Scratch creation synchronizes `objects/info`, every populated loose-object fanout, and its bottom-up parent-directory chain on POSIX before plan persistence. Stage synchronizes the exact currently loose source objects returned by its selected hashes. Commit separately retains its exact candidate commit and root tree, uses a bounded manifest for newly materialized private objects, and synchronizes their union when currently loose in the source; packed objects require no per-object Git probe. After acquiring the owned lock, the Host rechecks the complete expected-index evidence, then publishes through same-directory POSIX rename, Windows `ReplaceFileW`, or a create-only hard link for a missing index and completes the index-directory barrier before recording success.

Commit obtains a Git-canonical identity from worktree-local or repository-local configuration with includes disabled and fixes `core.fsyncMethod=fsync` plus `core.fsync=loose-object,index,reference` for structured-mutation plumbing. Attached-HEAD planning freezes the exact target branch, revalidates HEAD immediately before the effect, and compare-and-sets only that target; a concurrent later checkout cannot redirect publication. After `update-ref`, the Host synchronizes the stable target reflog file and the target ref and reflog parent-directory chains, and recovery repeats the barrier. The current target proves success without parsing an oversized reflog; after later external ref progress, an exact transition proves success only within the frozen `reflogReadLimit`, which limits parsing rather than file synchronization. Detached HEAD remains inspectable and supports Diff, stage, and unstage, but CreateCommit is unavailable because Git 2.45 cannot atomically prove that `HEAD` stayed direct while compare-and-setting its object id. Git 2.45 remains the minimum. A planned operation clears its operation-owned blocking lock before persisting a terminal or reconciliation result, terminal replay retries exact nonblocking artifact cleanup, and ambiguous attempted publication stops in reconciliation required instead of repeating the mutation. POSIX propagates scratch, source-object, index, ref, and reflog directory-sync failures; Windows synchronizes files and uses atomic publication but cannot claim directory-entry durability across a crash. The [structured-Git decision](../../../.agents/notes/implemented/architecture/2026-08-28-saki-recoverable-structured-git-operations.md) owns the complete failure ordering and platform consequences.

## Control plane and execution plane

Version 0.1.0 creates one stable Saki Installation with one active control-plane writer and one enrolled Local Host. The Installation and Host have separate stable identities even though both planes run in one process and repository. The control plane owns Principals, Grants, Actor attribution, Projects, Work Item projections, Work Assignments, Agent Profiles, Automation Policies, Execution Dispatches, Intervention Requests, and history and Attention Inbox projections; through Host Providers and the DSH runtime, the execution plane resolves Workspaces, operates Git, creates Sessions, runs tools and models, and reports state events and Outcome Evidence.

A Web View submits requested actions only to the control plane and does not access the filesystem, Git process, DSH Session, or credentials directly. The authenticated Web session resolves to a Principal; the client cannot supply trusted Actor or Grant fields. Direct Git and manual Give-to-Agent address the exact Installation, Host, Project, and Resource Binding, then use the same Host Execution interface without directly rewriting the Board or other control-plane state. Agent work is delivered through one Execution Dispatch and an `execution-dispatch` Host Operation source.

Every implemented product mutation except bootstrap exchange and logout enters through a durable, idempotent Control Intent before Saki invokes an external capability. The two access exceptions modify only the single Installation Access aggregate through `SakiAccess`; every protected query and submit revalidates the active session and generation, Principal lifecycle, and current Grant revision and scope. The Intent records an immutable Actor and the Grant revisions used at admission. Direct Git Intents reserve Binding Write Admission, bind their immutable source to one durable Host Operation before the effect, accept that exact preparation, and recover through inspection. Grant revocation blocks new Intents and not-yet-started effects while preserving inspection, cancellation, and reconciliation for existing operations. Other records converge through Intent recovery rather than claiming cross-record atomicity; product Views read projections and post-commit notifications only invalidate those projections.

Manual Give-to-Agent persists a separate Execution Dispatch before Host wake-up, uses an expected-revision Dispatch Claim with a monotonic fencing token, and accepts one prepared `StartAgentRun` Host Operation under the current claim. The existing Binding Write Admission's long-lived `agent-run` variant owns the rule that one worktree has at most one active writable Agent Run; it names the origin Intent and Agent Run rather than the shorter-lived Dispatch. Intervention Requests, Attention Inbox, and automatic claiming remain part of the wider execution closure. The [manual dispatch decision](../../../.agents/notes/implemented/feature/2026-08-18-saki-manual-give-to-agent-dispatch.md) owns exact input-delivery and recovery semantics.

This separation does not require version 0.1.0 to implement RPC, a separate queue or database service, microservices, full event sourcing, a password system, or general organization IAM. The interface does not pass live process handles, credential contents, or implicit state meaningful only on the local machine, allowing a later remote Host to add a network adapter without rewriting product orchestration. The Web surface binds to loopback by default; installed Host plugins are privileged trusted code, while dynamic model-generated plugins remain ephemeral until operator review. See [ADR 0004](../../adr/0004-control-and-execution-planes.md), [ADR 0005](../../adr/0005-recoverable-control-intents.md), [ADR 0007](../../adr/0007-single-control-plane-and-enrolled-hosts.md), [ADR 0008](../../adr/0008-principals-grants-and-actor-attribution.md), [ADR 0009](../../adr/0009-durable-dispatch-intervention-and-attention-projections.md), [ADR 0010](../../adr/0010-fenced-idempotent-dispatch-admission.md), [ADR 0011](../../adr/0011-dpapi-local-user-trust-credentials.md), and [ADR 0012](../../adr/0012-forward-migrations-and-installation-maintenance.md).

## Data ownership

| Data | Authoritative source | Saki responsibility |
| --- | --- | --- |
| Installation identity and state generation | Saki control plane | Persist one Installation identity, the manifest-selected Installation State Generation, state-format version, and creator-build provenance |
| Enrolled Host identities | Saki control plane | Persist Host enrollment and trust state and revalidated capability inventory independently from the Installation |
| Bootstrap Challenge and Browser Session entries | Saki Installation Access aggregate | Atomically consume one challenge and insert one session, enforce terminal lifecycle and cleanup, and retain only token digests plus non-secret request-token derivation version and domain metadata |
| Principal, Grant, and Actor attribution | Saki control plane | Persist security subjects, scoped authority, delegation, revocation, and immutable per-Intent attribution |
| Workspace identity and directory | DSH Workspace | Associate, validate, and recover |
| Worktree, branch, staging area, and Commit | Local Git | Read and perform explicit operations |
| Repository, Issue, PR, and Actions | GitHub | Display and submit authorized changes |
| Work Item Status and manual ordering | GitHub Project | Map fixed statuses and synchronize in both directions |
| Milestone scope, title, due date, and open or closed state | GitHub Milestone | Display confirmed delivery scope and expose external closure that needs classification |
| Milestone delivery phase and Release Evidence | Saki Milestone Delivery | Persist versioned Planned, In Progress, Ready to Release, or Canceled metadata and atomically embed immutable evidence from which Released derives |
| DSH Session transcript | DSH Session | Recover through the associated Work Session and Development Project |
| Agent Preset composition | DSH Agent Preset | Compose tools and prompt for each Session |
| Host Operation | Saki Host | Persist an immutable Control Intent or Execution Dispatch source-to-operation mapping before effects and provide stable preparation, start, inspection, cancellation, and effect evidence |
| Work Assignment, Work Session association, Agent Profile, Agent Run, Automation Policy, Execution Dispatch, Intervention Request, and Resource Binding metadata | Saki control plane | Persist responsibility, Project associations, configuration versions, execution delivery and relationships, required responses, and policies |
| Release tag, GitHub Release, peeled Commit, and official upstream Commit | GitHub | Read exact delivery facts and verify upstream-baseline existence and ancestry before Milestone Delivery finalization |

Every cache must include its source and last synchronization time and must not become a second authoritative source. Work Item context must be written to a recoverable Session event before entering a model.

Raw credential values belong to a capability Provider on the Local Host. The control plane stores only opaque references, Credential Protection Level and health observations, attributed usage, and routing decisions. Portable export excludes plaintext and DPAPI ciphertext; restoring on another Host preserves the Provider Account Profile relationship but requires device reauthorization or Host-only private-material import. Version 0.1.0 makes the accepted `local-user-trust` limitation visible and does not claim multi-user credential isolation.

## Data evolution and Host portability

Saki stores canonical control-plane records in a dedicated SQLite database routed through DSH `storageDomain`. State-format capability, not build identity, decides compatibility; build ids in generation and Recovery Backup metadata record provenance only. Retained v2 is exact B03 `saki_control_plane@2` without a storage-generation seal; retained v3 and v4 pair their control-plane versions with `saki_storage_generation@1` and `@2`; retained v5 and v6 pair `saki_host_execution@1` with their control-plane versions and `saki_storage_generation@3` or `@4`; current v7 requires `saki_control_plane@7`, `saki_host_execution@2`, and `saki_storage_generation@5`. Domains without an explicit adjacent `N -> N+1` chain keep DSH's version-mismatch rejection; Saki rejects downgrade migration and unsupported newer state versions.

The B03 Host predates the Installation lease and must be stopped and kept offline manually for the transition. Beginning with B18, the Host and every maintenance command share one no-wait Installation lease. `installation.json` is the sole authority after publication; without it, source selection recognizes only the exact configured B03 database or fresh state. Before artifact effects, an upgrade journal fixes the source state version, storage-generation identity, and build provenance together with the backup and candidate identities. Upgrade verifies that exact Recovery Backup, migrates a separate v7 candidate, validates all current domains and product relationships, proves the source bytes unchanged, and only then atomically publishes a `ready` manifest. A crash before publication retains the selected v2 through v6 authority; a crash after publication retains v7 authority. Journals validate and clean named recovery artifacts but never select state.

The maintenance package provides PowerShell 7 and CLI operations for `backup`, explicit `verify`, and exact v2-through-v6-to-v7 `upgrade`. A Recovery Backup is exact local rollback evidence whose state version must be readable by the verifying build; its recorded source build remains provenance and the package exposes no restore command.

Encrypted Installation Export, replacement-Host restore, and retention remain later 0.1.0 work rather than part of the first maintenance increment. Installation Export includes declared Saki records and linked DSH Session exports but excludes credentials and DPAPI ciphertext, caches, active processes, worktree contents, and absolute paths as reusable authority. Replacement restore keeps the Installation id, allocates a new Host id, marks Resource Bindings `needs-rebind`, disables Host-bound Provider Account Profiles pending reauthorization, reconciles unresolved Dispatches and Host Operations, and keeps automation disabled until recovery completes. The old Host must remain retired or offline because 0.1.0 provides no distributed fencing between historical copies.

## GitHub identities and credentials

GitHub integration involves four independent identities: the Saki Actor that chose an action, the GitHub App or user credential that performs an API mutation, the credential performing `git push`, and the Commit author. Version 0.1.0 cannot persist them as one concept merely because all four currently relate to the Host Operator.

| Method | Capability and advantage | Cost and limitation | Use |
| --- | --- | --- | --- |
| System Git Credential Manager or existing `gh` login | Directly inherits the Host Operator's existing access with the lowest development cost | Personal and potentially broad permissions; difficult for unattended execution and multi-user audit | Version 0.1.0 `git push` and development bootstrap |
| GitHub App installation token | Represents the App with least privilege over specified accounts and Repositories; suitable for unattended automation, with automatically renewable short-lived tokens | Actions are attributed to the App rather than a user; requires storing the App private key and installation ID | Board synchronization, Issue and PR operations, CI queries, and later automation |
| GitHub App user access token | Represents a specific user with the intersection of user and App permissions and supports Web or Device Flow | Requires login, refresh, revocation, and per-user authorization state; the App must also be installed in the target organization | Stage 3 user login, personal projects, and actions as a user |
| Combined user token and installation token | Attributes human operations to users and background automation to the App with the clearest permissions and audit | Highest implementation and testing complexity | Stage 3 target architecture |

The staged recommendation is that version 0.1.0 does not implement Saki multi-user login and continues to use system Git credentials for `git push`; a separate Saki Product GitHub App uses an installation token for GitHub Project, Issue, PR, and Actions APIs. Stage 3 adds GitHub App user authorization with Device Flow so personal operations use user tokens and unattended work continues to use installation tokens. The existing upstream automation App remains separate and does not expand into the product identity.

The 0.1.0 Saki Product App requests only organization Projects read/write; Repository Issues and Pull requests read/write; Repository Contents read for tag references, peeled Commits, upstream-baseline existence, and ancestry; Actions, Checks, and Commit statuses read; and the mandatory Metadata read permission. It requests neither Contents write nor Workflows write while `git push` uses system Git credentials. Write permissions are added only if the product explicitly begins using the App to create Commits, push branches, or edit workflow files.

GitHub describes installation tokens as identities for automation without user input and user access tokens as identities acting for particular users; installation tokens expire after one hour, while GitHub App user access tokens expire after eight hours by default and can be renewed with refresh tokens. Device Flow supports browserless, CLI, and desktop applications. See [GitHub App authentication types](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/about-authentication-with-a-github-app), [installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation), and [user access tokens and Device Flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app).

The Saki Product App remains separate from the upstream-automation App, and GitHub user authorization does not become a 0.1.0 release requirement. A later GitHub login links an external identity to a human Principal; organization membership may inform Grant administration but does not itself confer Host, Project, model-account, or filesystem authority.

## Failure and recovery

- When GitHub is unreachable, local Git, Sessions, and Terminal remain available; the Board displays cached and offline state without pretending that a remote write succeeded.
- When a local directory is missing or no longer matches its worktree observation, the Project remains read-only and prompts the operator to rebind or retire it; Saki does not guess a replacement from path, branch, remote, or Commit similarity.
- Switching Projects must not discard or hide uncommitted changes.
- When a GitHub Project field is missing or its mapping is invalid, the Board enters read-only repair mode and identifies the missing field.
- Manual dispatch never moves a Work Item to In progress until the Host confirms the exact Agent Run, physical Session, and original input. Unavailable preparation remains recoverable; unknown or conflicting admission or Session evidence remains visible and reconciliation required.
- Restart recovery reconciles non-terminal direct Git and manual Agent Control Intents, Execution Dispatches, Host Operations, Agent Runs, and shared Binding Write Admissions by stable identity. A running Run regains its live Agent only from the exact succeeded operation and matching physical Session header and input, reuses the same Session id, and adds no input or wake and issues no model request. Recovery never treats silence, a claimed inbox entry, or an expected value after an attempted effect as proof that no effect occurred. Automatic work additionally requires unsettled Automation Budget Reservation and Intervention Request recovery.
- Cancellation before acceptance records a canceled Dispatch; cancellation after acceptance preserves the accepted receipt and terminal Host snapshot. Saki stops and drains the live Agent before persisting child and Intent cancellation and releasing write admission. Disposal failure leaves the operation retryable and the handle tracked, while each valid terminal multi-record prefix remains monotonic and startup completes it idempotently.
- Automatic mode creates an Intervention Request and stops when budget, concurrency, credentials, worktree safety conditions, or completion evidence require human action; it does not loosen policy and continue.
- Open Intervention Requests remain answerable after Web reconnect and process restart; notification delivery, dismissal, or timeout never approves them.
- When a Session is recoverable but its terminal process is not, the interface displays both facts separately.
- A failed login, quota lookup, or provider request preserves the selected Provider Account Profile and distinguishes unavailable credentials, unavailable usage data, and denied execution.
- A profile restored onto another Host remains unavailable until reauthorization or Host-only private-material import; Saki never treats copied DPAPI ciphertext as a portable credential.
- An interrupted upgrade reopens only the manifest-selected Installation State Generation; an invalid candidate remains inactive, and a corrupt selected generation enters maintenance recovery instead of guessing another database.
- A replacement-Host restore keeps automation disabled until Resource Bindings, Host-bound profiles, unresolved operations, and GitHub observations have been rebound or reconciled, and it warns that the source Host must remain offline or retired.
- Context compaction failure preserves the append-only Session record and reports whether the next model request can safely continue.
- A failed or canceled Generation Job preserves its inputs and lifecycle record without presenting a partial file as a completed artifact.

## Verification strategy

Primary automated acceptance uses product-level Web flows: Playwright drives the real Saki Web UI and temporary Git repositories, with controllable GitHub, Agent, model-account, context, skill, and generation Providers covering project registration, Board synchronization, manual and automatic launch, account routing, repeated compaction, skill discovery, image jobs, code changes, commit, In review, and evidence-based automatic Done.

The GitHub API and external Providers retain a small number of interface tests, but large numbers of component mock tests do not replace product flows. External networks, real organization permissions, and paid models are not required in CI. Scripted local smokes exercise real Codex, Kimi, and image-generation routes after the operator completes login and preserve machine-readable evidence.

Windows credential integration tests prove current-user DPAPI ciphertext-at-rest, rejection of machine scope and plaintext fallback for managed references, explicit protection metadata, and absence of raw values and ciphertext from Projections, events, logs, diagnostics, Agent tools, crash artifacts, and portable export.

Migration and current maintenance tests exercise the exact B03 source schema, retained v3 through v6 state, every adjacent step through current v7, Host v1-to-v2 preservation, invalid historical relationships, missing or invalid steps, unsupported stored versions, candidate validation, source immutability, Recovery Backup integrity, lease exclusion, CLI behavior, and operation recovery. The v4 through v6 source readers are isolated behind closed frozen historical leaf packs, and drift tests replace mutable current leaves to prove that retained inputs remain readable. Crash injection before and after each manifest publication phase proves that exactly one generation reopens. The later export and replacement-Host restore work must additionally cover authenticated encryption, excluded data, new-Host reconciliation, and nonempty-target rejection.

Implemented structured-Git acceptance covers the complete Changes-to-Commit flow, including bounded display-safe status and Diff, explicitly selected Stage and Unstage mutations, deterministic attached and unborn Commit creation, restart recovery, and visible reconciliation for ambiguous effects; the [structured-Git decision](../../../.agents/notes/implemented/architecture/2026-08-28-saki-recoverable-structured-git-operations.md) owns the detailed boundary and failure-injection evidence.

Keyless assembled manual-dispatch tests boot the shipped Saki bundle, real Agent, physical Session persistence, system-owned `development` preset, checkpoint-policy stack, and a controllable fake LLM. They prove the configured provider and model, persona, repository instructions, and `read`, `write`, `edit`, and Windows `pwsh` tool composition.

Physical and restart assertions pin exact original-input and insertion counts, live-Agent registry membership before replay, restoration of the same Session id, no recovery input, wake, or model request, and fresh writable-Git-world revalidation immediately before original insertion or a pending-input wake.

Manual dispatch protocol and crash tests stop after each durable boundary and cover stale claims, claim expiry during awaited Host work at the final acceptance compare-and-set, changed replay input, start-before-acceptance, lost acknowledgement inspection, canceled or replaced input, conflicting Session evidence, and one writer per Resource Binding. They prove pre-acceptance cancellation prevents start and records a canceled Dispatch, post-acceptance cancellation preserves the accepted receipt and terminal Host snapshot, live-Agent disposal completes before durable child and Intent cancellation and admission release, disposal failure remains retryable with the handle tracked, and restart idempotently completes every terminal multi-record write prefix without another input or Agent Run. Interaction tests for Intervention Request remain part of the wider execution closure.

Before release, dogfood runs in the real `BreakfastDaPaiDang/saki` Project: manual mode completes one full Ready-to-Done flow; automatic mode automatically claims at least one controlled Work Item and marks it Done after configured Outcome Evidence is satisfied; Project and Session state remain recoverable after restart. One Host Operator may perform this dogfood; version 0.1.0 requires no second reviewer or separate manual QA role, and automated evidence carries every repeatable check.

## Release criteria

1. Saki itself is registered as a Development Project and runs reliably through the daily launch entry point.
2. Product-level automated acceptance for core user flows passes.
3. At least one real dogfood flow succeeds.
4. The Host Operator can complete dogfood without opening VS Code; Saki Terminal and an external browser may be used for login.
5. When GitHub, a Host, or an Agent is temporarily unavailable, Saki explains the failure, preserves recoverable Dispatch and Intervention state, and exposes required action through Attention Inbox.
6. Upstream DSH synchronization does not overwrite Saki Project Binding, Board, or Agent Run data.
7. Automatic mode can assign and dispatch without clicks and creates a visible Intervention Request when budget, concurrency, permission, or verification requires a person.
8. Key frontend flows have passed low-fidelity validation; high-fidelity visuals do not block release.
9. Real Codex and Kimi subscription smokes pass with device-code login, attributable account selection, and visible usage state where the provider exposes it.
10. The selected Context Policy passes repeated-compaction continuity tests and preserves a recoverable Session record.
11. The Saki Development Skill Pack is discoverable in DSH and completes its scripted planning-to-implementation handoff.
12. One real provider passes generation, reference-image editing, artifact persistence, and bounded-concurrency smokes.
13. Managed model and GitHub App credentials pass the `local-user-trust` security tests, and an encrypted Installation Export replacement-Host recovery drill retains the Installation identity while requiring rebinding, reauthorization, and unresolved-operation reconciliation.
14. At least one real schema upgrade and injected interruption complete without resetting Project state; the Recovery Backup remains verifiable by a build whose declared state capability reads its recorded version.

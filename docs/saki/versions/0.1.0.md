# Saki 0.1.0 Implementation Specification

English | [中文](0.1.0.zh.md)

Status: Draft for review of the first usable Stage 1 slice. This document derives from the [product requirements](../product-requirements.md) and does not replace the long-term product boundary.

## Version proposition

Version 0.1.0 introduces the first product role, Host Operator, and lets that operator complete the minimum development loop for a real Development Project from Work Item to merge in the Saki Web UI. The version does not attempt to complete the entire Agent-native development system stage.

## Goals

1. Register a local directory as a Development Project with stable associations to a DSH Workspace, Git worktree, and GitHub Repository.
2. Switch among multiple Development Projects in one Saki window and understand the work, code, and delivery state of each project.
3. Start an Agent Session manually or automatically from a Ready Work Item with the correct working directory and context supplied automatically.
4. Review file changes and Git Diffs produced by an Agent, stage and unstage by file, commit, and push explicitly.
5. View and update GitHub Issues, Project Status, Milestones, PRs, and Actions results.
6. Restore Project Binding, Work Item, Agent Run, and Session associations after restarting Saki.
7. Complete at least one real Issue-to-merge flow using the Saki repository.

## Non-goals

Version 0.1.0 does not provide Monaco or another complete manual code editor, a VS Code extension compatibility layer, SSH remote development, multi-Host execution, persistent Agent Identities, multi-user login, organization permissions, shared model quotas, general scheduled tasks, Feishu or QQ integration, browser control, computer control, or complete provider-account management.

Complex Git history editing, hunk-level staging, interactive rebase, a conflict editor, stash management, and complete branch management are not release requirements. The operator may use the Saki Terminal or an Agent for those operations.

## Product role

The Host Operator owns local directories, Git repositories, GitHub resources, and model supply, and is responsible for Project configuration and high-risk authorization. The data model must not assume that the system will always have one user, but the 0.1.0 interface and permission flow do not add complexity for later roles.

## User stories

1. The Host Operator can register a Development Project from an existing DSH Workspace or local directory.
2. Saki detects the Git repository and GitHub remote and asks the operator to confirm the association.
3. The Host Operator can switch Development Projects quickly and see Work Items requiring attention, uncommitted changes, PRs awaiting review, and failed CI.
4. The Host Operator can create a GitHub Issue and place it in the selected GitHub Project Inbox.
5. The Host Operator can drag a Work Item on the Board and synchronize its status and ordering to GitHub Projects v2.
6. Work Item details show acceptance criteria, Blockage, Milestone, Agent Run, PR, CI, and Outcome Evidence together.
7. Manual mode requires explicitly clicking "Give to Agent" on a Ready item; automatic mode claims it under Automation Policy without a click.
8. Automatic mode can commit, deliver, and mark Done automatically after completion evidence is satisfied.
9. The Host Operator can continue the Session of an active Agent Run and distinguish waiting for input, success, failure, and cancellation.
10. The Host Operator can inspect Git status and per-file Diffs and stage, unstage, and commit by file.
11. The Host Operator can push a branch explicitly and create or associate a PR.
12. Milestone View can display scope, status distribution, Blockage, and Release facts.
13. When GitHub, a directory, or an Agent is temporarily unavailable, Saki preserves recoverable state and explains the failure location.

## Development Project and concurrency

A Development Project durably associates one DSH Workspace, one Git worktree, and an optional GitHub Repository. Multiple worktrees from one repository may be registered as separate Development Projects, but a worktree may have only one writable Agent Run at a time. See [ADR 0003](../../adr/0003-development-project-worktree-ownership.md).

Project Binding stores stable identifiers and revalidatable location information without copying the complete authoritative data owned by Git or GitHub. When a directory is missing, the remote changes, or permission is insufficient, the Project retains its identity and enters a state requiring repair.

## Information architecture

- **Projects**: Development Project list and attention summary.
- **Work**: Board, Milestone View, and Work Item details.
- **Changes**: Git state, Diffs, staging area, branch, and commit entry points.
- **Sessions**: Agent Session and Agent Run associations for the current Project.
- **Terminal**: DSH terminal pinned to the current Development Project.
- **Project Settings**: Project Binding, GitHub Project, default Agent Profile, Automation Policy, and synchronization state.

Switching Development Project must switch the context of Work, Changes, Sessions, and Terminal together. Every operation that changes code, GitHub, or a Work Item must display the target Project.

## Frontend design gap

This specification fixes information and behavior but not final layout, visual hierarchy, or responsive form. Before frontend implementation Issues are split, low-fidelity flows are still required for Projects overview, Board, Work Item details, Changes, Session association, Automation Policy, and failure recovery, and they must show that a user can complete dogfood without opening VS Code; the visual system and high-fidelity design may evolve later.

## Board

By default, the Board shows only the current Development Project and filters the selected GitHub Project to Issues from the associated Repository. Issues from other repositories, PRs, and draft items do not enter the 0.1.0 Board.

The fixed columns are Inbox, Backlog, Ready, In progress, In review, and Done. Canceled is in the archive filter by default; Blockage is a marker and filter condition and does not add a Blocked column.

GitHub Projects v2 Status and item position are the remote authorities for Work Item Status and manual ordering; see [ADR 0001](../../adr/0001-github-projects-v2-work-authority.md). Saki maps its fixed statuses to Status options in the selected Project and does not require an organization to standardize naming in other Projects.

Open Issues in the associated Repository that are not yet in the Project appear in Inbox with a "not in Project" marker. When a card moves out of Inbox, Saki first adds it to the Project and then writes the target Status; when Saki creates a Work Item, it creates the Issue, adds it to the Project, and sets Inbox together, and any partial failure must show completed facts and a recovery action.

When information exists, each card shows its title, Issue number, Milestone, Blockage, Agent Run, branch or PR, CI, and update time. The details panel shows the body, acceptance criteria, status, Milestone, Agent Run, Session, Git changes, PR, CI, Outcome Evidence, and activity record.

When a card moves, Saki updates the local display optimistically and writes to GitHub; on write failure it restores the confirmed remote state and shows a retryable error. Manual refresh and background polling synchronize external changes; version 0.1.0 does not require Webhooks but must show the last successful time and error.

Inbox through In review correspond to open Issues, while Done and Canceled correspond to closed Issues. Reopening an Issue restores its most recent nonterminal status, or Backlog when none was recorded. When an external action closes an active Issue, Saki requires classification as Done or Canceled.

Each column uses GitHub Project item position. If a GitHub View ordering cannot be expressed through the API, Saki must explain that only status is synchronized for that View.

## Agent and automation

Ready means a Work Item can be claimed. Manual mode creates an Agent Run only after the Host Operator clicks "Give to Agent"; automatic mode continuously claims Ready Work Items that satisfy Automation Policy. A Work Item enters In progress only after a successful claim.

In manual mode, an Agent completing one execution does not automatically mark Done. After a PR is created or associated, Saki may enter In review and wait for operator acceptance. Automatic mode can authorize commit, push, PR creation, automatic merge, and Done separately, but must preserve the trigger reason, permissions, tests, Commit, PR, CI, or other Outcome Evidence and cannot rely only on an Agent's self-reported success.

A Work Item may have only one active Agent Run at a time. Agent Run distinguishes at least Starting, Running, Waiting for user, Succeeded, Failed, and Canceled; Agent Run Failed does not change Work Item Status automatically and instead adds an execution result requiring attention to the card.

Agent input must include the Work Item identifier, title, body, acceptance criteria, Blockage, Development Project identifier, Agent Profile identifier, and working directory. Any additional context entering a model request must identify its source and be reconstructable from the Session record.

Version 0.1.0 provides at least one usable Codex Agent path and reuses DSH models, per-session Agent Presets, and Provider extensions. The interface only needs to select one default Development Agent Profile for each Development Project, but persistence uses a stable Profile identifier and Agent Run records the actual Profile so later versions can add multiple Profiles to one Project; a Work Item does not bind directly to a model provider.

Agent Profile defines only how this class of development work executes and is not a persistent Agent actor. A one-off Development Agent Run in 0.1.0 may omit Agent Identity, but must record its initiator, actual Profile version, and run facts; see [Agent Operations ADR 0001](../../adr/agent-operations/0001-agent-identity-profile-run.md).

## Core flows

### Register a Development Project

1. The Host Operator selects a local directory or DSH Workspace.
2. Saki detects the Git worktree, branch, remote, and candidate GitHub Repository.
3. The Host Operator confirms Project Binding, GitHub Project, and the default Development Agent Profile.
4. Saki validates path, Git, and GitHub permissions and creates the Project.
5. Projects displays the work, code, and delivery summary for the project.

### Start an Agent from a Work Item

1. The Work Item is Ready, has acceptance criteria, and has no Blockage.
2. The Host Operator claims it in manual mode; Automation Policy claims it in automatic mode.
3. Saki checks active writable Runs, unattributed modifications, protected branches, credentials, budget, and concurrency.
4. Saki creates an Agent Run and Session and writes the Work Item context.
5. The Work Item enters In progress, and its card displays the launch source, Run status, and Session entry point.

### Review and deliver

1. Changes displays the worktree, staging area, per-file Diffs, and source Agent Run.
2. Manual mode permits staging and unstaging by file, running commands, requesting corrections, and committing confirmed changes.
3. After push, Saki creates or associates a PR, the Board displays the PR and Actions, and the Work Item enters In review.
4. The Host Operator accepts in manual mode; automatic mode checks Outcome Evidence under Automation Policy.
5. Done closes the Issue and updates Milestone progress.

### Resume interrupted work

1. Saki revalidates Project Binding after restart.
2. Projects highlights active Agent Runs, uncommitted changes, and PRs awaiting review.
3. The Host Operator can continue a persistent Session; a terminated terminal process is explicitly shown as unrecoverable.

## Milestone View

A GitHub Milestone is delivery scope, and Milestone View displays target date, Work Item total, counts by status, Blockage, and associated Release. Milestone Phase is Planned, In Progress, Ready to Release, Released, or Canceled and does not share columns with Work Item Status.

A Release uses a `saki-v*` tag to bind an exact Release Commit and records the included Upstream Baseline. Version 0.1.0 does not implement Gantt charts, complex roadmaps, or cross-repository release trains.

## Git capability

Changes provides worktree status, per-file Diffs, staging-area Diffs, file-level stage and unstage, commit message, commit, current branch, and remote. The Host Operator explicitly pushes a committed branch; the Work Item pre-fills an editable PR title and body.

The Web UI does not parse Git command output or hold filesystem permissions. Git operations reside in a Host-side Provider that invokes system Git and returns structured results in the first version so the implementation can be replaced later.

## Control plane and execution plane

Version 0.1.0 logically separates the two planes within one process and repository. The control plane owns Projects, Work Item projections, Agent Profiles, Automation Policies, Agent Run requests, and history projections; through Host Providers and the DSH runtime, the execution plane resolves Workspaces, operates Git, creates Sessions, runs tools and models, and reports state events and Outcome Evidence.

A Web View submits user intent only to the control plane and does not access the filesystem, Git process, DSH Session, or credentials directly. The control plane sends requests through a structured Execution interface with stable identifiers, Project, working-directory reference, Profile version, trigger source, and limits; the execution plane returns structured events and results without directly rewriting the Board or other control-plane state.

This separation does not require version 0.1.0 to implement RPC, a separate queue, or microservices. The interface does not pass live process handles, credential contents, or implicit state meaningful only on the local machine, allowing a later remote Host to add a network adapter without rewriting product orchestration. See [ADR 0004](../../adr/0004-control-and-execution-planes.md).

## Data ownership

| Data | Authoritative source | Saki responsibility |
| --- | --- | --- |
| Workspace identity and directory | DSH Workspace | Associate, validate, and recover |
| Worktree, branch, staging area, and Commit | Local Git | Read and perform explicit operations |
| Repository, Issue, PR, and Actions | GitHub | Display and submit authorized changes |
| Work Item Status and manual ordering | GitHub Project | Map fixed statuses and synchronize in both directions |
| Milestone scope | GitHub Milestone | Display scope and progress |
| Agent Session | DSH Session | Recover by Development Project |
| Agent Preset composition | DSH Agent Preset | Compose tools and prompt for each Session |
| Agent Profile, Agent Run, Automation Policy, and Resource Binding metadata | Saki control plane | Persist Project associations, configuration versions, execution relationships, and policies |
| Release Tag and Commit | Git and GitHub Release | Display delivery facts |

Every cache must include its source and last synchronization time and must not become a second authoritative source. Work Item context must be written to a recoverable Session event before entering a model.

## GitHub identities and credentials

GitHub integration involves four independent identities: the person logged into Saki, the Actor calling the GitHub API, the credential performing `git push`, and the Commit author. Version 0.1.0 cannot persist them as one concept merely because all four currently belong to the Host Operator.

| Method | Capability and advantage | Cost and limitation | Use |
| --- | --- | --- | --- |
| System Git Credential Manager or existing `gh` login | Directly inherits the Host Operator's existing access with the lowest development cost | Personal and potentially broad permissions; difficult for unattended execution and multi-user audit | Version 0.1.0 `git push` and development bootstrap |
| GitHub App installation token | Represents the App with least privilege over specified accounts and Repositories; suitable for unattended automation, with automatically renewable short-lived tokens | Actions are attributed to the App rather than a user; requires storing the App private key and installation ID | Board synchronization, Issue and PR operations, CI queries, and later automation |
| GitHub App user access token | Represents a specific user with the intersection of user and App permissions and supports Web or Device Flow | Requires login, refresh, revocation, and per-user authorization state; the App must also be installed in the target organization | Stage 3 user login, personal projects, and actions as a user |
| Combined user token and installation token | Attributes human operations to users and background automation to the App with the clearest permissions and audit | Highest implementation and testing complexity | Stage 3 target architecture |

The staged recommendation is that version 0.1.0 does not implement Saki multi-user login and continues to use system Git credentials for `git push`; a separate Saki Product GitHub App uses an installation token for GitHub Project, Issue, PR, and Actions APIs. Stage 3 adds GitHub App user authorization with Device Flow so personal operations use user tokens and unattended work continues to use installation tokens. The existing upstream automation App remains separate and does not expand into the product identity.

If accepted, the 0.1.0 Saki Product App requests only organization Projects read/write; Repository Issues and Pull requests read/write; Actions, Checks, and Commit statuses read; and the mandatory Metadata read permission. It does not request Contents write while `git push` uses system Git credentials, and does not request Workflows write. Those permissions are added only if the product explicitly begins using the App to create Commits, push branches, or edit workflow files.

GitHub describes installation tokens as identities for automation without user input and user access tokens as identities acting for particular users; installation tokens expire after one hour, while GitHub App user access tokens expire after eight hours by default and can be renewed with refresh tokens. Device Flow supports browserless, CLI, and desktop applications. See [GitHub App authentication types](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/about-authentication-with-a-github-app), [installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation), and [user access tokens and Device Flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app).

This recommendation remains unconfirmed. Existing App permissions do not expand and GitHub user authorization does not become a 0.1.0 release requirement before confirmation.

## Capability sourcing

| Capability | 0.1.0 strategy | Long-term assessment |
| --- | --- | --- |
| Workspace, Session, Terminal, file tools, model Providers, and plugin runtime | Inherit directly from DSH | DSH-owned |
| Tool, prompt, persona, and context composition for each Session | Map Agent Profile to DSH Agent Preset | DSH owns runtime composition; Saki owns the Project-Profile relationship |
| Multiple model providers, plugin marketplace, browser, computer control, LSP, SSH, and complete editor | Exclude from 0.1.0; continue observing and prefer integration | DSH or the community is more likely to provide a general implementation |
| Git status, Diff, stage, and commit | Implement the thinnest Host Provider | Replace with a mature general capability or contribute upstream later |
| GitHub API | Implement an independent, replaceable Provider | Platform Adapter that does not carry Board product semantics |
| Development Project, Resource Binding, Board mapping, Agent Run association, Automation Policy, and Outcome Evidence | Implement in a Saki plugin | Saki-owned |
| Frontend code editor | Defer; Terminal, Agent changes, and Diff review provide a fallback | Do not compete with a mature community editor implementation |

## Failure and recovery

- When GitHub is unreachable, local Git, Sessions, and Terminal remain available; the Board displays cached and offline state without pretending that a remote write succeeded.
- When a local directory is missing, the Project remains and prompts the operator to relocate or remove the Resource Binding.
- Switching Projects must not discard or hide uncommitted changes.
- When a GitHub Project field is missing or its mapping is invalid, the Board enters read-only repair mode and identifies the missing field.
- When Agent launch fails, the Work Item must not remain in a false In progress state.
- Automatic mode stops and waits for human action when budget, concurrency, credentials, worktree safety conditions, or completion evidence are missing; it does not loosen policy and continue.
- When a Session is recoverable but its terminal process is not, the interface displays both facts separately.

## Verification strategy

Primary automated acceptance uses product-level Web flows: Playwright drives the real Saki Web UI and temporary Git repositories, with controllable GitHub and Agent Providers covering project registration, Board synchronization, manual and automatic launch, code changes, commit, In review, and evidence-based automatic Done.

The GitHub API and Agent Provider retain a small number of interface tests, but large numbers of component mock tests do not replace product flows. External networks, real organization permissions, and paid models are not required in CI.

Before release, dogfood runs in the real `BreakfastDaPaiDang/saki` Project: manual mode completes one full Ready-to-Done flow; automatic mode automatically claims at least one controlled Work Item and marks it Done after configured Outcome Evidence is satisfied; Project and Session state remain recoverable after restart.

## Release criteria

1. Saki itself is registered as a Development Project and runs reliably through the daily launch entry point.
2. Product-level automated acceptance for core user flows passes.
3. At least one real dogfood flow succeeds.
4. The Host Operator can complete dogfood without opening VS Code; Saki Terminal and an external browser may be used for login.
5. When GitHub or an Agent is temporarily unavailable, Saki explains the failure and preserves recoverable state.
6. Upstream DSH synchronization does not overwrite Saki Project Binding, Board, or Agent Run data.
7. Automatic mode can claim and deliver without clicks and stops safely when budget, concurrency, permission, or verification fails.
8. Key frontend flows have passed low-fidelity validation; high-fidelity visuals do not block release.

# Agent Note: Saki local bootstrap access over Connection

Status: implemented

English | [中文](2026-08-19-saki-local-bootstrap-access.zh.md)

## Problem

Saki needs a first authenticated Host Operator before Development Projects or GitHub identity exist. That access must survive a normal process restart, enforce current Principal and Grant authority, and leave no raw reusable authenticator in durable records. The browser also needs strict typed operations without turning Typert Remote into an authentication framework or placing a second HTTP carrier beside Connection.

## Decision

**Keep local access inside one deep control-plane module with independently owned entities.** `@breakfastdapaidang/saki-control-plane` uses a versioned `control_state` provisioning owner that records stable child references before any child write. Branded Saki Installation, Saki Host, Principal, and Grant records occupy keyed tables with independent revisions and lifecycle; each id has a kind-specific prefix followed by canonical UUID text. The maintenance-selected physical Installation State Generation uses `storage-generation-*`; exact B03 migration input alone retains historical `installation-generation-*` fields. Principal has a closed `human | automation` kind. Provisioning creates one human Host Operator and validates that referenced kind on startup; unrelated automation Principals are valid records, but provisioning creates no automation Grant. The Installation selects its current Local Host without selecting the physical storage generation, whose ownership belongs to the [Installation-maintenance decision](2026-08-26-saki-manifest-selected-installation-maintenance.md). Provisioning creates or validates children in a fixed order and changes the owner from `provisioning` to `ready` only after all children are durable, so every committed interruption point resumes without inventing new references. Its public `SakiAccess` interface owns bootstrap and logout; its `SakiControlPlaneModule` interface owns protected Projection queries, Control Intent submission, and invalidation. One failing invalidation listener emits a fixed credential-free diagnostic while later listeners continue, and every listener registration is disposable. Storage tables and the authentication resolver remain outside browser entrypoints.

**Use one versioned Installation Access aggregate for security lifecycle updates and local recovery.** Distinct branded, revisioned Bootstrap Challenge and Browser Session entries live inside one keyed record. Their ids append a typed child segment and canonical decimal ordinal to the owning Access id. Monotonic ordinals allocate deterministic ids, verifier digests bind to those ids, and cleanup never lowers either high-water mark. One expected-revision update validates an `issued` challenge, records terminal `consumed`, revokes other issued challenges, and inserts exactly one `active` session before `Set-Cookie` becomes available. The first successful exchange also records an immutable completion summary that survives detailed-entry cleanup. Concurrent exchange and replay return the same generic unavailable result. A lost response leaves the commit intact. Server-clock expiry, logout, Principal retirement, and Installation generation replacement produce monotonic terminal states; cleanup only deletes terminal entries after the configured retention interval.

**Separate initial completion from repeatable local reauthentication.** Every privileged launcher startup issues and displays a fresh challenge while preserving older unexpired issued challenges. Before immutable completion its purpose is `initial-bootstrap`; afterward it is `local-reauthentication`, but both use the same strict exchange operation. Expiry, logout, or a lost `Set-Cookie` response is recovered by a challenge from a later launcher startup, never by reopening or replaying the consumed initial challenge. Reauthentication does not revoke other valid sessions, and logout revokes only the presented session.

**Authenticate a Principal, then re-evaluate authority.** A Browser Session binds a Principal and Installation generation but carries no Grant. Every protected query and submission resolves the current session again, checks the current Principal lifecycle, and reads the current Grant state and scope. Grant revocation immediately denies later protected work without deleting the session. Protected operations include project-selection inspection, Project-index and Development-Workspace queries, and the first successful `register-development-project` Intent. The [Project-registration decision](2026-08-20-saki-existing-directory-project-registration.md) owns its additional recovery and receipt rules.

**Carry authentication through one Saki-owned Connection channel.** `@breakfastdapaidang/saki-host-api` registers `/saki` and owns strict schemas for `access/read`, `access/exchange`, `access/logout`, `control/query`, and `control/submit`. It rejects a non-empty URL query before dispatch or decoding, reads Cookie, Origin, and the request-token header from trusted Connection metadata, uses the Host-only authentication resolver, and emits the opaque post-commit cookie header outside JSON. The channel registration requires `Cache-Control: no-store` on every pre-handler, handler, success, denial, and error path and replaces every transport or RPC failure with one fixed opaque error, so parser, request, exception, and internal sentinel details do not cross the carrier. The browser face uses same-origin credentials. Connection gained generic request metadata, required and handler response headers, an optional opaque-error policy, and client call options; Typert only adapts mechanically to that generic reply type and owns no Saki authentication rule.

**Limit each clear authenticator to one named carrier.** The bootstrap secret exists only in the launcher handoff and exact exchange body. The raw session credential exists only in `Set-Cookie`, Cookie, and the browser's HttpOnly jar. The configured Origin must be one exact HTTP(S) loopback origin according to Connection's shared hostname classifier. Authenticated Access contains a request token derived from that raw cookie by a versioned, domain-separated HMAC; mutations require that exact Origin and a constant-time token comparison. Durable Installation Access contains only domain-separated bootstrap and cookie digests plus non-secret derivation metadata. Business results, Projections, errors, fixtures, events, and snapshots contain no raw secret or cookie credential.

## Consequences

`pnpm run saki` starts a long-lived loopback Host with SQLite persistence and emits one launcher handoff on every non-oneshot startup. The output names the challenge purpose and contains the only clear secret. If the process stops before exchange, the original unexpired handoff and the next startup's fresh handoff are both valid until one exchange consumes its selected challenge and revokes the rest. Once initial bootstrap commits, an existing HttpOnly cookie authenticates the same Principal after restart, while a fresh local-reauthentication handoff remains available if that cookie was lost.

The API deliberately serves one local Host Operator. GitHub OAuth, multiple users, remote Saki Hosts, non-loopback deployment, and browser-only recovery UI remain separate decisions. Source and built-bundle snapshots drive the real `/saki` HTTP transport, verify initial and reauthentication launcher purposes without recording either clear secret, restart against the same SQLite database, and prove that the original cookie retains access to the registered Project.

## Alternatives considered

- **Put authentication into Typert Remote** — couples one product's cookie and Grant semantics to the generic generated RPC registry and still needs an HTTP metadata escape hatch.
- **Add a raw Saki HTTP route beside Connection** — duplicates route trust, JSON limits, correlation, cancellation, and disposal while creating two competing Host carriers.
- **Persist a browser bearer, local password verifier, or independent request-forgery secret** — adds reusable secret storage and recovery lifecycle even though the presented high-entropy cookie can authenticate the session and derive its request token.
- **Store challenges and sessions as independent records** — cannot express consume-and-create with the storage domain's one-record compare-and-set guarantee.
- **Cache Grant authority in the Browser Session** — lets an old session retain permissions after Grant revocation or narrowing.
- **Invent a no-op bootstrap-only Control Intent** — makes a successful mutation protocol look settled before any real product action exists.

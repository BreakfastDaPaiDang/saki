# Agent Note: polling-first staged GitHub synchronization

Status: implemented

English | [中文](2026-08-18-saki-polling-first-github-synchronization.zh.md)

## Problem

Saki treats GitHub Projects v2 as the authority for shared Work Item Status and manual order. A Board assembled directly from paginated responses can nevertheless combine facts that never existed together: page cursors are not change offsets, a Project-level `updatedAt` value is not documented as a revision for every item or field-value change, and a process may stop after any page. Configuration adds a second atomicity problem because a newly saved Project, Repository, field, or option mapping must not replace the working mapping until GitHub confirms the complete replacement.

The first release also needs useful offline behavior. A network, permission, mapping, rate-limit, cancellation, or restart failure must preserve the last confirmed Board and expose safe recovery evidence instead of publishing a partial candidate or an optimistic state.

## Decision

**Keep GitHub transport and Saki Board semantics in separate plugins.** `@breakfastdapaidang/saki-github` defines branded external identities, strict raw facts, complete-scan candidates, typed failures, and the replaceable `SakiGitHub` Service. `@breakfastdapaidang/saki-github-app` provides the Product App implementation. It resolves the private key only for one operation, requires `local-user-trust`, and creates a short-lived installation token with the exact read or write permissions needed by that operation. Installation identity reads use an App JWT; Repository-access enumeration and Project reads use installation-wide tokens, while Repository reads and complete Board scans bind the token to the configured Repository. Only installation-token REST responses contribute installation-token rate observations. The Provider rejects unexpected installation grants, Repository access, or token scope. The control plane owns configuration, mapping, scheduling, durable publication, and product Projections. The Host API projects those results without exposing storage records or credentials.

**Admit only a stable complete candidate.** The Product App completely enumerates Project fields, ordered archived and unarchived items with all field-value pages, and open Issues from the configured Repository. Every page repeats and validates its owning Project, Repository, or item identity before contributing facts. One Repository Issue number maps to one Issue identity, and the same Issue identity appearing in Project membership and the open-Issue enumeration must carry identical facts. Each pass has bounded page, item, field-value, response, timeout, rate-observation, and concurrency limits and requires stable pre/post Project, Repository, and connection-count observations. Installation Repository identities and Project fields use fixed Service admission limits; the Provider's configurable item limit applies only to Project items and open Issues. Because those observations are not a documented global revision, one operation performs two consecutive complete passes. Their versioned semantic fingerprints must match. The fingerprint includes external identities and source revisions, field and option identities, Project membership, Status, archive state, Issue state, API order and neighbors, and the pass fences. It excludes Provider timing and rate observations plus presentation-only values; retained Repository, Project, Issue, and item revisions cover mutable display facts that affect the Board. A mismatch is a failed scan, never a candidate.

Page cursors and partial arrays remain operation-local. The Service has no partial-result arm, and the control plane revalidates every candidate before mapping it. Targeted Work Item mutation inspections remain independent operations and do not advance the Board checkpoint. The [Branch Delivery and Milestone Release Evidence decision](../feature/2026-08-18-saki-branch-delivery-and-milestone-release-evidence.md) owns delivery-specific pull-request, review, CI, Milestone, tag, Release, Commit, and ancestry reads together with their provider-scoped pending-record loop; those reads also never advance the checkpoint.

**Publish configuration, Board, and checkpoint through one durable owner.** Control-plane state version 4 stores one `github_project_sync` aggregate per Development Project and idempotent `github_sync_configuration_intents`. A configuration Intent validates a field-scoped patch, expected revision, actor, and exact external ids, then saves a pending candidate configuration. A patch equal to the current pending or active configuration returns `configuration-unchanged` without allocating a revision. Saving does not make a changed configuration active. The first complete scan for that configuration performs one expected-revision update that activates it, publishes the confirmed Board, advances its local generation and remote fingerprint, records freshness and rate evidence, and schedules the next poll.

Every durable scan write for one Project runs through the same per-Project operation tail. Its atomic update callbacks therefore have one writer, and the defensive concurrent-change guards inside those callbacks are unreachable under the control plane's ownership invariant.

A failed or expired attempt records a bounded typed failure and retry schedule while retaining the prior active configuration, Board, checkpoint, generation, and confirmed time. Attempt ids and configuration revisions prevent an older Provider result from publishing after a replacement configuration or lease. The aggregate commit and saved receipt are separate durable writes. At startup, at most one prepared configuration Intent may exist per Project. If its exact aggregate commit already exists, recovery recognizes that commit before rechecking authority and finishes the saved receipt without allocating another revision; otherwise it resumes the retained Intent to a conflict, failure, or saved result. Startup then revalidates all cross-record identities before other effects, expires retained in-flight work, and requests immediate recovery. An interactive refresh is durably prioritized over background work and returns the current Projection immediately; it does not wait on the network.

**Map only exact configured identities.** The configured Status field and all seven Status option ids must still exist in the candidate. Names may be displayed but never repair an identity. Only Issue items from the configured Repository enter the Board. Their GitHub item order determines neighbors; an archived matching Issue becomes Canceled, and an open Repository Issue absent from the Project becomes Inbox with an explicit non-membership fact. Duplicate Project items for one Issue, duplicate derived Work Item identities, cross-Repository facts, or a mismatched Provider mapping failure invalidate the attempt. Mapping repair remains read-only: the Projection names the missing identities and blocks Work Item mutations instead of guessing by name.

The control plane persists and delivers at most 10,000 Work Items in one confirmed Board. A complete candidate whose derived Board exceeds that limit records `{ kind: 'capacity', resource: 'board-work-items', limit: 10_000, observed }`, retains the prior Board and checkpoint, and never truncates the candidate. Mapping evidence is bounded independently so a failed attempt cannot recreate the oversized payload through its failure Projection.

**Use one recoverable polling Consumer.** The control-plane plugin optionally injects `ctx.sakiGitHub`; existing compositions still load without a Provider. When present, the contained Consumer drains durable attempts, calls only the Service, and publishes or fails through the aggregate owner. Per-Project active and background intervals and the background rate reserve are validated configuration fields. The scan-attempt lease lifetime is validated control-plane plugin configuration. Disposal cancels Provider work and waits for the Consumer; any retained lease is recoverable after expiry or restart. The Product App separately serializes requests per installation, prioritizes interactive work over background pages, and bounds concurrent complete scans across installations.

The Host API exposes exact cached and interactive Board queries plus Project Settings synchronization evidence. The cached path is a pure durable read. The interactive path writes only the scan request before returning the same current-state schema. Both unconfigured and configured Projects have explicit Projection states, and confirmed Projections cross-check Project, Repository, configuration revision, checkpoint, generation, Work Item source, failure, mapping, freshness, and mutation-availability relationships.

[ADR 0013](../../../../docs/adr/0013-polling-first-staged-github-synchronization.md) owns the broader synchronization protocol, including mutation recovery and later webhook behavior. The implemented [recoverable GitHub Work Item mutations](2026-08-16-saki-recoverable-github-work-item-mutations.md) own Create, Move, and targeted Work Item inspection. The implemented [Branch Delivery and Milestone Release Evidence](../feature/2026-08-18-saki-branch-delivery-and-milestone-release-evidence.md) owns targeted delivery reads, its current provider-scoped pending loop, and pull-request delivery mutations. The implemented [Saki upstream synchronization](../process/2026-08-15-saki-upstream-synchronization.md) remains a separate repository-maintenance workflow.

## Consequences

The two-pass rule doubles complete-read cost in the stable case, and a busy Project may require a later poll before two passes agree. This is accepted for the single-operator foundation because it removes an undocumented global-revision assumption; validated intervals, rate reserve, priority, and bounded admission protect interactive work. Webhooks are not required and may later do no more than durably request an earlier scan.

The 10,000-Work-Item limit bounds durable and wire validation cost. It gives up publishing a new generation for a larger Board, while the typed failure preserves the prior snapshot and avoids both silent truncation and an oversized failure payload.

Keyless tests use a fake `SakiGitHub` Provider through the real bundle, control plane, Host API, durable restart path, and snapshot transcript. The transcript holds the Provider absent to prove `saved`, holds the first scan to prove `activating`, releases one complete scan to prove `activated`, restarts with the same Board and checkpoint, and retains both through a typed transport failure. Provider tests exercise the real Octokit request boundary with controlled GitHub replies, including pagination, parent-identity mismatches, cross-surface Issue disagreement, stability mismatch, permissions, token scoping, response bounds, and rate failures. A live Product App smoke remains an operator prerequisite because CI does not own an installed App, private key, organization Project, or external allowance.

The Service mutation declaration map in this decision supports exact Issue creation, Project membership, Status, API position, and Issue state operations. Pull-request creation belongs to [Branch Delivery](../feature/2026-08-18-saki-branch-delivery-and-milestone-release-evidence.md); Contents and Workflows writes remain absent. The Board never infers any mutation availability from App installation grants.

## Alternatives considered

**Trust Project `updatedAt` as a global fence.** GitHub documents object update fields but does not promise that every item Status or field-value change advances the containing Project. A count-preserving edit could therefore pass equal Project fences.

**Publish after one complete traversal.** A mutation between pages can still create a torn candidate even when membership counts do not change. Two matching semantic traversals are the strongest bounded validation available without a server-side snapshot token.

**Activate configuration when it is saved.** A typo, deleted option, inaccessible Repository, or recreated Project field would discard the last working Board before the replacement is proved. Pending activation keeps the existing configuration authoritative until one atomic successful publication.

**Persist cursors or publish pages incrementally.** Cursors paginate one traversal and do not prove removals or unchanged earlier pages. Persisting them would turn a transport detail into false recovery evidence.

**Repair mappings by name.** Human-readable names can be renamed or reused after recreation. Exact node ids and an attributed future repair Intent avoid silently attaching a Saki status to a different remote meaning.

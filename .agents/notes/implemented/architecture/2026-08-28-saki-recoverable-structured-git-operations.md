# Agent Note: Recoverable structured Git operations

Status: implemented

English | [中文](2026-08-28-saki-recoverable-structured-git-operations.zh.md)

## Problem

The Changes surface needs to inspect a bound repository, show bounded Diffs, and apply explicit stage, unstage, and Commit requests without making a browser-provided path authoritative. A status row is meaningful only within one complete repository observation, and every mutation must reject if the Resource Binding, HEAD, index, worktree, or inherited-change baseline has changed since that observation.

System Git effects cannot run inside a control-plane storage transaction. Process loss may occur after Git changed the index or a ref but before Saki recorded success, so an acknowledgement timeout cannot be treated as proof that no effect occurred. The control plane and Local Host need separate durable evidence, a single write owner, and a fail-closed result for effects whose outcome cannot be proved.

## Decision

### Display-safe observation and Diff

The protected `project-changes` query resolves the current active Resource Binding on its owning Host and publishes one complete browser-safe `ProjectGitStatusObservation`. The observation includes exact Binding revision, HEAD, branch, upstream, index-tree evidence, a worktree fingerprint, structured change rows, repository-level mutation eligibility, and a status fingerprint. Each change carries a bounded repository-relative display path plus an opaque observation-scoped id and fingerprint. File selections inside mutation Intents carry only the id and fingerprint; canonical Host paths remain private.

Parent status commands and non-gitlink Diff commands run with every submodule ignored. The Host reconstructs accepted gitlink status rows solely from scoped raw inventory; its nested reader exposes HEAD only after admitting stable nested administrative state, and gitlink Diff is unavailable before any Diff command executes. Public rows expose only the parent repository's proven gitlink commit relation as `changed`, `unchanged`, or `unknown`, never unobserved nested tracked or untracked dirtiness. If nested admission fails, stable directory identity may prove status mode `160000` while worktree evidence remains unavailable; provider-private identity evidence does not cross the Host API, and a changed gitlink with no proven current mode rejects the complete status. Before repository-aware Git reads a copied index, the Host captures the source index's native modification time between filesystem-version confirmations, sets the private copy's access and modification times to the whole-second floor of one second before that timestamp, clamped at the Unix epoch, and confirms that its applied modification time is not newer than the source. This preserves Git's racy-clean content checks for fast same-size worktree rewrites; unstable or unconfirmed timestamp evidence rejects the observation. Sparse configuration is derived from the admitted config snapshots, while assume-unchanged and skip-worktree flags are read from each private index and compared across the two observation rounds; status and Diff do not rediscover a live repository for those facts after stable inspection. Exact ordinary assume-unchanged paths may reconstruct Git-omitted status rows from same-round raw inventory, but remain explicit mutation blockers. A visible skip-worktree change also rejects the complete status instead of recasting captured current evidence as unavailable; other unsupported index flags remain explicit mutation blockers. Git's recursive submodule machinery therefore cannot open nested or escaping control data for status or Diff.

The `project-diff` query accepts the exact status fingerprint, opaque change id, layer, and optional cursor. The Host resolves that tuple against a new stable repository view and returns a bounded page whose patch fingerprint and cursor bind every page to one complete patch. Stale observations, missing or ambiguous rows, unsupported binary or untracked content, malformed output, and configured byte, line, or time limits return closed safe failures rather than partial authority.

### Direct Control Intent Host Operations

`StageFiles`, `UnstageFiles`, and `CreateCommit` are durable Control Intents. Their immutable payload freezes the authenticated Actor, Grant evidence, expected Registry and Project revisions, Resource Binding revision, status fingerprint, HEAD, exact index tree, worktree fingerprint, complete pre-effect baseline, and either selected change ids with fingerprints or the Commit message. The Host receives no caller-selected path.

The control plane maintains one Binding Write Admission record for every Resource Binding. It is either `available` or a `manual-host-operation` reservation in `reserved` or `accepted` phase. The reservation identifies the direct `{ kind: 'control-intent' }` source, action, Binding revision, and eventual Host preparation, so only one structured writer can cross the Binding's write boundary. Startup validates the Host request's complete private Binding authority against the Registry-derived snapshot, not only its id and revision. Unknown admission variants fail closed.

A Project-registration Registry compare-and-set can commit before the registration Intent advances or creates its Binding Write Admission. The Registry then exposes the Project while the registration remains recoverable, so a concurrently submitted Git Intent can durably stop at `prepared`. Pure startup validation tolerates the missing admission only for that exact phase and a Binding identified by registration recovery; later Git phases still require their admission evidence. Project recovery creates the `available` row before Git recovery resumes. If its fresh observation advances the Binding revision, the retained Git Intent reaches the Host boundary but closes as `source-canceled` with proven `effect: none`, clears unaccepted admission fencing, and releases the row instead of applying stale authority.

The control plane persists the Intent, reserves Binding Write Admission, calls `prepareOperation`, accepts that exact preparation with a compare-and-set, and calls `startOperation` outside storage callbacks. The Host exposes `prepareOperation`, `startOperation`, `inspectOperation`, `cancelOperation`, and post-commit change notifications. Exact request replay returns the same Host Operation; the same source with different immutable input conflicts. `busy` and `unavailable` start results keep the accepted operation recoverable, while cancellation and proven no-effect failures retain explicit evidence. After validating the complete durable graph, startup recovers current manual owners first, then remaining Intents by `createdAt` and id, in one bounded pass. Every terminal Intent with preparation re-inspects its exact Host Operation to retry cleanup and requires the returned snapshot to equal the durable snapshot. Terminal recovery releases an admission only while it still names the exact Intent source and payload; `reconciliation-required` retains admission, and a later valid owner's reservation remains authoritative. Typed browser receipts carry only phase-valid durable Intent, Host Operation, and terminal-result evidence; they never include `postObservation`. `onChanged` only invalidates Changes, whose Consumer reruns the protected query to obtain a fresh authoritative status after terminal completion or replay.

Host Operations currently accept only the direct `control-intent` source. The [fenced dispatch proposal](../../proposed/architecture/2026-08-18-saki-fenced-idempotent-dispatch-admission.md) defines `execution-dispatch` and `agent-run` sources together with Dispatch Claims, fencing-token acceptance, Execution Leases, and Agent Run allocation. Those sources reuse `prepareOperation` and the Host Operation lifecycle instead of introducing a second preparation API.

### Index and ref publication

After admission and before planning an effect, the Host reopens the exact active Binding and verifies every frozen precondition. Stage and unstage resolve selected ids inside that observation and construct a complete target index. Every mutation then creates a complete random operation-owned pin beside the bound index before any real `index.lock` exists: a stage or unstage pin contains the target index bytes, while a Commit pin contains the operation's exact lock marker. The durable `not-started` plan records the pin's path, digest, byte length, device and inode identity, and mode. On POSIX, an existing-index pin preserves and verifies the index's permission bits; for an existing Windows index, the Host installs the index DACL on the still-empty pin before writing bytes. A missing-index pin retains its actual Git-style umask-derived mode.

Before persisting that plan, the Host synchronizes each private file and pin, synchronizes `objects/info`, every present loose-object fanout, `objects`, the payload, the scratch wrapper, and the operating-system temporary parent in bottom-up order on POSIX, and then revalidates the scratch identities. The private-object manifest is strictly named and bounded by the stable inventory's aggregate path bytes plus the operation's possible new blobs, root tree, and Commit object; it records newly materialized private loose objects, while a Commit plan separately retains its exact candidate commit and root tree. Each attempt verifies the complete pin evidence, creates a no-clobber hard link from the pin to `index.lock`, proves that both names still identify the recorded file, and re-reads the complete expected index evidence after lock acquisition. Stage synchronizes only the exact source object ids returned by its selected worktree hashes; Commit synchronizes its exact candidate and root plus every private-manifest object that is currently loose in the source. Source-existing nested subtrees remain prior repository authority. Existing packed objects require no loose-directory barrier, while a loose object or fanout that disappears during the barrier leaves the attempt retryable. Stage and unstage publish an existing index by same-directory rename on POSIX or `ReplaceFileW` on Windows, and publish a missing index through a create-only hard link from the owned lock; each path synchronizes the index directory before success can be recorded. Publication advances through `not-started`, `attempting`, and `applied-recorded`; inspection distinguishes the target index, the untouched expected index, and contradictory evidence without treating a partial lock write as ownership.

The provider treats a recovered index effect plan as untrusted durable input. It admits a nonempty bounded change list whose display paths are bounded repository-relative Git paths, and independently limits aggregate UTF-8 display-path bytes and aggregate decoded exact-path bytes carried as canonical Base64. Raw count and byte preflight stops before structural element parsing or Base64 allocation, so an oversized row cannot force traversal or decoding of later evidence. The `update-index --index-info` stdin allowance equals the inventory aggregate path-byte allowance plus one object-format-specific fixed record allowance for every selected change and saturates at Node's Buffer limit. Stage reads symbolic links without following them and hashes their exact target bytes; a Node filesystem failure remains retryable, and cancellation is checked again after `readlink` and before `hash-object`.

Commit reads `user.name` and `user.email` only from worktree-local or repository-local configuration with includes disabled, supplies its frozen timestamp and timezone to `git var GIT_AUTHOR_IDENT`, and retains the Git-canonical name and email that Git will write as both author and committer. An absent or invalid canonical identity fails before a plan is persisted. Every structured-mutation Git plumbing invocation fixes `core.fsyncMethod=fsync` and `core.fsync=loose-object,index,reference` in addition to disabling hooks and signing. Commit uses the exact observed index tree and `commit-tree` to create the unsigned object.

While its verified pin holds the operation-owned `index.lock`, an attached-HEAD attempt revalidates that HEAD still names the plan's frozen target branch and publishes only that ref through an expected-old-object compare-and-set. A concurrent checkout after that revalidation cannot redirect publication to another branch. After `update-ref`, the Host synchronizes the stable target reflog file and the target ref and reflog parent-directory chains; recovery repeats that barrier before recording success. For an attached plan, the exact current target proves publication without parsing an oversized reflog. After later external ref progress, the operation-specific transition proves publication only when it is read from the same stable reflog within the frozen `reflogReadLimit`; oversized or changing attempted history enters `effect-unknown` reconciliation. An unborn HEAD follows the same symbolic target rule with a zero expected object id. Detached HEAD remains inspectable and supports Diff, stage, and unstage, but CreateCommit fails before an effect because Git 2.45 cannot atomically prove that `HEAD` stayed direct while compare-and-setting its object id. Historical detached plans are recovery-only: a `not-started` record terminates as `unsupported-state` with proven `effect: none`; an `attempting` or `applied-recorded` record never reruns Git and succeeds only after the exact old-to-new operation marker is read from stable per-worktree `logs/HEAD`, that file is synchronized, and the parent-directory chains for per-worktree `HEAD` and its reflog are synchronized. The Host retains the target, expected and new object ids, parent, Git-canonical signature, and reflog marker as effect evidence. Git 2.45 remains the minimum supported version.

### Artifact ownership and reconciliation

Planning snapshots `operationMaxIndexBytes` as the required `indexReadLimit` in every effect plan and snapshots `operationMaxReflogBytes` as `reflogReadLimit` in a Commit plan. Durable validation requires Buffer-safe configured bounds and rejects an index limit that cannot retain the plan's expected index, target index, or pin. Once the plan is durable, resume, inspection, cancellation, blocking-lock removal, and terminal cleanup use those frozen limits rather than live configuration. Lowering live configuration therefore cannot strand an exact durable artifact, while raising it cannot enlarge an older operation's reflog-read budget.

Every pin read is bounded by its durable byte length and the plan's `indexReadLimit`. Pin use and deletion require its exact same-directory path, length, device and inode identity, mode, digest, and stable open-file and pathname identity. Each mutation also creates a random `saki-host-operation-*` outer directory directly under the operating-system temporary directory, sets owner-only permissions where supported, and writes an exclusive owner marker derived from the Host Operation id and immutable request fingerprint. The durable plan records the creation identities of the outer directory, payload directory, and owner file together with the marker digest. Those identities authorize runtime path use as well as cleanup. Before each Node or Git handoff receives a scratch-derived hooks directory, object directory, or private index, the Host revalidates the outer directory, owner marker, and payload, then derives the child path from the verified payload. Commit repeats that check after `attempting` is durable and immediately before `update-ref`; a mismatch remains an attempted publication and enters reconciliation instead of returning to retryable no-effect evidence.

Cleanup verifies the wrapper and marker, renames the wrapper to a deterministic same-parent quarantine path derived from durable evidence, and promotes the owner marker to an external witness. It enters the payload only when a no-follow metadata read identifies the recorded real directory. Its no-follow walker captures each real child directory's identity and revalidates it after enumeration, before every child, and before removal; files, symbolic links, and Windows junctions receive a second type-and-identity check and are unlinked without following their targets. A failed unlink or directory removal counts as acknowledgement loss only when a follow-up no-follow lookup proves the path absent. A missing payload permits wrapper cleanup, while a foreign or unavailable payload replacement and any other non-missing removal failure abort cleanup, best-effort restore the marker and wrapper to the recorded path, and otherwise preserve the quarantine and witness for terminal replay. Recovery never sweeps either artifact class. Random owner-only wrappers, repeated identity checks, and avoiding recursive-remove APIs narrow pathname replacement races, but portable Node APIs do not provide handle-relative or `openat` path use or removal across Windows and POSIX. A malicious same-user process that can modify the private directory may therefore still replace a pathname between validation and the next filesystem call.

The Local Host stores the immutable request, lifecycle snapshot, and private effect plan in `saki_host_execution@1`. Once publication may have started, recovery compares durable plan evidence with the current index or ref. A proven target becomes success. A proven no-effect result is terminal only before publication could have occurred. Returning to the expected value after an attempted publication is an ABA-ambiguous outcome, and missing or contradictory witnesses become `reconciliation-required` with `effect-unknown` or `evidence-conflict`; Saki does not repeat the mutation automatically.

For an operation with a durable pin plan, the Local Host precisely removes its operation-owned blocking `index.lock` or proves that link absent, synchronizes the index directory, and verifies that the owned lock remains gone before persisting `succeeded`, `failed`, `canceled`, or `reconciliation-required`. An applied index is likewise not recorded as success until its directory-entry synchronization completes. POSIX directory-sync errors propagate; Windows does not expose supported directory `fsync` to this provider, so the scratch, source-object, index, ref, and reflog directory barriers are explicit platform limitations there. Reflog file data still uses a writable file handle synchronization on every platform. Only after the semantic terminal state is durable does exact-owner, idempotent cleanup remove the nonblocking pin and scratch directory; every terminal replay retries that cleanup. Acknowledgement loss therefore cannot expose a terminal record while retaining the operation-owned blocking lock.

This decision's original complete product state is version 6: `saki_control_plane@6`, `saki_host_execution@1`, and `saki_storage_generation@4`. Current product state version 9 retains its direct Stage, Unstage, and Commit records in `saki_control_plane@9`, `saki_host_execution@4`, and `saki_storage_generation@7`; the v8-to-v9 step adds the separate Branch Delivery Push Host operation format without changing the original direct-operation requests or evidence. The adjacent v4-to-v5 migration preserves the historical `saki_control_plane@4` plus `saki_storage_generation@2` state, creates an empty Host Operation domain, initializes one `available` Binding Write Admission for each Resource Binding, and seals the new generation as state v5. Its source reader consumes one closed frozen pack of exact v4 ids, limits, grammars, schemas, fingerprints, and helpers; the frozen v5 declarations validate only that migrated output. The adjacent v5-to-v6 migration preserves structured Git state and adds the recoverable Work Item mutation state owned by the [GitHub Work Item decision](2026-08-16-saki-recoverable-github-work-item-mutations.md).

Packed-object coverage proves that an exact object absent from the loose namespace does not trigger per-object Git probes. This decision partially realizes the broader [recoverable Control Intent](../../proposed/architecture/2026-08-18-saki-recoverable-control-intents.md), [stable Resource Binding](../../proposed/architecture/2026-08-18-saki-stable-resource-bindings.md), and [fenced dispatch admission](../../proposed/architecture/2026-08-18-saki-fenced-idempotent-dispatch-admission.md) proposals. Those notes remain active because rebind and retirement, automated dispatch, Agent Run allocation, fencing claims, and Execution Leases are not implemented by the direct Git operation set.

## Alternatives considered

**Send paths or Git argv from the browser.** A path or command line would turn presentation data into Host authority and make replay depend on untrusted parsing. Opaque change ids let the Host resolve one exact observed row and keep path policy inside the capability provider.

**Run Git inside a control-plane storage callback.** Git cannot join the SQLite transaction, and holding a callback across a subprocess would not make the filesystem effect atomic. Separate Intent, Binding Write Admission, Host preparation, and inspection evidence make the unavoidable split recoverable.

**Mutate the live index or create `index.lock` while planning.** Either choice could leave an unowned partial effect or a blocking path before durable publication evidence exists. A private alternate index produces and verifies the target, while the random pin keeps any pre-plan residue nonblocking until the durable plan can authorize exact lock acquisition.

**Verify symbolic HEAD and update its referent in one ref transaction.** Git rejects that transaction because the symbolic ref and its referent are duplicate updates. Freezing the exact target, revalidating HEAD immediately before the effect, and compare-and-setting only that target keeps the destination deterministic without raising the minimum Git version.

**Publish a detached Commit by compare-and-setting `HEAD` with no dereference.** The expected object id does not prove that `HEAD` is still direct: a concurrent checkout can make it symbolic to a branch at the same object, after which the update overwrites that symbolic state. Git 2.45 has no atomic direct-ref-plus-object precondition, so the release keeps detached reads and index mutations but makes CreateCommit unavailable.

**Treat a lock, timeout, or expected post-crash value as proof of no effect.** Another writer may own the lock, and an attempted effect may have succeeded and then returned to the old value. Those cases remain retryable before publication or require reconciliation after an ambiguous attempt.

**Reapply live read limits while recovering an existing plan.** A lower limit could make exact retained evidence impossible to inspect or clean up, while a higher limit would expand an old operation's resource budget. Persisting the validated limits with the plan keeps recovery deterministic across restart and configuration changes.

**Wait for automated dispatch before adding Host Operations.** Manual Git mutations cross the same durable Host boundary. A source-general Host Operation lifecycle provides the direct path and a stable extension point for dispatch without claiming its fencing protocol is complete.

## Consequences

The browser receives complete bounded Git facts and durable operation receipts without filesystem authority. Manual structured Git writes have one Resource Binding owner, exact replay identity, and deterministic recovery across every persisted boundary. Known no-effect failures remain retryable or terminal, while unknown effects deliberately stop automation for operator reconciliation.

Durable plans are larger and configuration changes affect only plans created afterward. POSIX Hosts pay additional file and directory synchronization work; Windows publication depends on DACL support and `ReplaceFileW` and cannot claim directory-`fsync` durability. Fixed Git per-file fsync and platform-specific publication increase write cost in exchange for stable recovery budgets, preserved index permissions, and explicit publication barriers.

The design adds durable control-plane and Host tables, same-filesystem pins, scratch artifacts, extra Git observations, and more publication states. It requires Git 2.45 or newer. A hard crash before the scratch identity becomes durable, or an early filesystem failure whose exact cleanup also fails, may leave an owner-only, semantically inert shell that can retain repository index, blob, or Commit bytes until manual cleanup. A crash after a pin is synchronized but before its plan becomes durable may likewise leave one nonblocking operation-named pin beside the bound index; a stage or unstage pin contains index bytes, while a Commit pin contains only its exact lock marker. Recovery never sweeps unrecorded pins or scratch directories. A checkout racing after final attached-HEAD revalidation does not redirect the Commit, but it may leave the user's newly checked-out branch unchanged while the frozen prior branch advances; the receipt identifies the actual target. This direct Stage, Unstage, and Commit decision does not own Push, which belongs to [Branch Delivery](../feature/2026-08-18-saki-branch-delivery-and-milestone-release-evidence.md); detached Commit, rebind, retirement, Execution Dispatch, Agent Run creation, Dispatch Claims, fencing tokens, and Execution Leases remain separate work.

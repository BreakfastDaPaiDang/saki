# Agent Note: Recoverable structured Git operations

Status: implemented

English | [中文](2026-08-28-saki-recoverable-structured-git-operations.zh.md)

## Problem

The Changes surface needs to inspect a bound repository, show bounded Diffs, and apply explicit stage, unstage, and Commit requests without making a browser-provided path authoritative. A status row is meaningful only within one complete repository observation, and every mutation must reject if the Resource Binding, HEAD, index, worktree, or inherited-change baseline has changed since that observation.

System Git effects cannot run inside a control-plane storage transaction. Process loss may occur after Git changed the index or a ref but before Saki recorded success, so an acknowledgement timeout cannot be treated as proof that no effect occurred. The control plane and Local Host need separate durable evidence, a single write owner, and a fail-closed result for effects whose outcome cannot be proved.

## Decision

### Display-safe observation and Diff

The protected `project-changes` query resolves the current active Resource Binding on its owning Host and publishes one complete browser-safe `ProjectGitStatusObservation`. The observation includes exact Binding revision, HEAD, branch, upstream, index-tree evidence, a worktree fingerprint, structured change rows, repository-level mutation eligibility, and a status fingerprint. Each change carries a bounded repository-relative display path plus an opaque observation-scoped id and fingerprint. File selections inside mutation Intents carry only the id and fingerprint; canonical Host paths remain private.

Parent status commands and non-gitlink Diff commands run with every submodule ignored. The Host reconstructs accepted gitlink status rows solely from scoped raw inventory; its nested reader exposes HEAD only after admitting stable nested administrative state, and gitlink Diff is unavailable before any Diff command executes. Public rows expose only the parent repository's proven gitlink commit relation as `changed`, `unchanged`, or `unknown`, never unobserved nested tracked or untracked dirtiness. If nested admission fails, stable directory identity may prove status mode `160000` while worktree evidence remains unavailable; provider-private identity evidence does not cross the Host API, and a changed gitlink with no proven current mode rejects the complete status. Sparse configuration is derived from the admitted config snapshots, while assume-unchanged and skip-worktree flags are read from each private index and compared across the two observation rounds; status and Diff do not rediscover a live repository for those facts after stable inspection. A visible skip-worktree change also rejects the complete status instead of recasting captured current evidence as unavailable; other index flags remain explicit mutation blockers. Git's recursive submodule machinery therefore cannot open nested or escaping control data for status or Diff.

The `project-diff` query accepts the exact status fingerprint, opaque change id, layer, and optional cursor. The Host resolves that tuple against a new stable repository view and returns a bounded page whose patch fingerprint and cursor bind every page to one complete patch. Stale observations, missing or ambiguous rows, unsupported binary or untracked content, malformed output, and configured byte, line, or time limits return closed safe failures rather than partial authority.

### Direct Control Intent Host Operations

`StageFiles`, `UnstageFiles`, and `CreateCommit` are durable Control Intents. Their immutable payload freezes the authenticated Actor, Grant evidence, expected Registry and Project revisions, Resource Binding revision, status fingerprint, HEAD, exact index tree, worktree fingerprint, complete pre-effect baseline, and either selected change ids with fingerprints or the Commit message. The Host receives no caller-selected path.

The control plane maintains one Binding Write Admission record for every Resource Binding. It is either `available` or a `manual-host-operation` reservation in `reserved` or `accepted` phase. The reservation identifies the direct `{ kind: 'control-intent' }` source, action, Binding revision, and eventual Host preparation, so only one structured writer can cross the Binding's write boundary. Startup validates the Host request's complete private Binding authority against the Registry-derived snapshot, not only its id and revision. Unknown admission variants fail closed.

A Project-registration Registry compare-and-set can commit before the registration Intent advances or creates its Binding Write Admission. The Registry then exposes the Project while the registration remains recoverable, so a concurrently submitted Git Intent can durably stop at `prepared`. Pure startup validation tolerates the missing admission only for that exact phase and a Binding identified by registration recovery; later Git phases still require their admission evidence. Project recovery creates the `available` row before Git recovery resumes. If its fresh observation advances the Binding revision, the retained Git Intent reaches the Host boundary but closes as `source-canceled` with proven `effect: none`, clears unaccepted admission fencing, and releases the row instead of applying stale authority.

The control plane persists the Intent, reserves Binding Write Admission, calls `prepareOperation`, accepts that exact preparation with a compare-and-set, and calls `startOperation` outside storage callbacks. The Host exposes `prepareOperation`, `startOperation`, `inspectOperation`, `cancelOperation`, and post-commit change notifications. Exact request replay returns the same Host Operation; the same source with different immutable input conflicts. `busy` and `unavailable` start results keep the accepted operation recoverable, while cancellation and proven no-effect failures retain explicit evidence. Terminal recovery releases an admission only while it still names the exact Intent source and payload; a later valid owner's reservation remains authoritative.

This implemented source is the manual Control Intent path. The fenced dispatch design remains proposed: a later execution increment adds `execution-dispatch` and `agent-run` operation sources together with Dispatch Claims, fencing-token acceptance, Execution Leases, and Agent Run allocation. It reuses `prepareOperation` and the Host Operation lifecycle instead of introducing a second preparation API.

### Index and ref publication

After admission and before planning an effect, the Host reopens the exact active Binding and verifies every frozen precondition. Stage and unstage resolve selected ids inside that observation and construct a complete target index. Every mutation then creates a complete random operation-owned pin beside the bound index before any real `index.lock` exists: a stage or unstage pin contains the target index bytes, while a Commit pin contains the operation's exact lock marker. The durable `not-started` plan records the pin's path, digest, byte length, device and inode identity, and mode. Each attempt verifies that complete evidence, creates a no-clobber hard link from the pin to `index.lock`, and proves that both names still identify the recorded file. Stage and unstage then rename the lock over the index. Publication advances through `not-started`, `attempting`, and `applied-recorded`; inspection distinguishes the target index, the untouched expected index, and contradictory evidence without treating a partial lock write as ownership.

Commit uses the exact observed index tree, a frozen author and committer identity from Git configuration, and `commit-tree` with hooks disabled and signing disabled. While its verified pin holds the operation-owned `index.lock`, an attached-HEAD attempt revalidates that HEAD still names the plan's frozen target branch and publishes only that ref through an expected-old-object compare-and-set. A concurrent checkout after that revalidation cannot redirect publication to another branch. An unborn HEAD follows the same symbolic target rule with a zero expected object id. Detached HEAD remains inspectable and supports Diff, stage, and unstage, but CreateCommit fails before an effect because Git 2.45 cannot atomically prove that `HEAD` stayed direct while compare-and-setting its object id. The Host retains the target, expected and new object ids, parent, signature, and reflog marker as effect evidence. Git 2.45 remains the minimum supported version.

### Artifact ownership and reconciliation

Every pin read is bounded by its durable byte length and `operationMaxIndexBytes`. Pin use and deletion require its exact same-directory path, length, device and inode identity, mode, digest, and stable open-file and pathname identity. Each mutation also creates a random `saki-host-operation-*` directory directly under the operating-system temporary directory, sets owner-only permissions where supported, and writes an exclusive owner marker derived from the Host Operation id and immutable request fingerprint. Cleanup recursively removes only the exact recorded direct child with the matching marker. Recovery never sweeps either artifact class. These checks prevent mismatched ownership from authorizing use or cleanup, but they are not operating-system isolation against a malicious same-user process that can replace pathnames in writable directories.

The Local Host stores the immutable request, lifecycle snapshot, and private effect plan in `saki_host_execution@1`. Once publication may have started, recovery compares durable plan evidence with the current index or ref. A proven target becomes success. A proven no-effect result is terminal only before publication could have occurred. Returning to the expected value after an attempted publication is an ABA-ambiguous outcome, and missing or contradictory witnesses become `reconciliation-required` with `effect-unknown` or `evidence-conflict`; Saki does not repeat the mutation automatically.

For an operation with a durable pin plan, the Local Host precisely removes its operation-owned blocking `index.lock` or proves that link absent, synchronizes the index directory, and verifies that the owned lock remains gone before persisting `succeeded`, `failed`, `canceled`, or `reconciliation-required`. POSIX directory-sync errors propagate; Windows does not expose supported directory `fsync` to this provider, so that synchronization is an explicit platform limitation. Only after the semantic terminal state is durable does exact-owner, idempotent cleanup remove the nonblocking pin and scratch directory; every terminal replay retries that cleanup. Acknowledgement loss therefore cannot expose a terminal record while retaining the operation-owned blocking lock.

The complete product state is version 5: `saki_control_plane@5`, `saki_host_execution@1`, and `saki_storage_generation@3`. The adjacent v4-to-v5 migration preserves the historical `saki_control_plane@4` plus `saki_storage_generation@2` state, creates an empty Host Operation domain, initializes one `available` Binding Write Admission for each Resource Binding, and seals the new generation as state v5. Historical schemas remain frozen.

## Alternatives considered

**Send paths or Git argv from the browser.** A path or command line would turn presentation data into Host authority and make replay depend on untrusted parsing. Opaque change ids let the Host resolve one exact observed row and keep path policy inside the capability provider.

**Run Git inside a control-plane storage callback.** Git cannot join the SQLite transaction, and holding a callback across a subprocess would not make the filesystem effect atomic. Separate Intent, Binding Write Admission, Host preparation, and inspection evidence make the unavoidable split recoverable.

**Mutate the live index or create `index.lock` while planning.** Either choice could leave an unowned partial effect or a blocking path before durable publication evidence exists. A private alternate index produces and verifies the target, while the random pin keeps any pre-plan residue nonblocking until the durable plan can authorize exact lock acquisition.

**Verify symbolic HEAD and update its referent in one ref transaction.** Git rejects that transaction because the symbolic ref and its referent are duplicate updates. Freezing the exact target, revalidating HEAD immediately before the effect, and compare-and-setting only that target keeps the destination deterministic without raising the minimum Git version.

**Publish a detached Commit by compare-and-setting `HEAD` with no dereference.** The expected object id does not prove that `HEAD` is still direct: a concurrent checkout can make it symbolic to a branch at the same object, after which the update overwrites that symbolic state. Git 2.45 has no atomic direct-ref-plus-object precondition, so the release keeps detached reads and index mutations but makes CreateCommit unavailable.

**Treat a lock, timeout, or expected post-crash value as proof of no effect.** Another writer may own the lock, and an attempted effect may have succeeded and then returned to the old value. Those cases remain retryable before publication or require reconciliation after an ambiguous attempt.

**Wait for automated dispatch before adding Host Operations.** Manual Git mutations already cross the same durable Host boundary. A source-general Host Operation lifecycle provides the implemented direct path now and a stable extension point for dispatch without claiming its fencing protocol is complete.

## Consequences

The browser receives complete bounded Git facts and durable operation receipts without filesystem authority. Manual structured Git writes have one Resource Binding owner, exact replay identity, and deterministic recovery across every persisted boundary. Known no-effect failures remain retryable or terminal, while unknown effects deliberately stop automation for operator reconciliation.

The design adds durable control-plane and Host tables, same-filesystem pins, scratch artifacts, extra Git observations, and more publication states. It requires Git 2.45 or newer. A hard crash before the scratch identity becomes durable may leave an owner-only, semantically inert directory that can retain repository index, blob, or Commit bytes until manual cleanup. A crash after a pin is synchronized but before its plan becomes durable may likewise leave one nonblocking operation-named pin beside the bound index; a stage or unstage pin contains index bytes, while a Commit pin contains only its exact lock marker. Recovery never sweeps unrecorded pins or scratch directories. A checkout racing after final attached-HEAD revalidation does not redirect the Commit, but it may leave the user's newly checked-out branch unchanged while the frozen prior branch advances; the receipt identifies the actual target. Stage, unstage, and attached or unborn Commit are implemented; detached Commit, push, rebind, retirement, Execution Dispatch, Agent Run creation, Dispatch Claims, fencing tokens, and Execution Leases remain separate work.

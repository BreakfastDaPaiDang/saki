# Agent Note: Saki existing-directory Project registration and control-domain v2 recovery

Status: implemented

English | [中文](2026-08-20-saki-existing-directory-project-registration.zh.md)

## Problem

Local bootstrap establishes an authenticated Host Operator but does not identify a Development Project. First registration must accept an existing Git worktree without making a browser-supplied path authoritative, expose enough evidence for an informed confirmation without leaking Host paths or changed file contents, and create or adopt the DSH Workspace before committing Project records. Workspace creation and control-plane storage cannot share one transaction, so process termination or a lost response must not create a second Workspace, Project, Resource Binding, or receipt on retry.

## Decision

**Keep Host Execution read-only and inspection-specific.** `ctx.sakiHostExecution` exposes only `inspectProjectSelection(request, signal)`. The request names an enrolled Saki Host and carries an untrusted directory locator. The Local Host provider discovers ordinary, linked or detached, and local separate-Git-directory topology from filesystem control files before it runs repository-aware Git. It copies the admitted config, an enabled `config.worktree`, HEAD, current ref, index, and repository-local exclude and attribute files into a private control directory; explicit `git config --file ... --no-includes` queries audit the copied config, and a closed read-only argv set then keeps repository-aware Git from reopening the source config, HEAD, or index in that observation. Repository- and worktree-scoped include directives fail closed and are never followed, while `core.fsmonitor` must be absent or explicitly false. A source object alternate fails closed; the private view uses one generated alternate to the live admitted source object database. The provider accepts a successful result only when two independently collected valid observations and their source-control manifests agree, which detects observed changes without claiming to prevent every transient same-user race. Direct reparse locators and final Git marker, administrative, control-file, object-directory, and configured-worktree entries are rejected; the current FileSystem capability does not prove no-follow traversal for every ancestor component. A locator below the Git top level is accepted only after canonical containment is proven; all returned worktree and Workspace evidence names the top level. The Projection contains sanitized Git facts, lowercase, sorted, and deduplicated public-GitHub repository candidates when safe remotes provide them, a revisioned fingerprint, and an exact raw-byte inherited-change baseline whose path and content material is retained only as digests and bounded metadata. A candidate supports confirmation but does not bind or authorize a repository. A clean zero-entry baseline is complete; an unavailable baseline has a bounded reason and no partial entries or fabricated complete digest. Because this slice observes an initialized gitlink's nested HEAD but not nested staged, unstaged, or untracked membership, every initialized gitlink is conversion-ambiguous and blocks automatic mutation. The trusted observation contains canonical paths and opaque same-Host identities for the per-worktree and common Git administrative directories, but a retained identity, path, or prior Projection never authorizes a later effect.

**Add the first Project Registry in control-domain version 2 without claiming the wider binding lifecycle.** Version 2 of the `saki_control_plane` domain adds the `schemaVersion: 1` revisioned `development_project_registry` aggregate and keyed `registration_intents`. The Registry contains Development Projects, Resource Bindings, Host-scoped canonical-worktree and per-worktree Git-directory indexes, and committed Intent mappings. One Project, Binding, and Workspace have independent stable ids; canonical paths remain revisioned observations rather than product identity. A registration Intent retains its immutable request, server-derived Actor and Grant revisions, complete accepted inspection, phase-specific Workspace evidence, deterministic receipt id, and any committed identities. Same-Host canonical worktree or per-worktree Git-directory reuse conflicts; the retained administrative-directory identity prevents a replacement repository at the same path from being accepted as the original Binding, while a common Git directory only groups linked worktrees and does not collapse them.

**Persist before the possible Workspace effect and recover by observation.** A new `register-development-project` submission must match the browser-confirmed fingerprint and baseline under a fresh Host inspection and the current Registry revision. The control plane derives the Actor from the active Browser Session and current Grant, writes `prepared`, advances to `workspace-dispatching`, and re-inspects the retained canonical worktree path as an untrusted locator before it may call `WorkspaceRegistry.create`. It records the exact Workspace as `workspace-observed`, then compare-and-sets the Project, Binding, path indexes, and Intent mapping into one Registry revision, records `registry-committed`, and finally records `confirmed`. If that compare-and-set loses, the Intent enters `conflict` while the created or adopted Workspace remains registered for reuse; the control plane does not delete a Workspace the registration may not exclusively own. No Host or Workspace call runs inside a `storageDomain` update callback.

An Intent id is serialized in process and every durable phase change also checks the expected Intent revision and phase. Exact replay resumes the stored phase and converges on the same deterministic receipt and committed identities; reuse with changed content conflicts. If Workspace creation may have succeeded without an acknowledgement, recovery re-inspects the retained canonical worktree path as an untrusted locator and adopts only the unique Workspace whose id and path match the retained evidence. Current authority is required before a new effect begins. Principal retirement, Installation State Generation replacement, Grant revocation, or scope narrowing therefore blocks undispatched work, while a post-dispatch recovery may inspect and adopt the exact possible result without starting another effect.

Startup parses and cross-checks the complete provisioning, access, Registry, Binding, index, mapping, and Intent inventory before any repair write or external call. It resumes nonterminal registration only after that pure validation, recognizes a Registry mapping committed before the Intent phase advanced, and refreshes every committed Binding through a fresh Host inspection. A transient unavailable inspection leaves the Intent recoverable; changed identity or contradictory Workspace evidence enters `reconciliation-required`; expected-revision and duplicate-identity failures enter `conflict`; lost current authority before dispatch enters `failure`. Receipts expose only fields valid for their `prepared`, `confirmed`, `conflict`, `failure`, or `reconciliation-required` state.

This decision implements only the Host-inspection and first-registration subset of the broader [control-plane capability seams](../../proposed/architecture/2026-08-18-saki-control-plane-capability-seams.md), [stable Resource Binding](../../proposed/architecture/2026-08-18-saki-stable-resource-bindings.md), and [recoverable Control Intent](../../proposed/architecture/2026-08-18-saki-recoverable-control-intents.md) proposals. The separate [polling-first GitHub synchronization](2026-08-18-saki-polling-first-github-synchronization.md) implements the read-only GitHub slice. Those broader notes remain proposed because Host and GitHub mutation operations, the two remaining Model Account and Image Generation capability seams, rebind, retirement, repair, Execution Leases, successor Sessions, generalized external dispatch, compensation, and other Intent families are not implemented.

## Verification

Host Execution contract tests pin strict safe and trusted schemas, raw-byte baseline completeness, hostile-path rejection, two-observation stability, cancellation, bounds, and the absence of mutation placeholders. Local-provider tests exercise ordinary, linked, detached, and separate-Git-directory repositories; common and worktree-specific config precedence; private-only repository Git; direct reparse rejection; source-config and checkout races; SHA-256 objects; explicit non-files ref-storage rejection; source object-alternate rejection; and split-index failure when the required shared index is outside the private view. Control-plane tests inject interruptions at every durable registration transition, including the possible Workspace-effect window and the Registry-commit-before-Intent window; reopen storage; and verify one stable result without duplicate effects. They also cover exact replay, changed-payload conflicts, path-index collisions, hostile durable records, current-Grant checks before effects, post-dispatch revocation recovery, Projection invalidation, and phase-specific receipts. The assembled source and plain-Node bundle scenarios register a real temporary Git repository, restart against the same SQLite database, replay the same Intent, and verify stable Project, Binding, and Workspace identities without recording a path, credential, or raw inherited-change value in the transcript.

## Alternatives considered

**Treat the browser locator or returned trusted path as authority.** A stale or substituted path could authorize a later Workspace effect without a current Host observation, and canonical Host paths would escape into browser state.

**Run repository-aware Git directly against the source administrative files.** A repository-owned config, HEAD, index, or linked-worktree control file could change between commands or activate repository-directed behavior. A private control snapshot narrows Git to the exact admitted files while the worktree and object database remain live data.

**Copy the complete worktree and object database or require operating-system isolation.** Either choice would provide a stronger immutable or process-level boundary, but it would turn a bounded local inspection into a potentially repository-sized copy or a platform sandbox. Version 0.1.0 instead fails closed for unsupported control layouts and documents the remaining live-data and same-user race limits.

**Create the Workspace and then write one final Registry record.** A crash or lost acknowledgement after creation would leave no durable phase that tells recovery to inspect and adopt the possible Workspace before retrying.

**Create the Workspace inside a storage update callback.** The callback may be retried and owns only one local record update; placing an external effect inside it would neither make the effect transactional nor make replay safe.

**Use a path or Workspace id as the Project and Binding identity.** Paths can move or gain aliases, and Workspace identity belongs to DSH. Separate Project and Resource Binding ids preserve product references while observations and Workspace association evolve under their owning records.

**Implement the complete Resource Binding and generic Control Intent designs in the first slice.** Rebind, retirement, leases, dispatch, and compensation need additional Consumers and lifecycle evidence. Adding their methods or states without those users would make planned semantics appear supported.

## Consequences

An authenticated Host Operator can inspect an existing local Git worktree, confirm its bounded inspection evidence, register it once, and retrieve revisioned Project-index and Development-Workspace Projections after restart. The recovery machinery adds durable intermediate records and repeated Host inspection, but it confines ambiguous outcomes instead of guessing that an external effect failed. An expected-revision loser can therefore leave a reusable DSH Workspace without a Saki Project or Resource Binding; repair and cleanup of that reusable registration remain outside this slice. Registration stores the caller locator as immutable replay content and the trusted observations as private control-plane recovery evidence; browser responses, diagnostics, and snapshots expose only sanitized or normalized values.

The operation set remains intentionally narrow. It does not create or move a repository, rebind or retire a Resource Binding, start an Agent Run, mutate Git, or resolve a reconciliation-required registration. Those capabilities require their own authority checks, durable evidence, and implemented Agent Notes before they extend the service.

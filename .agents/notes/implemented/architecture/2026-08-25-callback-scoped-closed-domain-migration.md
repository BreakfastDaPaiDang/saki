# Agent Note: Callback-scoped closed domain migration

Status: implemented

English | [中文](2026-08-25-callback-scoped-closed-domain-migration.zh.md)

## Problem

`storageDomain` previously opened only the exact current `DomainSpec`. That is correct for serving but cannot safely evolve an authoritative historical unit: ordinary open may create current state, keeps a live handle, and cannot publish into a separate missing candidate without exposing backend-specific layout. Direct backend reads would make product packages depend on JSON files or SQLite tables, while in-place migration would risk the only known-good source before product invariants and authority publication succeed.

The generic mechanism also needs an exact commit distinction. Cancellation or validation before target publication must leave no complete target. Once publication commits, a readback failure means a candidate exists and maintenance must clean it up; reporting both cases as the same failure would make recovery ambiguous.

## Decision

The optional `KvFacet.closed` group owns callback-scoped, fail-fast unit-name reservations. `withReservedUnit(name, signal, callback)` registers its reservation and backend-close completion before invoking the callback. A live, opening, or already-reserved unit rejects with `unit-open`; it never waits for another reservation. Once the scope observes either callback outcome it ends lease admission, so escaped leases and commit tokens reject with `closed`. The reservation is released only after every lease method admitted earlier drains, including methods the callback did not await, and backend close waits for the callback and the same admitted work.

A lease can inspect stored identity without mutation, read a detached snapshot through an exact descriptor, or create-only materialize a complete missing unit. Materialization observes the caller signal until publication and returns `KvClosedUnitMaterialization`: a `durable` result carries exact committed `readBack()`, while an `uncertain` result carries the commit failure and a `readBack()` that returns either the visible snapshot or `undefined` after confirmed absence. Only a result whose backend can prove non-publication rejects; such a rejection must not leave a unit that inspection recognizes as complete. Readback remains scoped to the reservation and ignores later cancellation.

Ordinary writes distinguish known publication with uncertain durability (`durability-uncertain`, `published: true`) from an undecidable commit (`commit-outcome-unknown`, `publicationPossible: true`). A direct unit stops serving after either result. The domain layer preserves the initiating backend error but neither adopts memory nor emits `domain/changed`; it poisons the domain so every queued and later read or write rejects `write-outcome-uncertain`, while close still drains and releases the unit. Recovery closes the handle, discards and recreates the affected backend (or restarts), and only then reopens from the medium; this conservative rule also covers providers whose uncertainty poisons a shared connection. A definite pre-publication failure keeps the previous memory and leaves the write chain usable.

A KV unit/domain version, whether declared or read from storage, is a non-negative safe integer; negative zero is invalid. `defineDomainMigrations` is the only plan constructor. It verifies ordered `N -> N+1` steps over one domain, requires shared declaration identity at intermediate versions and the exact current declaration at the end, captures frozen copies of the spec containers, and registers the plan under a module-private identity. Migration entry points reject structural forgeries, so a caller cannot bypass adjacency checks or mutate a registered plan through its original spec objects.

Determinism and absence of external effects are obligations of the registering caller. The synchronous callback receives only a detached, deeply frozen snapshot, which removes service handles from its declared inputs, but runtime validation cannot prove repeatability or detect clocks, network clients, process state, or other ambient imports. Review and caller-owned evidence establish those properties; the runner validates the data and publication results it can observe.

`DomainFacility.migrate` reserves the domain name, then nests source and target backend reservations. It rejects an existing target before inspecting or reading the source, selects a retained historical spec by the stored version and exact table/global layout, validates all source records, and passes a detached deeply frozen snapshot to each synchronous step. Sources and complete outputs must be exact JSON data before validation against the adjacent target spec: values whose encoding would omit or coerce data reject before publication. The source reservation remains held through target commit and current-schema readback; the source medium is never changed and no `domain/changed` event is emitted.

Pre-publication cancellation releases both reservations and leaves the target missing. After publication, readback and current-schema validation drain without observing late cancellation. The raw visible snapshot is compared with the intended validated snapshot before the visible value is parsed again; equality ignores object member order but preserves array order and exact numbers, so a dropped or changed schema-valid record is still invalid and schema transforms cannot hide divergence. An uncertain result with an exact returned target reports `migration-target-durability-uncertain` and `committed: true`; confirmed absence reports `migration-target-not-committed`; a rejected uncertain readback reports `migration-target-outcome-unknown`. A durable materialization whose readback rejects has a known commit but an unverifiable target, so it reports `migration-target-invalid` and `committed: true`; a successfully returned snapshot that is schema-invalid or divergent reports the same failure. The generic layer neither blindly retries nor deletes the target. `DomainFacility.materialize` uses the same validation, create-only publication, readback, and evidence classification for fresh current-version state. Facility teardown first stops admission, drains ordinary opens and cold operations admitted earlier, attempts every resulting live-domain close to settlement, reports one failure directly or several as an aggregate, and unmounts its storage form regardless of close failures.

The JSON provider stamps physical format version 1 and the unit's name, domain version, `hasGlobal`, global value, and actual table objects in each file. Ordinary and closed reads use fatal UTF-8 decoding and the shared strict lossless parser: byte-order marks, comments, trailing commas, nested duplicate members, and numeric lexemes that JavaScript would round, underflow, or overflow reject without changing the source. The backend resolves its root once, pins the first real directory identity it creates or observes, and checks that identity before and after reads and immediately around rename/link publication. A detected pre-publication replacement rejects without a final target; a replacement detected after namespace publication produces honest unknown-commit evidence, never deletes the final path through a stale string, and causes direct units or live domains to stop serving. Create-only publication uses a synced same-directory temporary file and a no-clobber hard link, never removes a linked target after directory-sync failure, and preserves uncertain readback evidence. Backend close synchronously stops live-unit admission and drains operations admitted earlier. Because portable Node path APIs cannot bind rename/link to an open directory handle, a same-user replacement inside the final unobserved path-resolution interval remains a deployment limitation.

The SQLite provider separates its physical schema version from domain versions. Physical version 2 stores `has_global` and explicit logical table rows, while record tables use hex-encoded unit and table segments so underscore-bearing names cannot collide. It requires UTF-8 databases and stores logical record keys as canonical JSON string text, preserving embedded NUL and unpaired surrogates without collisions. Key and value TEXT cells are selected as exact bytes, decoded with fatal UTF-8 handling, and only then decoded or parsed, so bridge truncation, replacement characters, non-canonical keys, and hidden suffixes cannot change migrated data silently. `sqlite_schema` SQL text, object types, names, and owning-table names follow the same exact-byte decoding before token and inventory validation; the inventory omits only exact implicit primary-key autoindexes. A file-backed ordinary open validates the complete v2 layout and all stored content on a frozen copy, repeats that validation on the original connection before writer configuration, and reads the requested unit exactly before exposing a live handle. It therefore rejects malformed media without changing its journal mode or source bytes. Current and legacy stored values use the shared strict JSON parser, which rejects duplicate members and numeric lexemes that JavaScript would round, underflow, or overflow. The closed reader additionally accepts the exact legacy physical-v1 subset needed by B03: one valid unit, no stored global row, and only its valid record tables. File-based closed reads copy the database plus any nonempty WAL and rollback-journal sidecars into a private directory, normalize each copied recovery file to owner-read/write mode, verify that source database/WAL/SHM/rollback-journal state did not change during the copy, and let SQLite replay or recover only the copy; they never use `immutable=1`, which can omit committed WAL frames. A missing database is recognized only when all three sidecar paths are also absent; an orphan WAL, SHM, or rollback journal is malformed and remains untouched by reads and creation attempts. A failed SQLite `COMMIT` is rejected as not published only when the transaction remains active and rollback succeeds; an ended transaction returns an uncertain result. An uncertain outcome, rollback failure, or entered ordinary write-statement failure poisons the shared connection, blocking its later reads and writes; file-backed recovery can still use a fresh frozen copy, while `:memory:` cannot expose the poisoned handle.

The generic layer does not choose generation paths, create backups, validate product-wide referential invariants, or publish authority. Those remain with the Saki Installation-maintenance Consumer described by the [manifest-selected Installation-maintenance decision](2026-08-26-saki-manifest-selected-installation-maintenance.md). A successful generic migration proves exact stored layout, historical and adjacent schemas, committed current-schema readback, and source immutability; Saki still opens the candidate through its normal current spec under the Installation lease before publishing the manifest.

## Alternatives considered

**Expose independent `inspect`, `read`, and `materialize` calls.** Separate calls leave reservation gaps and require every caller to release backend resources correctly. A callback-scoped lease keeps exclusion, invalidation, commit evidence, and close draining inside each adapter.

**Use ordinary `DomainFacility.open` for historical and candidate units.** Ordinary open is a serving path that may create a missing current unit and produces a live handle. It cannot hold two backend reservations continuously through commit readback, and using it would blur cold maintenance with event-emitting runtime state.

**Migrate the source in place.** A transaction cannot preserve an old-build-compatible source after current-schema writes or protect against product invariants discovered after commit. A separate create-only target keeps the source available until a higher layer publishes authority.

**Open SQLite through an immutable URI.** SQLite immutable mode assumes the file cannot change and may ignore a committed uncheckpointed WAL. A verified private copy includes nonempty WAL and rollback-journal sidecars, allowing replay or recovery without touching the source.

**Derive layout from values or delimiter-based table names.** A null global cannot distinguish an undeclared slot from a declared never-written slot, and underscore concatenation is not injective. Explicit `hasGlobal` metadata and hex segments make both identities exact.

## Consequences

Cold migration is opt-in: backends may omit `kv.closed`, and domains without a registered plan retain exact `version-mismatch` serving behavior. Migration requires different source and target backend instances and may copy a SQLite file several times during inspection, read, and committed readback; this cost is accepted for offline maintenance correctness.

JSON's physical header and SQLite physical v2 are deliberate pre-release format breaks. Ordinary adapters do not repair old media. SQLite retains one narrow, read-only physical-v1 path for the declared B03 source; it cannot write or generally serve that format.

A visible or possibly committed candidate can remain after post-publication validation or durability evidence fails. The explicit error classes let the owning maintenance journal distinguish confirmed visibility, confirmed absence, and an undecidable outcome from a retryable pre-publication failure, but the generic layer intentionally does not delete that candidate or select another medium.

Shared backend contracts cover non-negative safe unit versions, including rejection of negative zero and unsafe integers, same-turn live-unit rejection when backend close begins, reservation exclusion and expiry, immediate post-settlement rejection, draining admitted unawaited lease methods before reservation release and backend close, pre- and post-publication cancellation, create-only preservation, detached exact JSON ownership, every JavaScript string key, exact layout, and readback. Storage-domain tests cover invalid version declarations, forged and mutated plans, every retained source, invalid historical and adjacent records, target preflight ordering, exact semantic readback, durability/commit uncertainty, poisoned queued writes, teardown races, close-failure draining and unmount, and no events. Provider tests cover strict current and retained JSON bytes, invalid stored versions, fatal UTF-8 handling, source preservation, JSON root replacement around real rename/link operations, SQLite key encoding and transaction outcomes, and rejection of incompatible SQLite media before initialization changes them. Cross-provider tests run the complete retained chain in both JSON-to-SQLite and SQLite-to-JSON directions, open the durable target through the ordinary current serving path, and reopen the unchanged historical source.
